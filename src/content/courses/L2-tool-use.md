# L2 · 让模型能"行动"：工具调用

> 本层目标：理解 agent 的"手"是怎么长出来的。这是整门课**最关键的一层**——
> 它把模型从"只会聊天"变成"能改世界"。对应修补缺陷：**② 不能行动（只会说）**。
> 看懂这一层，你就懂了 80% 的"AI 能自动干活"到底是怎么回事。

---

## 0. 先讲一个画面

还是白房间里的顾问。你问他："我电脑桌面上有个 `报告.txt`，里面写了啥？"

顾问不可能知道——他在白房间里，碰不到你的电脑。但聪明的他会这么回你一张纸条：

> "我需要读这个文件。**请你（房间外的人）帮我执行：打开 `报告.txt`，把内容告诉我。**"

于是你（harness）真的去打开文件，把内容写在新纸条上塞回去。顾问读到内容，才接着回答。

**注意这里发生了什么：顾问自己一个字节的文件都没碰。他只是"写了一张申请单"，真正动手的是房间外的你。** 这就是工具调用（tool use / function calling）的全部秘密——**模型负责"决定调用什么"，harness 负责"真的去做"**。

---

## 1. 模型缺了什么：它的输出永远只是文字

L0 缺陷②：模型不能行动。它写出 `delete file` 这几个字，世界不会有任何变化——那只是字符。模型**永远只能输出文字，无法直接触碰文件、网络、终端、数据库**。

但很多任务的本质就是"要动手"：查今天天气、读一个文件、跑一段代码、下个订单。光会说没用。于是 harness 要搭一座桥：**让模型用"文字"表达"我想做这个动作"，再由 harness 把这段文字翻译成真实操作去执行，最后把结果用文字喂回模型。** 这座桥就是工具调用。

---

## 2. 这层怎么补：工具调用的闭环

工具调用是一个**四步闭环**，请记牢这张图，它是 agent 的心脏起搏器：

```
   ┌──────────────────────────────────────────────────────────┐
   │                                                          │
   │  ① 定义工具          ② 模型"申请"        ③ harness 执行    │
   │  harness 告诉模型：  模型输出一张        harness 读到申请， │
   │  "你有这些工具，     结构化"申请单"：    真的去跑这个动作， │
   │   各自能干嘛、       {tool: "读文件",    得到结果           │
   │   要什么参数"        args:{path:"报告"}} （文件内容）       │
   │                                                          │
   │                          ④ 结果回填                       │
   │                  harness 把结果当成一条消息               │
   │                  塞回 messages，再喂给模型                │
   │                  → 模型基于结果继续（可能再申请下一个）    │
   │                                                          │
   └──────────────────────────────────────────────────────────┘
```

逐步拆：

**① 定义工具（tool definition / schema）。** harness 在 system 区域附近，用结构化格式（通常是 JSON Schema——一种描述"数据长什么样"的标准格式）告诉模型："你有一个工具叫 `read_file`，作用是读文件，需要一个参数 `path`（字符串）。" 模型由此**知道自己有哪些手、每只手怎么用**。

**② 模型"申请"调用。** 模型决定要用某工具时，**不会执行**，而是输出一段特殊的结构化文字（一张"申请单"），写明：调哪个工具、参数填什么。比如 `{ "tool": "read_file", "args": { "path": "报告.txt" } }`。这一步它仍然只是"输出文字"——完全没违反 L0 缺陷②。

**③ harness 执行（tool execution）。** harness 解析这张申请单，**用普通代码真的去执行**：打开文件、调天气 API、跑命令……拿到结果。**这一步纯粹是确定性代码，没有模型参与。** 这正是 L0 说的"判断交给模型、执行交给确定性代码"。

**④ 结果回填（tool result）。** harness 把执行结果打包成一条新消息（角色通常叫 `tool`），塞回 messages 列表末尾，再次调用模型（回到 L1 的"整叠纸重发"）。模型这下"看到"了文件内容，可以继续——回答你，或者再申请下一个工具。

> **核心洞察：模型从不亲自动手，它只会"开申请单"。所有真实副作用（删文件、发请求、花钱）都发生在 harness 的第③步。**
> 这就是为什么**安全和权限的控制点天然落在 harness**：要不要批准这张申请单，由你的代码（或你本人）说了算，模型管不着。

## 3. 底层原理：为什么这么设计，以及它带来什么

**为什么让模型"只申请、不执行"？** 三个原因，全是工程智慧：

1. **安全可控。** 执行权握在 harness 手里，就能在第③步插入检查："这是 `rm -rf`？先弹窗问用户。" 如果模型能直接执行，就没有任何刹车了。
2. **能力可扩展。** 想让 agent 多一项本事？不用重训模型，**给它多定义一个工具**即可。工具是 harness 给模型"插的外设"，即插即用。
3. **职责清晰。** 模型只干它擅长的"判断该用哪个工具、参数填啥"；脏活累活（IO、网络、错误处理）交给确定性代码。

**它带来的两个关键认知：**

- **工具的"说明书"质量直接决定 agent 聪不聪明。** 工具描述写得含糊，模型就不知道何时该用、参数怎么填，频频用错。**写好工具定义（名字、描述、参数说明），是 harness 工程师的核心手艺之一**，本质上是在给模型写"使用说明书"。
- **错误也要喂回去。** 工具执行失败（文件不存在、网络超时），harness 不该崩溃，而应把**错误信息当作结果**塞回去。模型看到"文件不存在"，往往能自己改路径重试。这是 L3 循环和 L7 可靠性的伏笔。

### MCP：工具的"通用插座"（顺带一提）

你可能听过 **MCP（Model Context Protocol，模型上下文协议）**。它是一个让"工具"标准化、可插拔的开放协议——把工具做成符合 MCP 的"插件"，任何支持 MCP 的 harness（包括 Claude Code）都能即插即用，不用各写各的。理解到"它是工具的通用插座标准"这一层就够了，细节后面有需要再深挖。

## 4. Claude Code 锚点：它的每一项本事都是一个工具

Claude Code 之所以能干活，全靠一套挂在模型上的工具。你用它时的每个动作，背后都是这个四步闭环：

| 你看到 Claude Code | 背后的工具调用闭环 |
|---|---|
| "正在读取 `foo.ts`" | 模型申请 `Read(path)` → harness 真去读文件 → 内容回填 → 模型继续 |
| "运行 `npm test`" | 模型申请 `Bash(cmd)` → harness 真在终端执行 → 输出（含报错）回填 → 模型看结果 |
| "编辑了 `bar.py`" | 模型申请 `Edit(old,new)` → harness 真改文件 → "改好了"回填 |
| **弹出"是否允许运行此命令？"** | 正是第③步执行前的**权限闸**——危险申请单先交你批准，模型无权越过 |
| 你装的 MCP 服务器（如 Superpowers 的工具）| 通过 MCP 标准插进来的额外工具，对模型来说和内置工具一样用 |

下次 Claude Code 报"命令执行失败"然后自己换个方式重试——你现在知道了：那是**错误结果被回填，模型读到后重新申请**。整个"自我纠错"的观感，就是这个闭环在转。

## 5. 小练习 / 思考题

1. 用"申请单"模型解释：为什么即使模型在回答里写出了 `rm -rf /`，你的电脑通常也不会被删？真正的安全闸在哪一步？
2. 你想给一个客服 agent 加"查订单状态"的能力。按四步闭环，列出 harness 需要做哪些事、模型负责哪一步。
3. **判断对错**：工具执行报错了，最好的做法是 harness 直接抛异常、终止 agent。
4. 为什么说"工具的描述写得好不好，直接影响 agent 表现"？这本质上是在影响模型的哪一步决策？
5. 自检：不看图，默写工具调用的四步闭环，并指出"真实副作用发生在第几步、由谁执行"。

<details>
<summary>参考答案</summary>

1. 因为模型写出 `rm -rf /` 只是**输出文字（申请单）**，并不会执行（缺陷②）。只有 harness 在第③步去执行才会有真实后果——而正经 harness 会在第③步前设**权限闸**（危险命令要用户批准）。安全闸在第③步执行前，不在模型那里。
2. **harness**：① 定义 `query_order(order_id)` 工具并写清说明；③ 收到申请后真的去查数据库/调订单 API；④ 把订单状态打包回填。**模型**：② 判断"用户在问订单，我该调 query_order，参数 order_id=12345"，输出这张申请单。
3. **错。** 应把错误信息**当作工具结果回填**给模型，让它有机会自我纠错（换参数、换方法重试）。直接终止会浪费模型的纠错能力，也是 L3/L7 要避免的脆弱设计。
4. 工具描述是模型的"使用说明书"，直接影响第②步——模型**判断何时调用、参数怎么填**。说明书含糊，模型就乱用、错填。所以写工具定义本质是给模型写决策依据。
5. ①定义工具 →②模型开申请单 →③harness 真执行 →④结果回填再喂回。真实副作用在**第③步**，由 **harness（确定性代码）**执行，模型全程只输出文字。

</details>

## 一句话带走

> **Agent 的"手"不长在模型上，长在 harness 上。模型永远只会"开一张结构化申请单"，真正动手、产生一切真实后果的是 harness——这也正是权限、安全、能力扩展的全部抓手所在。**

下一层 **L3**，我们把单次的"申请—执行"接成一个**循环**。正是这个循环，让模型从"答一句"变成"能连续干活直到任务完成"——agent 之所以是 agent 的那一步，就在这里。
