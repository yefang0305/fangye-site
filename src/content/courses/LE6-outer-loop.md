# LE6 · 外循环：评测 / 人在环 / 飞轮

> 本章目标：拧最后一个旋钮，并把镜头从"单个任务之内"猛地拉远到"许多任务之上"。再好的内循环，也要靠一个慢得多的大循环，才能让整个系统一代比一代强。
> 拧的旋钮：⑥ 外循环（outer loop）——跨任务的改进闭环。

---

## 0. 先讲一个画面

你开了家装修公司。你不会指望工人**第一单**就完美——也没有哪个老板这么指望。

真正让公司变强的，是另一个循环：每完成一单，你去看成品 → 记下"这家客户嫌收边毛糙""那次颜色调错了" → 下一单改流程、换工具、给工人定新规矩 → 再接单 → 再复盘……这个**跨工单让公司越来越强**的循环，就是**外循环**。

注意它和前五章的尺度差异：前五章都在调**一个任务内部**那台发动机的旋钮（秒级）；这一章跳到**任务之上**，调的是"让发动机一代比一代好"的那个慢循环（天/周级）。

> 关系说明：外循环是 Harness 课几乎没碰的增量。它和内循环不是两个东西，而是**同一个"循环"思想在两个时间尺度上的复用**——这正是本课最后想留给你的统一视角。

---

## 1. 核心概念：评测、人在环、飞轮、可观测性

| 概念 | 大白话 | 在外循环里的角色 |
|---|---|---|
| **外循环**（outer loop） | 跨任务/会话、天周级的改进循环 | 整个机制本身 |
| **评测闭环**（eval loop） | 攒一组测试用例 → 跑 agent → 看失败 → 改 prompt/工具/外壳 → 再跑 | 外循环的"心跳" |
| **人在环**（human-in-the-loop） | 人的反馈在某个环节进来：审批、纠正、打标 | 给外循环提供判断和标注 |
| **数据飞轮**（data flywheel） | 失败样本沉淀成下一轮的用例/改进燃料，越跑数据越多越准 | 让改进**复利** |
| **可观测性**（observability） | 日志/轨迹记录，看清循环到底在哪一步坏的 | 一切改进的前提 |

术语注释：
- **外循环（outer loop）**：相对于"运行时内循环"，指工程师跨许多次任务、用天/周为单位迭代改进整个 agent 系统的循环。
- **评测 / eval（evaluation）**：用一组固定的测试用例去**量化**agent 表现，让"改得好没好"有客观依据，而不是凭感觉。
- **人在环（human-in-the-loop）**：让人类在关键环节介入——审批高风险动作、纠正错误输出、给数据打标签——人的反馈是外循环最贵也最关键的输入。
- **数据飞轮（data flywheel）**：失败和真实使用产生的数据，被收集起来变成下一轮改进的燃料；用得越多、数据越多、系统越准、又吸引更多使用，形成正反馈。

## 2. 原理"为什么"：内循环让任务跑完，外循环让系统变好

这是全课最后、也最重要的一个观念转弯：

**内循环再完美，也只解决"这一个任务"。** 系统会不会一个月后比今天强，跟内循环无关——那是外循环的事。两件事必须分开看：

- 内循环（LE1–LE5）：给定当前的 prompt、工具、外壳，把**眼前这个任务**自主跑完。
- 外循环（本章）：通过看大量任务的成败，去**改进那个 prompt、工具、外壳本身**，让所有未来的内循环都变好。

外循环有两条铁律：

1. **没有评测就是盲改。** 如果你不先用一组用例量化"现在错在哪、改完好没好"，你的每一次"优化"都是凭感觉、可能越改越差还不自知。评测闭环是外循环的心跳——它把"我觉得变好了"换成"在 100 个用例上从 72% 到 81%"。这正呼应了 LE3："纠错质量取决于反馈质量"——只不过这次纠的是整个系统，反馈来自评测集。
2. **飞轮让改进复利。** 每次失败如果只是"修掉就算了"，你永远在原地打补丁；如果把失败**沉淀成一条新用例**，它就永久进了你的评测集，保证这个错以后不再回来，且数据越滚越厚、系统越来越准。这就是"飞轮"——改进会累积、会复利，而不是一次性。

> 原理一句话：**内循环和外循环是同一个"循环"思想的两个时间尺度——内循环用反馈把单个任务做完，外循环用反馈把整个系统做好。没有评测的改进是盲改，没有飞轮的改进不复利。**

## 3. 结构图：大循环套着小循环

```
┌──────────── 外循环 OUTER LOOP（天/周级）─────────────────────┐
│                                                              │
│   评测集 ──→ 跑 agent ──→ 看失败 ──→ 改 prompt/工具/外壳 ──┐ │
│     ▲           │                                         │ │
│     │           │  每个任务内部跑的是……                   │ │
│     │       ┌───▼──────────────────────────────┐         │ │
│     │       │  内循环 INNER LOOP（秒级）         │         │ │
│     │       │  想→做→看→…（LE1–LE5 五个旋钮）   │         │ │
│     │       └──────────────────────────────────┘         │ │
│     │                                                     │ │
│     │   失败样本沉淀成新用例（数据飞轮）                   │ │
│     └─────────────────────────────────────────────────────┘ │
│         人在环：审批 / 纠正 / 打标，在多处注入反馈            │
└──────────────────────────────────────────────────────────────┘
```

读图要点：内循环（LE1–LE5）原封不动地被套在外循环里当"被改进的对象"；外循环转一圈是天/周，每圈让里面那台内循环发动机变好一点；失败样本回流成评测集，就是飞轮。

## 4. Claude Code 锚点：你和它一起在跑外循环

| 你在 Claude Code 里做的事 | 对应外循环的哪部分 |
|---|---|
| 让它跑完后用 verification-before-completion 核对"真做到了没"（证据而非声称） | 给外循环提供**可信的成败信号**（没有这个，评测就是假的） |
| 用 code-review 复查它的产出、把问题反馈回去 | **人在环**——人的判断注入循环 |
| 你发现它总在某类活上犯同样的错，于是往 `CLAUDE.md` 加一条规则 | 外循环转了一圈：看失败 → 改外壳 → 下次更好 |
| 先用 writing-plans 写计划再执行 | 一种外循环纪律——把"怎么做"先固化下来，便于复盘和改进 |

观察练习：回想你用 Claude Code 这段时间——你其实**一直在手动跑外循环**：发现它不好用的地方、改提示词或 `CLAUDE.md`、下次验证有没有变好。本章只是把这件你凭直觉做的事，升级成有评测、有飞轮的系统工程。下一步可以试着把"它常犯的错"记成一个小清单（你的私人评测集），每次改完外壳就对照跑一遍——你就拥有了一个真正的外循环。

## 5. 小练习 / 思考题

1. 内循环和外循环的**时间尺度**和"转一圈做什么"各是什么？为什么说它们是"同一个思想的两个尺度"？
2. 为什么说"没有评测的改进 = 盲改"？评测把什么"凭感觉"换成了什么"可量化"？
3. 数据飞轮怎么让改进"复利"？把失败"修掉就算了"和"沉淀成新用例"长期看差别有多大？
4. "人在环"可能在外循环的哪些环节注入？各起什么作用？

<details>
<summary>参考答案</summary>

1. 内循环：秒级、单任务内，一圈=想→做→看→再想；外循环：天/周级、跨任务，一圈=跑一批→看失败→改外壳→再跑。说它们同源，是因为本质都是"用反馈驱动下一轮变好"——只是一个改进"这次任务的进展"，一个改进"整个系统的能力"。
2. 因为不量化就无法客观判断"改完到底好了没"，每次优化都凭感觉、可能越改越差还不自知。评测把"我觉得变好了"换成"在 N 个用例上从 X% 到 Y%"这样可量化、可对比的依据。
3. 把每个失败沉淀成一条永久进评测集的新用例，保证这个错以后不再回来，且数据越滚越厚、系统越来越准——改进会累积、复利。只"修掉就算了"则永远在原地打补丁，老错可能反复回来。
4. 审批（高风险动作执行前，呼应 LE2 的"停下问人"）、纠正（输出错了人来改）、打标（给数据标注对错，喂给评测/飞轮）。作用：提供机器拿不准的判断，并产出高质量标注数据。

</details>
