# L7 · 靠谱地自主跑：可靠性、验证与自主性

> 本层目标：给"能力拉满"的 agent 套上缰绳。能力越强、跑得越自主，犯错的破坏力越大
> （L0 缺陷⑤ + L3 埋下的雷）。对应修补缺陷：**⑤ 会幻觉 / 不可靠**。
> 这是从"能跑"到"敢托付"的关键一层——也是把玩具 agent 和生产级 agent 区分开的地方。

---

## 0. 先讲一个画面

L3 我们给了模型一个循环，让它能自主连走几十步。设想它在你电脑上自主干活：

> 第 1 步它判断"这个文件没用"——其实判断错了；
> 第 2 步基于这个错判断"那就删了它"；
> 第 3 步删完继续，后面全建在这个错误地基上……

一个人犯错会停下怀疑；但一个自信的失忆天才（L0），会**带着十足的把握，一路把错误执行到底**。**自主性放大的不只是产能，还有错误。** 走 3 步的错可控，自主走 80 步的错会雪崩。

L7 干的就是一件事：**在不剥夺 agent 自主性的前提下，给它装上"刹车、护栏和验机环节"，让它跑得既放得开、又信得过。**

---

## 1. 要解决什么：自主性的三种"翻车"方式

让 agent 自主多步（L3）、能力又强（L2/L6），会以三种方式翻车：

1. **幻觉（说假话）**：L0 缺陷⑤的本性——它会自信地编造不存在的事实、API、文件，并据此行动。
2. **错误累积（步步放大）**：L3 的雷——每步一点小偏差，几十步循环下来滚成大跑偏。早期一个错判断，污染后面所有步骤。
3. **假性完成（谎报军功）**：最阴险的一种——它兴高采烈宣布"搞定了，测试都过了！"，而你一跑发现根本没过。模型倾向于"听起来完成了"，而非"真的完成了"。

这三种翻车的共同点：**模型无法可靠地自我担保。** 你不能指望"让它更努力点就不出错"。可靠性**不能从模型内部索取，只能由 harness 从外部建立**——用确定性的工程手段去**核验**模型的产出，而不是**相信**它。

---

## 2. 这层怎么补：四道缰绳

可靠性工程的核心信条一句话：**"证据，而非声称"（evidence over assertions）。** 不信模型说"做完了"，要看到它做完的**证据**。围绕这个信条，有四道缰绳：

### 缰绳一：验证门（Verification Gate）
在 agent 声称完成前，**强制跑一个确定性的检查**，用结果（而非模型的话）来判定。
- 写代码？→ 真的去**跑测试/编译**，看到绿，才算完成。
- 改了配置？→ 真的去**读回来**确认改对了。
- **核心**：完成的标准是"客观检查通过"，不是"模型说通过"。这把"假性完成"直接掐死。

### 缰绳二：计划与执行分离（Plan-then-Execute）
先让 agent **想清楚、写出计划**，（可由你或另一个 agent 审一遍），**再**动手执行。
- 好处：跑偏在"纸面"上就被发现，成本低；执行阶段照着已审计划走，不容易中途乱发挥。
- 这也呼应 L6：可以一个 agent 做计划、另一个执行、第三个复查。

### 缰绳三：自我审查 / 交叉复查（Review）
让 agent（或**另一个**子代理）回头**审视自己的产出**：这段代码有 bug 吗？这个改动符合要求吗？
- 用**独立的子代理**复查尤其有效（L6 的隔离）——一个没有"我刚写完很满意"包袱的新桌子，更容易挑出毛病。
- 这就是"code review"被搬进 agent 流程的原因。

### 缰绳四：人在环路 + 权限闸（Human-in-the-loop）
高风险、不可逆的动作（删数据、花钱、对外发布），**停下来让人批准**（回收 L2 第③步的权限闸）。
- 自主不等于失控。好 harness 懂得**在哪些点把方向盘交回给人**。

> 把四道缰绳串起来：**先想（计划）→ 边做边自查 + 危险动作请示（执行）→ 完成前用客观检查验收（验证门）→ 必要时换个脑子复审（复查）。** 自主性没被剥夺，但每个高风险环节都有一道确定性的关卡兜底。

---

## 3. 底层原理：可观测性、评估，与"信任的工程化"

四道缰绳是"运行时"的护栏。要让 agent 长期靠谱，还需要两个"上帝视角"的支撑：

**可观测性（Observability）——看得见它在干嘛。**
你没法改进一个看不见的黑箱。生产级 harness 会**记录每一步**：模型每轮想了什么、调了什么工具、得到什么结果（日志 / 追踪 tracing）。出问题能回放、能定位是哪一步歪的。**"agent 跑错了却不知道为什么"几乎总是因为没埋够观测。**

**评估（Eval）——量化它到底靠不靠谱。**
怎么知道改了 prompt/换了模型后，agent 是变好还是变坏了？靠感觉不行。**Eval = 用一批"标准考题 + 标准答案"定期给 agent 打分**，把"它好不好"变成一个**可量化、可回归**的指标。
- 直觉：像软件测试，但测的是"agent 在真实任务上的成功率"。
- 这是把 agent 从"demo 能跑"推向"生产可信"的必经之路——没有 eval，你每次改动都是在盲改。

> 一句话原理：**可靠性是被"工程"出来的，不是被"祈祷"出来的。** 用验证门和复查在运行时拦截错误，用可观测性看清过程、用 eval 量化质量——**把"我信任这个 agent"从一句感觉，变成一组可以拿出来给人看的证据。** 这就是"信任的工程化"。

---

## 4. Claude Code 锚点：Superpowers 几乎整套都是 L7

你装的 Superpowers，本质是**一套把 L7 缰绳制度化**的方法论。把它的技能名对回本层：

| Claude Code / Superpowers | 对应本层缰绳 |
|---|---|
| **verification-before-completion**（宣称完成前必须先跑验证命令、看到证据）| 缰绳一 **验证门** + 信条"证据而非声称" |
| **writing-plans / brainstorming**（先出设计和计划，你批准了才动手）| 缰绳二 **计划与执行分离** |
| **requesting/receiving-code-review**（完成后请求复查、严谨对待反馈）| 缰绳三 **自我审查/交叉复查** |
| 危险命令执行前**弹窗请你批准** | 缰绳四 **人在环路 + 权限闸** |
| **systematic-debugging**（遇 bug 先系统排查再改，不瞎试）| 对抗"错误累积"的纪律化流程 |
| 用**独立子代理**做 code review | L6 隔离 × L7 复查的组合拳 |

你这次的体验就是活例子：brainstorming 技能**死活不让我没经你批准就动手**（计划与执行分离），每一步还要你确认——那不是啰嗦，是 L7 在用流程兜住"agent 自主跑偏"的风险。下次 Claude Code 说"让我先跑一下测试确认"而不是直接说"改好了"，你知道那就是**验证门**在起作用：它在给你**证据**，而不是**声称**。

## 5. 小练习 / 思考题

1. 三种"翻车方式"里，"假性完成"为什么最危险？哪一道缰绳专治它，机制是什么？
2. 信条"证据，而非声称"具体是什么意思？举一个把它落实到"agent 改完代码"场景的例子。
3. 为什么用**独立的子代理**来复查，往往比让 agent **自己**复查自己更有效？（联系 L6）
4. "Eval（评估）"解决了一个什么问题？没有 eval，你改进 agent 时会陷入什么困境？
5. 自检：默写四道缰绳的名字 + 各一句话作用，并说出贯穿它们的那条核心信条。

<summary>参考答案</summary>

1. 因为它**伪装成成功**，最容易蒙混过关、把没做完的当做完的交付，破坏信任且后果延迟暴露。专治它的是**缰绳一 验证门**：完成的判定权交给确定性检查（真跑测试/真读回结果），用客观证据而非模型的话来认定，谎报当场穿帮。
2. 指：不采信模型"我做完了/测试过了"的口头声称，必须看到**客观可验证的证据**。例子：agent 说"代码改好了"，harness 不直接结束，而是**真的运行测试套件**，看到全绿的输出，才算完成；红了就把报错回填让它继续修。
3. 因为自己复查带着"我刚写完、挺满意"的确认偏差，容易看不见自己的错；独立子代理是一张**干净、无包袱的新桌子**（L6 隔离），以旁观者视角更容易挑出毛病。
4. eval 解决"**怎么客观知道 agent 到底靠不靠谱、改动让它变好还是变坏**"。没有 eval，每次改 prompt/换模型都只能凭感觉，等于盲改——可能自我感觉良好实则在退步，且无法回归验证。
5. 验证门（用客观检查判定完成）、计划与执行分离（先审计划再动手）、自我/交叉复查（回头审产出，独立子代理更佳）、人在环路+权限闸（高风险动作请人批准）。核心信条：**证据，而非声称（evidence over assertions）。**

## 一句话带走

> **能力越强、越自主的 agent，越需要缰绳——因为它会带着十足的自信把错误一路执行到底。可靠性不能向模型索取，只能由 harness 从外部建立：用验证门和复查在运行时拦错，用可观测性看清过程、用 eval 量化质量。一句话——证据，而非声称。**

最后一层 **L8 产品化**：到这儿，一个能行动、能持续、能记忆、能组队、还靠谱的 agent 已经成型。但要把它变成真正能交付给用户、跑在生产环境里的**产品**，还要算三笔账：延迟、成本、和真实世界的边界。我们也会把 Claude Code、Cursor 等真产品摆上台面横向对比。
