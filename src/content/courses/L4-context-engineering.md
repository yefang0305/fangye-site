# L4 · 装得下、记得住：上下文工程

> 本层目标：掌握 harness 工程里**最考手艺、回报最高**的一门技术——在有限的上下文窗口里，
> 只装最该装的东西。对应修补缺陷：**④ 容量有限**。这一层是"为什么有的 agent 越用越笨、
> 有的却始终清醒"的答案，也是你"把 Claude Code 用到极致"的最大杠杆。

---

## 0. 先讲一个画面

把模型的上下文窗口想成一张**有限大小的办公桌**。你要它处理一个任务，就得把相关资料摊在桌上——它只能看见桌上的东西。

- 桌子太空（资料没给够）：它两眼一抹黑，瞎猜、幻觉。
- 桌子堆满（把整个档案室都搬上来）：① 桌子根本放不下（**溢出**）；② 就算放下，它在一座纸山里**找不到重点**，反而把关键那张压在底下忘了看（**中间遗忘**）；③ 每次"扫一遍整张桌子"又慢又费钱（**token 成本**）。

**上下文工程（context engineering）= 当好这张办公桌的管家：每一轮，精准地决定"哪些资料该摊上桌、哪些该收进抽屉、哪些该缩成一张便利贴"。** 这就是本层的全部。

---

## 1. 模型缺了什么：窗口是稀缺资源，且有个隐藏陷阱

显性约束你已经知道（L1）：上下文窗口（context window）有 token 上限，messages 太长会溢出。而 L3 又火上浇油——循环每转一圈，messages 就变长一截，复杂任务转几十圈，迟早撑爆。

但真正的杀招是那个**隐藏陷阱**，叫**上下文腐烂（context rot）/ 中间遗忘（lost in the middle）**：

> 即使没溢出，**塞进去的内容越多、越杂，模型的表现反而越差**。研究反复发现，模型对**开头和结尾**的信息最敏感，对**中间**的信息容易"视而不见"。一张堆满的桌子，不是"信息更全"，而是"信号被噪声淹没"。

所以核心矛盾被钉死了：

> **信息太少 → 它不懂、会瞎猜；信息太多 → 它溢出 / 变慢变贵 / 还在噪声里丢掉重点。**
> harness 的任务不是"塞得越多越好"，而是**"在正确的位置放正好够用的信息"**。这就是为什么"上下文窗口大到 100 万 token"也消灭不了这门手艺（回收 L0 那道思考题）。

## 2. 这层怎么补：管理上下文的四把手术刀

好的 harness 用四类技术动态裁剪上下文。把它们想成桌面管家的四个动作：

### 刀一：裁剪 / 过滤（Trimming）
最朴素：**只放相关的，扔掉无关的**。比如工具返回了 500 行日志，但只有报错那 3 行有用——harness 在回填前先**截断/筛选**，别把 500 行全塞回 messages。原则：**进入上下文的每个 token 都该挣得它的位置。**

### 刀二：压缩 / 总结（Compaction / Summarization）
当历史 messages 太长，harness 调用模型（或用规则）把**前面一大段对话总结成一小段**，用这段摘要**替换掉**原始的长历史。
- 例：前 40 轮对话（5 万 token）→ 压成一段"目前为止我们做了 X、决定了 Y、还差 Z"（2 千 token）。
- 代价：会**丢细节**。所以压缩时机和保留什么，是手艺。这正是你在 Claude Code 里看到"Compacting conversation…"时发生的事。

### 刀三：检索注入（Retrieval / RAG）
把海量知识**放在窗口外面**（数据库/文件里），**用到哪段才捞哪段**塞进上下文。这就是 **RAG（Retrieval-Augmented Generation，检索增强生成）**：
- 流程：用户问问题 → 先去外部知识库**检索**出最相关的几段 → 只把这几段连同问题一起塞进 messages → 模型基于这几段作答。
- 直觉：不是把整个图书馆搬上桌，而是"按需去书架上抽出那一页"。RAG 是给 agent 接入大体量私有知识（你的文档、产品手册）的主流方式。

### 刀四：外部记忆 / 卸载到文件（Offloading）
把不需要时刻在眼前的信息**写到文件/外部存储**，上下文里只留一个"指针/目录"，需要时再用工具（L2 的 Read）读回来。
- 直觉：桌上只放一张便利贴写着"详细方案见 D 盘 plan.md"，要看时再去读。
- 这把"无限大的硬盘"变成了 agent 的外部记忆，绕开了窗口上限。Claude Code 大量用这招（不把整个代码库塞进去，而是按需 Read 文件）。

> **把四刀串起来看，上下文工程就是一道持续的取舍题：每一轮，对每一块信息问三句——它现在用得上吗？(裁剪) 它能更短吗？(压缩) 它能先收起来、要用再取吗？(检索/外部记忆)**

## 3. 底层原理：为什么这是"工程"而非"运气"

- **上下文是预算，要像花钱一样花。** 窗口的每个 token 都有成本（钱、速度、以及"挤占信号"的注意力成本）。优秀 harness 把上下文当**预算**来主动分配，而不是被动地"有啥塞啥"。这种"主动经营上下文"的意识，是新手和高手的分水岭。
- **位置即权重。** 既然模型偏重开头结尾，harness 会把**最重要的指令放 system（开头）、把当前最关键的信息放最近（结尾）**，把次要的压缩进中间。布局本身就是一种控制手段。
- **"少而精"常胜"多而杂"。** 反直觉但关键：给模型更少、更相关的上下文，往往比给它更多、更全的上下文**效果更好**。这直接颠覆"资料给越全越保险"的产品直觉。
- **它是 L5（记忆）和 RAG 的共同地基。** 记忆系统本质就是"该把哪条往事捞回上下文"的检索问题；RAG 是"该把哪段知识捞回上下文"。两者都是上下文工程的特例——所以这一层吃透了，下一层会很轻松。

## 4. Claude Code 锚点：它一直在帮你管这张桌子

你"把 Claude Code 用到极致"的最大杠杆，就在这一层。它无时无刻不在做上下文工程：

| 你看到/做的 | 背后的上下文工程动作 | 对应哪把刀 |
|---|---|---|
| "Compacting conversation…" | 把变长的对话历史**总结压缩**成短摘要，给窗口腾地方 | 刀二 压缩 |
| 它**不**把整个项目读进来，而是"按需"`Read` 某个文件 | 代码库放在窗口外，**用到才捞** | 刀四 外部记忆 |
| `CLAUDE.md` / memory 文件被注入开头 | 把"长期该记住的规则"放在 system 区（开头=高权重位） | 位置即权重 |
| 工具返回超长输出时它只引用关键几行 | 回填前**截断/筛选**，不把整坨塞回 | 刀一 裁剪 |
| 你主动 `/clear` 开新会话 | 清空堆积的上下文，从"干净的桌子"重新开始 | 你手动行使裁剪 |

**实操贴士（直接提升你用 Claude Code 的水平）**：
- 任务切换时主动开新会话/`/clear`，别在一张堆满旧任务的桌子上继续——又慢又容易串味。
- 把长期约定写进 `CLAUDE.md`，而不是每次在对话里重复——等于把它钉在高权重的开头位。
- 大文档别一股脑粘进对话，放成文件让它按需读——把刀四用在你自己身上。

## 5. 小练习 / 思考题

1. 用"办公桌"比喻解释"中间遗忘（lost in the middle）"：为什么把资料堆满桌子反而可能让模型漏掉关键信息？
2. 反驳这句话："等上下文窗口大到 1000 万 token，上下文工程就没意义了。"（至少给两个理由）
3. 四把刀里，"压缩"和"外部记忆"都能给窗口省地方，它们的关键区别是什么？各自的代价/适用场景？
4. 你要给公司内部文档做一个问答 agent，文档有几千页。为什么不能（也不该）把几千页全塞进上下文？该用哪把刀，怎么用？
5. 自检：默写上下文工程的核心矛盾（一句话），以及四把手术刀的名字和各自一句话作用。

1. 桌上资料越多，关键那张越可能被压在中间、淹没在噪声里；模型对开头结尾敏感、对中间易"视而不见"，于是"信息更全"反而变成"信号更弱"，关键信息被漏看。
2. ①**中间遗忘/上下文腐烂**不随窗口变大消失——塞得越满越容易丢重点、表现下降；②**成本与速度**：token 越多越贵越慢，把 1000 万都填满每轮都是天价且龟速。所以"该放什么、不放什么"的取舍永远在。
3. **压缩**：把历史**总结成摘要替换原文**，信息仍在上下文里但**丢了细节**，适合"大意要留、细节可弃"的长对话历史。**外部记忆**：把信息**移出上下文存到文件**，细节**完整保留**，上下文只留指针，要用再 Read 回来，适合"细节不能丢、但不必时刻在眼前"的大块资料。
4. 因为会溢出 + 即使不溢出也会中间遗忘 + 极贵极慢。该用**刀三 RAG**：把几千页存进可检索的知识库，用户问问题时先检索出最相关的几段，只把这几段塞进上下文作答。
5. 矛盾：信息太少则瞎猜、太多则溢出/变慢/丢重点，要在对的位置放正好够用的信息。四刀：裁剪（只放相关、扔无关）、压缩（长历史总结成摘要）、检索/RAG（按需从外部捞相关片段）、外部记忆（卸载到文件、留指针按需读回）。

## 一句话带走

> **上下文窗口是一张有限的办公桌，而上下文工程就是当好它的管家——靠裁剪、压缩、检索、外部记忆这四把刀，每一轮都精准决定"什么摊上桌、什么收进抽屉"。记住：不是塞得越多越聪明，而是放得越准越清醒。**

下一层 **L5 记忆系统**：上下文工程管的是"这一次任务内"的桌面；但怎么让 agent **跨会话、跨天**还记得你是谁、你的偏好、上次聊到哪？你会发现，记忆本质上就是上下文工程的一个特例——"该把哪条往事捞回桌上"。
