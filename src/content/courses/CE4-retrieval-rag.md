# CE4 · 检索注入（RAG）：图书馆放窗外，用到哪页捞哪页

> 本章目标：磨亮 L4 的**刀三 检索注入（RAG）**——当知识量大到几千页、几百万 token，根本摊不上桌，怎么办？答案是：把整座图书馆放在窗口**外面**，每次只按需抽出**最相关的那几页**摊上桌。本章深挖 L4「刀三 检索注入 RAG」，把它从一个名词讲成一套可上手的手艺。
> 拧的旋钮：知识规模远超窗口容量时，**"放什么进桌面"从静态选择变成动态检索**。

---

## 0. 先讲一个画面

上一章 **CE3 压缩**，处理的是**已经摊在桌上、但太长了**的东西——把四十轮对话压成一段摘要。它的前提是：信息本来就在桌上。

这一章的难题完全不同：信息**从一开始就上不了桌**。

想象你要给公司做一个客服 agent，背后是一套产品文档——**几千页**，几百万字。用户问一句"退款要几天到账"，你会怎么把文档给模型？

- 全搬上桌？桌子（上下文窗口）根本放不下，**溢出**直接报错。
- 就算放得下？模型在几千页里翻找那一句话，又慢又贵，关键信息淹没在中段——**中间遗忘**，反而答不准。

聪明的图书管理员从不会这么干。你问他"退款几天到账"，他不会把整座图书馆搬到你面前，而是**走到书架前，精准抽出讲退款政策的那一页**，递给你。

> **这就是 RAG 的全部直觉：知识放在窗口外的"书架"上，用到哪段，才去捞哪段摊上桌。** 模型的桌子始终干净，桌上永远只有"这个问题正好需要的那几页"。

CE2 教你把无关的从桌上扔掉，CE3 教你把太长的压短——这两刀都在**桌面之内**做减法。刀三换了个战场：它让海量知识**根本不必先上桌**，而是建一座外部书架，按需取阅。

## 1. 核心概念：从"问题"到"那几页"的五个零件

RAG 听起来玄，拆开只有五个零件。一句话说清它们各自干什么：

| 概念 | 大白话 | 类比（图书馆） |
|---|---|---|
| **RAG**（retrieval-augmented generation，检索增强生成） | 先去外部知识库**检索**出相关片段，再把片段喂给模型**生成**答案 | 先抽出那几页，再让专家照着这几页回答 |
| **分块**（chunking） | 把长文档切成一小段一小段，方便单独检索 | 把整本书拆成一张张可单独抽取的卡片 |
| **向量 / embedding**（嵌入） | 把一段文字转成一串数字（向量），意思相近的文字，数字也相近 | 给每张卡片贴一个"语义坐标"，主题相近的卡片坐标也相近 |
| **相似度检索**（similarity search） | 把"问题"也转成向量，去库里找坐标**最接近**的几块 | 拿问题的坐标，在书架上找离它最近的几张卡片 |
| **重排**（rerank） | 对初步检索回来的一堆候选，再用更精细的模型重新排个序，挑出真正最相关的 | 抽出十张差不多的卡片后，让资深馆员再细看一遍，挑出最对题的三张 |

术语再补两句：

- **embedding（嵌入向量）**：你不用懂它数学上怎么算的。只要记住一件事——它把"语义"变成了"距离"。"退款多久到账"和"返款几天能收到"字面不同，但 embedding 后两者**坐标很近**；和"如何注册账号"则坐标很远。**这就是为什么检索能"按意思找"而不只是"按关键词找"**。
- **top-k（前 k 个）**：相似度检索不是只捞一块，而是捞**最接近的前 k 块**（比如 top-5）。k 是你能调的旋钮——这是第 3 节的手艺。

把五个零件串成一条流水线：**文档先分块、每块算 embedding 存进库 → 用户提问时把问题也算成 embedding → 相似度检索捞回 top-k 块 → （可选）重排挑出真正最相关的几块 → 只把这几块连同问题塞进上下文 → 模型作答。**

## 2. 原理"为什么"：知识放窗外，与"垃圾进垃圾出"

### 为什么不直接全塞进去？

回到 CE0 钉死的核心矛盾——桌子太空 vs 桌子太满。几千页文档全塞进窗口，是"太满"的极端：溢出、变慢变贵、中间遗忘三宗罪一次集齐。RAG 的整个设计动机，就是**用一座外部书架，把"海量知识"挡在窗口外面**，让真正进桌的永远只是一小撮相关片段。

这呼应了 CE0 那句反直觉的话：**"少而精"常胜"多而杂"**。给模型五段精准相关的资料，几乎总比把整本手册砸给它效果更好。RAG 就是把这条原则做成了系统。

### 比"装得下"更要命的一句话：垃圾进，垃圾出

新手以为 RAG 的难点是"怎么把知识库建起来"。真正的难点是：**检索回来的那几页，到底对不对题。**

> **检索质量决定回答上限（garbage in, garbage out，垃圾进垃圾出）。** 模型再聪明，也只能基于你**捞给它**的片段作答。如果检索捞错了页——把"退货政策"当成"退款政策"递上去——模型会**一本正经地照着错页回答**，而且语气笃定，比直接说"不知道"更危险。

这是 RAG 最反直觉、也最该刻进骨子里的一点：

- 桌子太空（没捞到相关页）→ 模型瞎猜、幻觉。这是 CE0 的**失败模式 A**。
- 桌子捞错了页（捞回不相关的）→ 模型照着错页自信地答错。这是 RAG 特有的、比 A 更隐蔽的坑。

所以一个 RAG 系统答得好不好，**七分功夫在检索，三分功夫在生成**。你优化半天 prompt，不如先去看一眼：检索到底捞回来了什么？这也是为什么"重排"这个零件值钱——它就是在检索之后、喂给模型之前，再做一道"挑对页"的质检。

## 3. 工程手艺：四个要亲手拧的旋钮

原理懂了，落地全在四个取舍上。代码只作示意，重点是每个旋钮往哪拧、为什么。

### 旋钮一：分块粒度——切太大噪声多，切太小没上下文

分块是 RAG 的地基，也是最容易做砸的一步。它是一道经典取舍：

- **切太大**（比如整章一块）：一块里混进太多无关内容，检索时"沾边就算命中"，捞回来一大坨噪声——又回到了"桌子太满"。
- **切太小**（比如一句一块）：每块太碎，**丢了上下文**。捞回"7 个工作日到账"，却不知道这句说的是退款还是退货，模型照样答不准。

> 手艺：**按语义自然边界切**（一个小节、一个 Q&A 对、一段完整说明），让每一块"自己能说清一件事"。常配一点**重叠**（chunk overlap，相邻块共享一两句，避免把一句话从中间劈断）。

```python
# 示意：不是按字数硬切，而是顺着结构切
chunks = split_by_headings(doc)          # 按小标题这样的语义边界切
chunks = add_overlap(chunks, sentences=1) # 相邻块各借一句，别切断上下文
```

### 旋钮二：embedding 选型——决定"按意思找"找得准不准

embedding 模型决定了"语义坐标"画得准不准。选型上记住几条经验就够：

- **领域匹配优先**：通用 embedding 对法律、医疗等专业术语可能"坐标画歪"，垂直领域考虑领域专用模型。
- **维度不是越高越好**：更高维更精细，但更慢更占存储——又是一道成本取舍。
- **查询和文档要用同一个模型**：否则两边坐标系不一致，相似度算出来是错的（像用两套不同的地图找同一个点）。

### 旋钮三：top-k——捞几块？少了漏，多了又把桌子塞满

top-k 直接回到 CE0 的钢丝：

- **k 太小**：可能把唯一对题的那块漏在第 k+1 名，桌子太空。
- **k 太大**：捞回一堆沾边的噪声块，桌子又太满，还触发中间遗忘。

> 手艺：**先用较大的 k 粗捞，再用重排（rerank）精挑出真正相关的前几块**喂模型。粗捞保证"对的那块在网里"，重排保证"最后摊上桌的都是精华"。这就是"召回"与"精度"的经典分工。

### 旋钮四：何时**不该**用 RAG（最被低估的手艺）

RAG 是个有成本的系统（要建库、要维护、检索会出错）。很多场景**根本不该上 RAG**，强行用反而更糟：

| 场景 | 别用 RAG，该用什么 | 为什么 |
|---|---|---|
| 知识很小（几页、一份规则） | **直接整段放进上下文**（CE2 的功夫够用了） | 几页全塞进桌子毫无压力，还省掉一整套检索误差 |
| 强结构化数据（库存数量、订单状态、价格） | **用工具去查**（调数据库 / API） | 相似度检索是"模糊找意思"，查精确数字会找错；结构化数据用 SQL 一查一个准 |
| 需要全局汇总（"这一百份报告整体趋势如何"） | RAG 只擅长"捞局部相关片段"，全局题它天然抓不全 | 检索本质是"找几块最像的"，回答不了"全部加起来怎样" |
| 信息变化极快、要求绝对准确 | 工具实时查 | 知识库有同步延迟，捞回的可能是旧版本 |

> 一句话判据：**小知识直接放上桌，精确结构数据用工具查，只有"大体量、半结构化、靠语义找"的知识，才轮到 RAG。** 这正好和刀四（外部记忆，CE5）划清界限——RAG 捞的是**静态、共享、海量**的知识库，刀四存的是 **agent 自己跑出来的、动态的**状态。

## 4. 结构图：从问题到答案的一条检索流水

```
              ┌─────────── 离线准备（建书架，一次性）───────────┐
              │  几千页文档 → 分块 → 每块算 embedding → 存进向量库  │
              └────────────────────────────┬───────────────────────┘
                                            │ （知识始终在窗口外）
═══════════════════════════════════════════╪═════════════════════════════
   在线问答（每次提问跑一遍）                ▼
                                   ┌──────────────────┐
   用户问题 ──算 embedding──▶       │   向量库（书架）   │
   "退款几天到账?"                  │  全部知识睡在这里   │
        │                          └─────────┬─────────┘
        │        ① 相似度检索：找坐标最近的     │
        └──────────────── top-k 块 ◀──────────┘
                          │
                          ▼
                  ② 重排（可选）：精挑真正对题的 2-3 块
                          │
                          ▼
        ┌──────────────── 上下文窗口（办公桌·始终干净）──────┐
        │  ③ 只注入这几块相关片段  +  用户问题             │
        │     桌上没有那几千页，只有"正好需要的这几页"      │
        └──────────────────────────┬───────────────────────┘
                                    ▼
                            ④ 模型基于片段作答
                       （答案质量 ≤ 检索质量：垃圾进垃圾出）
```

读图要点：横线上方是**离线建库**（一次性的脏活累活），下方是**每次提问的实时流水**。整张图的灵魂在那行小字——**桌上从头到尾没有那几千页**，只有检索捞回的几片。而决定成败的瓶颈不在最后那步"作答"，在前面那步"检索捞对了没"。

## 5. Claude Code 锚点：你天天在用的"按需检索"

Claude Code 自己其实**很少用经典向量 RAG**——它更偏爱刀四（按需 `Read` 文件，CE5 细讲）。但"用到才捞、不全搬上桌"的检索心智，它无处不在；而当你给它接外部知识时，就是标准 RAG 了。把现象翻译成动作：

| 你看到 / 做的 | 背后的检索动作 | 对应 |
|---|---|---|
| 它不读整个代码库，而是先 `Grep`/搜索关键词，再只 `Read` 命中的那几个文件 | **先检索、只捞相关片段上桌**——RAG 的同一套心智 | 刀三检索的思路 |
| 你给它接一个文档库 MCP / 知识库工具做文档问答 | 标准 RAG：检索相关片段再作答 | 刀三 RAG 本体 |
| 它查精确数据时调工具（如查数据库、跑命令）而不是"语义检索" | **强结构数据用工具查更准**——不该用 RAG 的场景 | 第 3 节旋钮四 |
| 你把一份只有几页的规范直接粘进对话，而不是建库 | **小知识直接上桌**——不该用 RAG 的场景 | 第 3 节旋钮四 |
| 它答得头头是道却引错了文件/段落 | 检索捞错了片段，**垃圾进垃圾出** | 第 2 节核心坑 |

观察练习：下次看它做文档问答或在大代码库里找东西，盯住一个动作——它**先搜后读**，而不是先把全部读进来。那一步"搜"，就是检索；它只 `Read` 命中的几个文件，就是"只把相关片段摊上桌"。看懂这一层，你就理解了为什么给它接知识库时，**检索配置（分块、top-k）比 prompt 更值得你调**。

## 一句话带走

> **刀三检索注入（RAG）的全部直觉：把海量知识放在窗口外的"书架"上，每次只按需捞出最相关的那几页摊上桌——桌子始终干净，桌上永远只有"这个问题正好需要的几页"。它靠分块、embedding、相似度检索、重排这条流水把"语义"变成"距离"来按意思找页。但记住那句最该刻进骨子的话——检索质量决定回答上限，垃圾进垃圾出，七分功夫在检索。同时也要懂得何时别用它：小知识直接上桌，精确结构数据用工具查。**

下一章 **CE5 外部记忆与跨会话**：RAG 捞的是**静态、共享、海量**的知识库——它一直睡在那座外部书架上等你来查。但 agent 自己跑任务时**当场产出**的状态、决定、记忆——这一轮算到哪了、上次帮你定了什么偏好——这些**动态生长**出来的东西怎么存、怎么在下次捞回来？这就是刀四要解决的另一种"窗口外存储"。
