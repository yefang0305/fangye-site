# LE8 · 今天就动手：搭你的第一个 Loop

> 本层目标：从一行命令起步，一步步搭建出你生命中第一个真正在后台运行、具备发现、状态记忆、独立评判以及人回复核卡点的“自跑循环系统”。

---

## 0. 先讲一个画面

很多程序员一听到“自跑循环（Loop）”，脑子里立刻浮现出 Stripe 这种大型独角兽公司里那种每分钟处理数千个 PR、自动发布构建的超级工业流水线。然后他们就会觉得：“这玩意儿离我太远了，我只是个独立开发者，没必要弄这个。”

这是一个极大的误区。Stripe 的那套东西是终点，而不是起点。

你手里的第一个 Loop，应该小到几乎不像一个系统，甚至不需要云端服务器。它可以只是一个**定时帮你盯一眼代码库、分析一下最近构建失败原因的“分诊小助手”**。

只要它能做到“定时触发 + 自动发现”，它就越过了 Loop 的门槛。让我们在本地终端里，从最简单的一行命令开始。

---

## 1. 第一步：跑一个 `/loop`

在 `Claude Code` (v2.1.72+) 之后，命令行内置了一个非常好用的原生指令：`/loop`。它的核心作用很简单：**按指定的时间间隔，把同一件事重复跑一遍。**

它有三种基本形态，你可以根据需求挑选：

1. **固定时间间隔**：`/loop 5m check the deploy` 
   代表每隔 5 分钟在后台执行一次部署检查。
2. **AI 自适应间隔**：`/loop check the deploy`
   不指定时间，由 Claude 评估任务的紧急程度，自己在 1 分钟到 1 小时之间动态决定什么时候醒来跑下一次。
3. **裸跑**：直接输入 `/loop`
   执行内置的常规仓库维护任务，或者读取你写在项目本地 `.claude/loop.md` 里的自定义循环指令。

> 💡 **避坑指南**
> * **会过期**：这些在本地终端启动的 `/loop` 任务是“会话作用域（Session-scoped）”的。每个 recurring（循环）任务默认在 **7 天后过期**（注意：不是有些早期教程里写的 3 天）。
> * **本地限制**：它完全跑在你本机终端的进程里。一旦你把笔记本盖子合上、机器关机，循环就会停止。如果需要关机也跑，后面我们会提到云端的解决方案。

---

## 2. 第二步：从分诊开始（Triage）

如果只是让 AI 每隔 5 分钟去 ping 一下服务器，那它跟一个 cron 脚本没区别。要让它变成 Loop，它得**去读数据、做判断**。

一个非常实用的起点是搭建一个 **Triage（分诊）** 任务。你可以给它写一段类似这样的 Prompt：

> “每天早上 9 点，去查看这三样东西：昨天 CI 构建跑挂的测试、目前还开着的 Issue 列表、最近 24 小时的 commits 改动。看完后，挑出最值得修复的 bug，并在控制台列个清单。”

这一下，你就有了 Loop 的两个核心零件：
* 一个定时触发的发现机制（Automation）
* 一个用来筛选和分拣的脑子（Triage Skill）

这就是 Addy Osmani 所说的：**是 Automation 让循环成为了真正的循环，而不仅是你手动按了好多遍的单次任务。**

---

## 3. 第三步：落笔为记（状态文件与记忆）

AI 在执行分诊和修复时，如果把所有的信息和进度都只留在当前的对话窗口里，一旦终端退出，记忆就全丢了。

所以，你得给它加个**记忆实体——一个落盘的状态文件**。

让 AI 每次跑完之后，在你的项目根目录下写一个 `loop_status.md`（或者直接利用看板工具如 Linear 的 API）：
* 昨天发现了哪些 bug？
* 哪些已经尝试修复过但测试没过？
* 哪些处理到一半，需要今天继续？

**“模型会忘，但代码仓库和磁盘不会忘。”** 有了这个跨越运行期的状态文件，第二天循环被定时唤醒时，第一件事就是去读 `loop_status.md`，把记忆接上，继续往下干。

---

## 4. 第四步：安上刹车（使用 `/goal` 与评判器）

一个无人看守的循环，犯起错来也同样无人看守。如果一个写 bug 的 Agent，在没有硬卡点的情况下自己闷头改代码，它甚至会不停自我点头，宣称“我已经修复了问题”。

我们必须在 Loop 里塞进一个**会说“不”的评判器（Evaluator）**。

在 `Claude Code` (v2.1.139+) 之后，内置了 `/goal` 命令。它的核心逻辑是：**不断运行，直到设定的条件完全满足为止。**

例如：
```bash
/goal all tests in test/auth pass and the lint step is clean
```

这个命令最精妙的设计在于它的 **Maker/Checker（生成者与评判者）阻断** 机制：
在每一轮循环尝试修复后，判断“测试是否通过、Lint 是否干净”的，是一个**全新的、干净的独立大模型实例（Checker）**。它不带有干活 Agent（Maker）的任何主观记忆和妥协情绪。只有 Checker 亮绿灯，这个 `/goal` 才会判定结束。

---

## 5. 第五步：分头干活（Git Worktree 隔离）

如果你的 Triage 分诊出了 3 个不相干的 bug，你想让 3 个子 Agent 并行去修，该怎么办？

如果它们都在同一个工作目录下干活，互相修改文件会产生灾难性的 Git 冲突。**“两个 AI 同时改同一个文件，跟两个暴躁的程序员在同一行代码上提交合并请求一样头疼。”**

解决方法就是使用 Git 的 `worktree` 机制。

在 `Claude Code` 运行命令时加上 `--worktree`（或 `-w`）参数。这样，它就会为每一个后台 Agent 创建一个隔离的临时目录进行修改和测试。干完活后，再通过 Triage 收件箱将 PR 汇总。

---

## 6. 工具链速查：两强相遇

在 2026 年 6 月的今天，市面上两个最顶尖的自跑 Agent 平台是 `Claude Code` 和 `Codex`。别把它们的命令名记混了：

| 能力 | Claude Code | Codex |
| :--- | :--- | :--- |
| **定时调度** | `/loop` (本地后台定时任务) | `Automations` 标签页 (支持自定义 cron) |
| **条件达成阻断** | `/goal` (直到条件达成) | 靠 Automation 轮询脚本执行判断 |
| **并行隔离** | `--worktree` 或 `-w` | 专用后台 worktree，产出送入 Triage 收件箱 |
| **子代理调用** | Subagents / Agent Teams (在 `.claude/agents/` 下) | 通过 `.codex/agents/` 的 TOML 定义配置 |
| **外部生态连接** | MCP + Plugins (一键安装) | MCP Connector |
| **显式调用技能** | Skills (在项目 `SKILL.md` 中声明) | `$skill-name` 模块 |
| **关机可用性** | Cloud Routines (云端托管) | 云端规划中的 Codex Jobs |

*注：MCP（Model Context Protocol）连接器两边完全兼容，你在其中一方写好的自定义 Slack/Linear 连接工具，可以直接无缝迁移到另一方。*

## 7. 课前检查：你的 Loop 会不会闯祸？

在你按下第一个 Loop 的启动键之前，请对着这 6 个问题问一下自己。**如果漏掉后 4 条，你的循环就有失控闯祸的风险**：

1. **发现源**：它定时去读什么？（CI 构建失败 / Issue 列表 / Commit / 外部邮箱？）
2. **状态文件**：它跨轮的记忆存放在哪个磁盘文件上？
3. **独立评判器**：有没有一个带着全新 Prompt、会无情说“不”的 Checker 检查测试结果？
4. **并行隔离**：如果开多个 Agent，是不是各自拥有一个独立的 Git Worktree？
5. **Token 预算天花板**：设没设置这次循环的最大重试次数或 Token 花费上限？
6. **人工复核点**：在什么地方必须停下来，等你人肉看一眼，而不是一路自动合并到生产环境？

记住，**前两条决定了你的 Loop 能不能跑起来，而后四条则决定了它跑起来后，你明天睡醒时会不会收到一张天价账单和一堆被污染的代码库。**

## 8. 小练习 / 思考题

1. 如果在本地运行 `/loop 10m run tests`，在执行第 3 轮时你强行关闭了电脑。第二天重新打开终端时，这个循环会发生什么？为什么？
2. 为什么在设计 `/goal` 的 Checker（评判器）时，我们强调一定要使用一个“Fresh（干净）”的模型实例，而不能继续用 Maker 的上下文？
3. 尝试为你手头最头疼的一个日常重复性动作（如检查项目依赖漏洞、格式化代码、整理 release note）设计一个包含“人工复核点”的最简 Loop 流程。

---

## 一句话带走

> **搭建你的第一个 Loop 不需要高大上的架构，只要实现“定时触发 + 状态存盘”就是合格的起点。使用 Claude Code 的 `/loop` 和 `/goal` 进行起步，务必装好“独立评判器”、“Worktree 隔离”和“Token 预算天花板”这三把刹车，才能放心地让它在你睡觉时运转。**
