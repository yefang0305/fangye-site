# LE7 · 自跑循环：把旋钮与零件组装成无人值守系统

> 本章目标：把前六章拧好的内外循环旋钮（LE1–LE6）+ Harness 课的零件（工具 / 记忆 / 子代理），**组装成一台定时自跑、自己找活、自己验收的无人值守机器**——你只设计一次，之后它自己转。
> 本章定位：**这不是第七个旋钮。** 前六章造好并调好了发动机；本章不再拧旋钮，而是把发动机 + 一堆现成零件**装成一台会自己启动、自己派活、自己喂自己的整车**。本章改编自 Addy Osmani《Loop Engineering》一文，把它的判断纳入本课"发动机 / 旋钮"话语体系。

---

## 0. 先讲一个画面

过去两年，你从一个 coding agent 身上拿到东西的方式是这样的：你写一段好提示词、塞够上下文，敲下回车，读它吐回来的东西，再敲下一句。**agent 是工具，你全程攥着它**，一个回合接一个回合。

现在画面变了。两位一线的人这样描述：

- @steipete：「你不该再 prompt agent 了，你该去**设计那个会 prompt agent 的循环**。」
- @bcherny（Anthropic Claude Code 负责人）：「我不再 prompt Claude 了。我有一堆**循环**在跑，由它们去 prompt Claude、去想下一步该干嘛。我的工作是**写循环**。」

这句话翻译成本课的话：**杠杆点从"写提示词"搬到了"设计循环"。** 你不再当那个"按一次、看一次、再按一次"的人，而是搭一个小系统——它自己找活、自己派活、自己验收、自己记下进度，然后**自己去戳 agent**，而不是你去戳。

而这台系统的零件，恰好就是你前六章一直在练的东西：内循环的形态、缰绳、纠错、嵌套（LE1–LE5），加上外循环的节拍（LE6），再配上 Harness 课的工具、记忆、子代理。本章干的事，就是把它们**拼成一台你只设计一次、之后无人值守自己跑**的机器。

> 衔接 LE6：上一章你已经知道"外循环"是天/周级、靠你手动转的改进循环。本章是把外循环那个节拍**装上定时器**——让"你定期回头看、改、再跑"这件你凭手做的事，变成系统自己每天去做。
> 分寸提醒（忠于原作者）：作者是**谨慎乐观**的。他明确说现在还很早、他自己也存疑、token 成本可能失控、slop（低质量产出）的担忧是真的。本章不吹捧自动化——口号是 **"build the loop, stay the engineer"（搭好循环，但你仍是那个工程师）**。

## 1. 核心概念：五块积木 + 第六块记忆

一个自跑循环需要**五块积木**，再加**一个用来记事的地方**。先就地认一遍术语，每块都标出它对应本课 / Harness 课的哪个旋钮或零件——你会发现没有一样是新的，全是旧零件换了装配位置。

| 积木 | 就地中英注释 + 大白话 | 类比 | 对应本课 / Harness 的旋钮 / 零件 |
|---|---|---|---|
| **定时调度**（Automations / 自动化心跳） | 按时间表自动触发，自己去做"发现 + triage（分诊：把一堆活分类、定优先级）"。**这是让"一次运行"变成"真·循环"的心跳。** | 公司的晨会闹钟：每天早上自动响，没人响它也响 | 外循环 **LE6** 的节拍——把"你定期回头看"装上定时器 |
| **Worktrees**（git worktree / 并行隔离） | 一个独立的工作目录 + 独立分支、共享同一份仓库历史，让两个 agent 同时干活不互相踩文件 | 两个工人各自一间车间，地基（仓库历史）共用，但谁也别碰谁的料 | Harness **L6 编排**（多 agent 并行的机械隔离） |
| **Skills**（技能 / 把项目知识写下来） | 把"我们这个项目的约定、构建步骤、那次踩过的坑"写成 agent 每次都会读的文件，省得它每次冷启动靠猜 | 给新来的工人一份《本店规矩手册》，而不是每天口头重讲一遍 | Harness 的**记忆 / 上下文工程**；治的是下文"intent debt 意图债" |
| **Plugins & Connectors**（插件与连接器） | 基于 **MCP（Model Context Protocol，模型上下文协议）**，把 agent 接进你已经在用的真实工具：issue tracker、数据库、Slack、staging API | 给工人配一串万能钥匙，能进仓库、能开门、能打电话——而不只是站在原地空想 | Harness **L2 工具使用** |
| **Sub-agents**（子代理 / maker-checker 分离） | 一个 agent 出主意写代码（maker / 制造方），**另一个 agent 来验**（checker / 检查方）——写代码的别给自己打分 | 厨师做菜、另一个验菜员尝味，绝不让厨师自己说"我这道满分" | **LE4 嵌套**（工头派工人）+ **LE3 反思**（独立反馈源） |
| **第六块：Memory / 状态文件** | 一个 markdown 文件、或 Linear board——**活在单次对话之外**，记住"做了什么、还差什么、明早从哪接着干" | 工地门口那块进度白板：人下班走了，板子还在 | Harness 的**外部记忆 / 上下文工程**（LE5 也靠状态摘要抗漂移） |

> 第六块的金句（直接引原作者）：**"the agent forgets, the repo doesn't"——agent 会忘，仓库不会。** 模型在两次运行之间会把上下文忘得精光，所以记忆必须**落盘**（写进文件 / 看板），而不能指望它留在 context（上下文窗口）里。这是所有"长程运行 agent"共用的同一个老把戏。

读这张表的关键：**没有一块是新旋钮。** 自跑循环的全部本事，就是把这六块旧零件**按一个固定形状拼起来**，让它们在你不看的时候自己协作。

## 2. 原理"为什么"：自跑循环到底凭什么成立

### 2.1 它是 harness 的"上面一层"

Harness（外壳）是**单个 agent 运行时所在的环境**——它提供那个 `while` 循环、那套工具、那段上下文。自跑循环不是另起炉灶，它就是**一个装了三样东西的 harness**：

- **装了定时器**（自动化心跳）——所以它会自己启动，不等你。
- **会派小弟**（子代理 + worktree）——所以它能并行干活、还能让别人验自己。
- **会自己喂自己**（状态文件 + connector）——所以它跨运行不失忆、能在真实世界里动手。

一句话：**harness 是发动机舱，自跑循环是在发动机舱上又装了启动钥匙、副驾和油箱的整车。** 它比 harness 高一层，但用的是同一台发动机（你前六章调好的内循环）。

### 2.2 maker/checker 分离，是循环里最有用的结构

这是整篇文章里作者反复强调的一点：**把"写的人"和"验的人"分开，是自跑循环里最值钱的结构。**

为什么？因为写代码的那个模型，给自己的作业打分时**太宽容**了——它会替自己找补、把"我说服了自己"当成"对的"。换一个带不同指令、甚至不同模型的 checker，专门挑刺，才能逮住第一个 agent 自我催眠过去的问题。

而它在自跑场景里**为什么尤其关键**：循环是在你不看的时候跑的。所以——

> **一个你信得过的验证者，是你敢走开的唯一理由。**

这正是 LE3（独立反馈源比自我感觉可靠）和 LE6（人在环 / 可信成败信号）在自跑场景下的直接落地。Claude Code 的 `/goal` 干的就是这件事：每跑完一轮，一个**单独的小模型**来判断"到底完了没"——把 maker/checker 分离用到了"停止条件"本身上，写代码的那个不许给自己判结业。

### 2.3 状态文件是脊柱

模型每次运行之间会忘光（无状态）。所以在一个"今天跑一段、明天接着跑"的循环里，**记忆不能待在 context 里，必须落盘**。

状态文件（markdown / Linear）就是这条**脊柱**：它记住"试过什么、什么过了、什么还开着"，让明早那一跑能从今天停下的地方接上。没有它，每个清晨循环都从零重新发现整个项目——这既烧 token，又永远在原地打转。呼应 LE5：抗漂移靠的就是周期性把"目标和进度顶回眼前"，状态文件就是这件事的持久化版本。

> 原理一句话：**自跑循环 = 一个装了定时器、会派小弟、会自己喂自己的 harness。它能在你不看时成立，靠的是三根支柱——心跳让它自启动、maker/checker 分离让它的"done"可信、状态文件让它跨运行不失忆。**

## 3. 一个完整 loop 长什么样 + 它不替你做的事

### 3.1 一台自跑循环转一圈

把六块积木拼起来，一个普通会话就变成一个小控制台。下面是作者反复在用的那个形状，逐步看：

1. **心跳触发**：每天早上，一个自动化在仓库上自动跑一次（没人去点它）。
2. **发现 / triage**：它的提示词调用一个 **triage skill**，去读昨天的 CI 失败、open issues、最近的提交。
3. **写状态文件**：把发现写进一个 markdown 文件或 Linear board。
4. **派 maker 子代理**：对每一条值得做的，开一个**隔离的 worktree**，派一个子代理去起草修复。
5. **派 checker 子代理**：第二个子代理对照**项目 skills 和现有测试**，审查这份草稿。
6. **connector 行动**：通过连接器开 PR、更新 ticket、（CI 绿了之后）在 Slack 里吱一声。
7. **难题进收件箱**：循环搞不定的，落进一个 triage 收件箱，留给**你**。
8. **状态文件续命**：状态文件记住进度，明早那一跑从这儿接着干。

看看你实际做了什么：**你只设计了一次。上面没有一步是你 prompt 的。** 这就是 @steipete 那句话落地的样子——而且因为零件是同一套零件，这个 loop 在 Claude Code 里和在 Codex 里几乎长得一模一样。

### 3.2 它不替你做的事（别漏这一节）

作者的分寸全在这里：**循环改变了工作，但没有把你从工作里删掉。** 而且有三个问题，**循环越好，它们反而越尖锐，不是越轻松。**

- **① 验证仍在你身上。** 一个无人值守跑着的循环，同时也是一个**无人值守地犯着错**的循环。你把 checker 子代理从 maker 里拆出来，正是为了让循环说的"它做完了"有点分量；但即便如此，**"done"是一个声称，不是一个证明**（直接呼应 verification-before-completion：你的活是 ship 你**确认过**能跑的代码）。
- **② comprehension debt（理解债）。** 循环 ship 你没亲手写的代码越快，"实际存在的系统"和"你脑子里以为的系统"之间的缺口就越大。一个顺滑的循环只会让这个缺口长得更快——除非你去读它造的东西。
- **③ cognitive surrender（认知投降）。** 循环自己跑得好好的时候，人特别容易**停止有自己的判断**，循环吐什么就照单全收。这是最舒服、也最危险的姿势。

> 结论（作者原话精神）：**同一个动作，带着判断去设计循环，是解药；为了逃避思考去设计循环，是加速器。同样的循环，两个人能跑出完全相反的结果——循环分不清这俩，但你能。**

## 5. Claude Code 锚点：这些零件你都摸得到

下表把六块积木对应到你在 Claude Code 里能直接用的东西，并注明 Codex 也有对应物（作者的核心观察：**两边零件是同一套，所以你设计的 loop 换工具也成立**）。

| 积木 / 概念 | Claude Code 里的对应物 | Codex 对应物 |
|---|---|---|
| **心跳 · 在会话内重跑** | **`/loop`**：按一个节拍重跑一个 prompt 或命令 | automations tab |
| **心跳 · 跑到条件成立** | **`/goal`**：一直跑到你写的可验证条件**真的成立**，且**每轮由另一个模型判断完没完**（maker/checker 用在停止条件上） | `/goal`（同名，同样可暂停 / 恢复 / 清空） |
| **心跳 · 生命周期挂钩** | **hooks**：在 agent 生命周期的某些点触发 shell 命令 | （hooks 类机制） |
| **心跳 · 定时任务** | **cron 计划任务**：按时间表自动跑 | automations tab |
| **心跳 · 关机后还跑** | **GitHub Actions**：推上去，合上笔记本它也继续 | （CI / 后台运行） |
| **Worktrees · 并行隔离** | **`--worktree` 标志**（开一个独立 checkout 的会话）+ 子代理上的 **`isolation: worktree`** 设置（每个小弟一份自清理的新 checkout） | 内建 worktree 支持 |
| **Sub-agents · maker/checker** | **`.claude/agents/`** 下定义子代理；常见三分：一个探索、一个实现、一个对照 spec 验证 | **`.codex/agents/`**（TOML 定义，可指定模型与 reasoning effort） |
| **Connectors · 接真实工具** | **MCP connectors**：接 issue tracker / DB / Slack / staging API | MCP（同协议，连接器常可互通） |
| **Skills · 写下项目知识** | **`CLAUDE.md` / skills**（`SKILL.md` 格式）：把约定、构建步骤、踩过的坑写一次，每次读 | skills（同格式，`$` 或 `/skills` 调用） |

> 一句话：**这些不是要你新学的概念，而是前六章旋钮 + Harness 零件在 Claude Code 里的具体把手。** 你已经会用 `/goal`、会写 `CLAUDE.md`、会派子代理——自跑循环只是把它们用一根 cron 串起来。

## 小练习 / 思考题

1. 为什么说"自跑循环是 harness 的**上面一层**"？它在 harness 上多装了哪三样东西，各解决什么？
2. maker/checker 分离在普通会话里就有用，但在**自跑**场景里为什么尤其关键？用一句话说清"你敢走开的唯一理由"是什么。
3. "the agent forgets, the repo doesn't" 这句话主张把记忆放哪、不放哪？为什么在"今天跑一段、明天续跑"的循环里这件事是生死攸关的？
4. 作者说"循环越好，三个问题反而越尖锐"。这三个问题分别是什么？为什么"done"只是声称不是证明？
5. 作者强调"同一个循环，两个人跑出相反结果"。结合"带判断地设计是解药、为逃避思考地设计是加速器"，说说你打算怎么给自己设一条底线，避免滑向 cognitive surrender。

<details>
<summary>参考答案</summary>

1. 因为 harness 是**单个 agent 运行所在的环境**（提供 `while` 循环、工具、上下文），而自跑循环不另起炉灶，只是在这个环境上又装了：**定时器**（心跳——让它自启动，不等你）、**派小弟的能力**（子代理 + worktree——并行干活、还能让别人验自己）、**自己喂自己的能力**（状态文件 + connector——跨运行不失忆、能在真实世界动手）。所以它比 harness 高一层，但用的是同一台发动机。
2. 因为自跑循环是在你**不看**的时候跑的，所以一个你信得过的验证者，是你**敢走开的唯一理由**。写代码的模型给自己打分太宽容，必须有一个带不同指令 / 不同模型的 checker 来挑刺，循环说的"done"才有分量。
3. 主张把记忆**落盘**（写进 markdown / Linear），**不要**留在 context（上下文窗口）里。因为模型在两次运行之间会把上下文忘光；若不落盘，每个清晨循环都从零重新发现整个项目，既烧 token 又原地打转，明早那一跑也无法从今天停下的地方接上。
4. 三个问题：① **验证仍在你身上**（无人值守的循环=无人值守地犯错）；② **comprehension debt 理解债**（循环 ship 你没写的代码越快，你对系统的理解缺口越大）；③ **cognitive surrender 认知投降**（循环跑得好时人容易停止判断、照单全收）。"done"只是声称：因为它是 agent（哪怕是 checker）对自己工作的**断言**，不是你**确认过能跑**的证据——呼应 verification-before-completion。
5. （开放题）参考方向：给自己定"循环可以起草、但合并前我必须读 diff 并能讲清它改了什么"这类硬规则；把 checker 子代理设成不同模型；让难题强制进收件箱而不是自动合并；定期抽查循环跑过的 PR 反向考自己。核心是把"带判断"变成制度，而不是靠自觉。

</details>

## 一句话带走

> **自跑循环不是第七个旋钮，而是把前六章的旋钮 + Harness 的零件（工具 / 记忆 / 子代理）装成一台无人值守的整车：五块积木（定时调度、worktrees、skills、connectors、子代理）+ 第六块记忆（状态文件——"agent 会忘，仓库不会"）。它是 harness 的上面一层（装了心跳、会派小弟、会自己喂自己），靠 maker/checker 分离让"done"可信，靠状态文件跨运行不失忆。你只设计一次，它自己找活、自己验收、自己续跑——但验证、理解、判断仍在你身上。Build the loop, stay the engineer：搭好循环，但你仍要当那个工程师，不只是按"开始"的人。**

到这里，从内循环五个旋钮（LE1–LE5）、外循环（LE6），到把它们组装成自跑系统（LE7），你已经走完全程。最后去看 **总图**：把内外两个循环、六个旋钮拼成一张能随身带走的全景地图 + 一页"旋钮↔失败模式↔怎么调"对照卡——本章这台自跑机器，就是那张图被装上定时器、放手让它转起来的样子。
