# CE3 · 压缩与总结：把一摞旧稿，叠成一张便笺

> 本章目标：磨亮 L4 介绍的**刀二「压缩 / 总结」**——当桌上的旧稿越堆越厚，怎么把它"叠"成一张占地极小、却仍抓得住要点的便笺。重点不在"压不压"，而在**何时压、压哪一段、丢什么、留什么**——这是一门有损的手艺。
> 拧的旋钮：把"长历史"折叠成"短摘要"替换原文，给窗口腾地方，同时尽量不丢命脉。

---

## 0. 先讲一个画面

你和这个 agent 已经聊了 40 轮。桌上摊着整整一摞稿纸——5 万 token 的对话往返：每一次提问、每一次工具返回、每一次返工。它当然都"看得见"，可这张桌子已经堆到放不下新东西，而且越堆，它越容易把当前最要紧的那张压在纸山底下（这正是 CE0 反复点名的**中间遗忘**）。

这时它做了一件事，你在 Claude Code 里见过那行字：

```
Compacting conversation…
```

几秒钟后，那一摞 5 万 token 的旧稿不见了，桌上只剩薄薄一张便笺，约 2 千 token：

> **做了 X**：搭好了登录模块、跑通了三个测试。
> **定了 Y**：数据库用 Postgres，接口风格 REST，错误码统一走 4xx/5xx。
> **还差 Z**：支付回调还没接、`config.py` 第 12 行那个 TODO 没清。

40 轮浓缩成一段话。原始稿纸里那些"第 17 轮它纠结了五分钟的措辞""第 23 轮那段被推翻的方案"——**全没了**。这不是 bug，这是设计：把"大意"留下来，把"过程细节"扔掉。

这就是刀二。它和上一章 CE2「裁剪」是亲兄弟，但分工不同——这一节第 1 节就先把这对兄弟分清楚。

---

## 1. 核心概念：四个词，分清"叠稿子"这门手艺

L4 用一句话带过了压缩。这一章我们把这把刀拆成四个零件：

| 术语（中 / 英） | 大白话类比 | 它到底在干什么 |
|---|---|---|
| **压缩 / 紧实**（compaction） | 把一摞旧稿**叠**成一张便笺，旧稿撤下桌 | 用一段短摘要**替换掉**原始长历史，腾出窗口空间。强调"结果占地变小" |
| **总结**（summarization） | 写那张便笺的**动作**本身 | 调用模型（或用规则）把长内容读一遍、提炼成短文。compaction 靠它来实现，是手段 |
| **分层 / 滚动摘要**（hierarchical / rolling summary） | 便笺写满了，把"旧便笺 + 新对话"再叠成一张更新的便笺，循环往复 | 对越来越长的历史**反复地、增量地**再摘要——不是一次性压完，而是每隔一段就把"上次的摘要 + 这段新的"合并重压 |
| **保真取舍 / 有损**（lossy） | 叠稿子必然丢字，丢哪些是手艺 | 压缩**注定丢信息**（这叫 lossy，有损，借自图片压缩——JPEG 越压越糊但更小）。所以"丢什么、留什么"才是这门手艺的全部难点 |

把四个词串成一句话：**用「总结」这个动作，做出「压缩」这个效果；当历史长到一次压不完，就用「滚动摘要」反复压；而无论怎么压，它永远是「有损」的——所以取舍是核心。**

> **和 CE2 裁剪划清界限**（这是最容易混的一对）：
> - **裁剪（刀一）**：面对一坨**新进来**的东西（比如工具刚吐的 500 行日志），进桌前先扔掉无关的，只留报错那 3 行。它处理的是"**要不要让你上桌**"。
> - **压缩（刀二）**：面对**已经在桌上**的一长段历史，把它**整体改写**成更短的摘要。它处理的是"**桌上这摞旧的，怎么叠小**"。
> 一句话：裁剪是**进门时的安检**（按行扔），压缩是**桌满后的归档**（整段改写)。

## 2. 原理"为什么"：压缩是一笔"有损交易"，划不划算全看取舍

L4 给过结论："压缩会丢细节，所以时机和保留什么是手艺。"这一节我们把这句话拆开，讲清它**为什么**是手艺。

### 它的本质：拿"细节"换"空间"

压缩不是免费的。它做的是一笔**交易**：

> 你交出去的是**细节与原始措辞**，换回来的是**窗口空间 + 更低的 token 成本 + 更少的中间遗忘**。

这笔交易划不划算，取决于两个判断——这也是整把刀的两个旋钮：

**旋钮一：何时压（时机）。** 压早了，浪费——本可以原样看着的细节，被你提前抹糊了；压晚了，桌子早已溢出或陷入中间遗忘，等于没压。常见的触发时机有三种：

- **按水位**：历史占到窗口的某个比例（比如 70%）就触发——最常见，Claude Code 的 `Compacting…` 多属此类。
- **按节奏**：每 N 轮固定压一次，节奏稳定可预测。
- **按事件**：一个子任务刚收尾、一个里程碑刚达成时压——此刻"哪些是结论、哪些是过程"最清楚，压出来的摘要质量最高。

**旋钮二：压哪一段（对象）。** 回想 CE0 那张办公桌分区图：最该压的，永远是**中段的历史消息区**——它既是中间遗忘的高发区，又堆得最满。而**最近几轮**（结尾高权重区）通常**不压或少压**，因为那是当前任务的命脉，糊了就直接断线。所以压缩不是"从头压到尾",而是"**压陈年旧账，留眼前要务**"。

### 丢什么、留什么：这才是真正的手艺

既然有损不可避免，那"丢得聪明"就是全部本事。一条优先级铁律：

> **优先保留三类"硬通货"：① 关键决策（定了什么）、② 约束 / 前提（不能碰什么、规矩是什么）、③ 未完成项（还差什么、下一步干嘛）。优先丢弃：探索过程、被推翻的弯路、寒暄与重复确认。**

为什么是这三类？因为它们是**面向未来**的——决定了 agent 接下来该怎么走。而"过程"是面向过去的：第 17 轮怎么纠结的，对第 41 轮毫无用处。**摘要要的是"现在的存档点"，不是"完整的回放录像"。**

### 最阴险的坑：摘要套摘要，信息悄悄漂移

滚动摘要很强，但它藏着一个隐形杀手——**信息漂移**（每压一次都丢一点，压多了原意就走样了）。

打个比方，这就像**复印件的复印件**：第一张还清楚，复印第五张时字已经发虚，到第十张可能把"用 Postgres"糊成了"用某个数据库"，甚至悄悄变成"用 MySQL"。每一次"摘要套摘要"，都在已经有损的基础上再损一次，误差**累积放大**。

> 它比溢出更危险，因为**它不报错**。溢出会"啪"地报错提醒你，漂移却是无声的——agent 某天突然基于一条被压糊了的约束做出错误决策，你回头翻历史，发现原文早在三次压缩前就没了。

应对的手艺：
- **关键事实"钉死"不参与滚动**：把硬通货（决策、约束）单独拎出来，逐字保留、每轮原样带上，**不让它进"反复重压"的绞肉机**——这其实是把它升级成了 CE5 的"外部记忆"。
- **用结构化模板，而非自由发挥**：固定字段（做了 / 定了 / 还差 / 约束）逼着每次摘要都对齐到同一骨架，比让模型每次自由写一段散文更抗漂移——字段在，信息就不容易整段蒸发。

一个**结构化摘要模板**示意（只作示意，不是要你背的代码）：

```text
## 进度存档（截至第 40 轮）
- 已完成：登录模块、3 个测试通过
- 已定决策：DB=Postgres；接口=REST；错误码=4xx/5xx
- 硬约束（逐字保留，勿改写）：禁止改动 auth/ 目录；上线前不接真实支付
- 未完成 / 下一步：接支付回调；清掉 config.py:12 的 TODO
- （过程细节已丢弃，如需回看见原始日志）
```

> 原理一句话：**压缩是拿细节换空间的有损交易，划算与否全看两个判断——何时压、压哪段；而丢得聪明的诀窍是「留住面向未来的硬通货、丢掉面向过去的过程」，并警惕「摘要套摘要」让原意无声漂移。**

## 3. 结构图：长历史被"折叠"成一张摘要

把 CE0 那张办公桌的②号区（历史消息区）单独拉出来看，压缩做的就是这个"折叠"动作：

```
压缩前：桌上摊着一长摞旧稿（中段 · 占地巨大 · 易中间遗忘）
┌─────────────────────────────────────────────┐
│ 第1轮  问答 + 工具往返   ▓▓▓▓▓               │
│ 第2轮  问答 + 工具往返   ▓▓▓▓                │   ← 这一整段
│ ……（中间 36 轮，5 万 token）  ▓▓▓▓▓▓▓▓▓     │      都是"陈年旧账"
│ 第39轮 问答 + 工具往返   ▓▓▓                 │
│ 第40轮 问答 + 工具往返   ▓▓▓▓                │
└─────────────────────────────────────────────┘
                    │
                    │   总结（动作）：读一遍，提炼硬通货，丢过程
                    ▼
压缩后：旧稿撤下桌，只留一张便笺（约 2 千 token）
┌─────────────────────────────────────────────┐
│ 【进度存档】做了X · 定了Y · 还差Z · 约束…   │  ▓   ← 占地骤减
└─────────────────────────────────────────────┘
│  最近 2~3 轮：原样保留（结尾高权重 · 当前命脉 · 不压）  ▓▓▓▓
└─────────────────────────────────────────────┘

滚动摘要（历史又长了，再折一次 —— 当心复印件越复越糊）：
   [旧便笺] + [新攒的 10 轮]  ──总结──▶  [更新的便笺]
                                          ⚠ 每折一次丢一点，硬通货要"钉死"在折叠之外
```

读图要点：折叠永远只折**中段陈账**，不折**结尾命脉**；而滚动那一步是把"上次的便笺"和"新攒的对话"再叠一次——好用，但每叠一次都离原文更远，所以硬通货得拎出来单独存。

## 4. Claude Code 锚点：你看到的那行 `Compacting…`

刀二是四把刀里你**肉眼最容易抓现行**的一把——它会明明白白打出一行字。下次见到，试着透视背后的动作：

| 你在 Claude Code 看到 / 做的 | 背后的压缩动作 | 对应本章哪一节 |
|---|---|---|
| `Compacting conversation…` | 历史到了水位线，把中段长历史**总结成短摘要替换原文**，给窗口腾地方 | 时机·按水位（§2） |
| 压缩后它仍记得"我们用 Postgres、还差支付回调" | 摘要保住了**决策 / 约束 / 未完成项**这三类硬通货 | 丢什么留什么（§2） |
| 压缩后它忘了"你早先随口提过的一个小偏好" | 那属于**被丢弃的过程细节**——有损的代价 | 有损取舍（§1、§2） |
| 长会话里它偶尔把一条旧约束理解跑偏了 | 多半是**摘要套摘要的信息漂移**——原文几次压缩前就没了 | 信息漂移（§2） |
| 你主动 `/compact`（手动触发压缩） | 你**亲手行使刀二**，在自己觉得合适的时机折叠历史 | 时机·按事件（§2） |
| 你嫌它压糊了，改用 `/clear` 重开 | 那不是压缩，是**裁剪到底**（CE2）——整张桌子清空重来，不留摘要 | 与裁剪的区别（§1） |

> 透视一层：`Compacting…` 不是"它累了喘口气"，而是一次**精打细算的有损归档**——它在替你判断"哪段旧账该折、折成什么、留住哪几条命脉"。你越懂这笔交易，就越知道什么时候该信它的摘要、什么时候该手动 `/compact` 抢在它前面、什么时候干脆 `/clear` 重来。

## 小练习 / 思考题

1. 用"叠稿子 / 便笺"的比喻，说清 **compaction（压缩）** 和 **summarization（总结）** 的关系——谁是目的、谁是手段？
2. CE2 裁剪和 CE3 压缩都能给窗口省地方，但处理的对象和动作完全不同。请各用一句话说清它们的分工（提示：安检 vs 归档）。
3. 压缩是**有损**的。请默写"优先留三类、优先丢三类"分别是什么，并解释为什么留的那三类都"面向未来"。
4. 什么是**滚动摘要的信息漂移**？为什么说它"比溢出更危险"？给出两条对抗它的手艺。
5. 你在做一个会聊很久的客服 agent。它必须永远记住用户开场报的"订单号 SN-20260615-007"。你会让这个订单号参与每一次滚动摘要吗？为什么？该怎么处理它？（提示：硬通货 + CE5 预告）

<summary>参考答案</summary>

1. **总结（summarization）是手段，压缩（compaction）是目的 / 效果**。总结是"把长内容读一遍、写成短文"这个动作；压缩是"用这段短文替换掉原始长历史、腾出窗口空间"这个结果。你靠"做一次总结"来达成"实现一次压缩"。
2. **裁剪 = 进门时的安检**：面对刚进来的一坨新东西（如 500 行日志），进桌前按行扔掉无关的，只留有用几行，管"要不要上桌"。**压缩 = 桌满后的归档**：面对已经在桌上的一长段历史，整段改写成更短的摘要，管"桌上旧的怎么叠小"。
3. 优先**留**：①关键决策（定了什么）②约束/前提（不能碰什么、规矩是什么）③未完成项（还差什么、下一步干嘛）。优先**丢**：探索过程、被推翻的弯路、寒暄与重复确认。留的三类都"面向未来"——它们决定 agent 接下来怎么走；而过程是"面向过去"的回放，对下一步没用。摘要要的是"现在的存档点"，不是"完整回放录像"。
4. **信息漂移**：滚动摘要是"对摘要再摘要"，每压一次都在有损基础上再损一次，误差累积放大，像复印件的复印件越来越糊，原意慢慢走样（"Postgres"可能被压成"某数据库"甚至"MySQL"）。它**比溢出更危险**，因为**溢出会报错、漂移不报错**——agent 某天悄悄基于一条被压糊的约束做错决策，而你回头翻历史时原文早已没了。对抗手艺：①把关键事实"钉死"在滚动之外，逐字保留、每轮原样带上，不让它进反复重压的绞肉机；②用结构化模板（固定字段）而非自由散文，逼每次摘要对齐同一骨架。
5. **绝不让它参与滚动摘要**。订单号是一个字符都不能错的硬通货，一旦进了"摘要套摘要"的绞肉机，迟早被漂移弄糊。正确做法：把它**单独拎出来逐字钉死**，每轮原样带上，不进重压流程——这其实已经越界进了**刀四外部记忆（CE5）**：与其指望摘要记住它，不如把它写进一个稳定的"事实区 / 外部文件"，桌上只留指针，要用再取，永不失真。

## 一句话带走

> **刀二压缩，是把桌上一长摞陈年旧账，用「总结」这个动作折叠成一张占地极小的便笺。它是一笔有损交易——拿细节换空间，划不划算全看两个旋钮：何时压、压哪段。丢得聪明的诀窍是「留住面向未来的硬通货（决策/约束/未完成项）、丢掉面向过去的过程」；而最大的暗坑是「摘要套摘要」让原意无声漂移，对策是把命脉钉死在滚动之外、用结构化模板抗漂移。你在 Claude Code 看到的 `Compacting…`，就是这笔交易在你眼前发生。**

下一章 **CE4 检索注入（RAG）**：压缩干的是"把**已经在桌上**的东西缩小"。可有一类更根本的难题它解决不了——**你想要的知识，从一开始就根本不在窗口里**呢？（公司几千页文档、整个产品手册，压都没得压，因为它们压根没上过桌。）这就需要刀三：把海量知识放在窗口外，用到哪段、才去捞哪段。
