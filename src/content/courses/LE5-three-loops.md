# LE5 · 让循环在你睡觉时跑：三个真实的 Loop

> 本层目标：摆脱纸面上的逻辑分析，看三个工业界真正在跑的自循环工程案例，理解大厂是如何用脚手架支撑起海量无人值守的代码提交的。

---

## 0. 先讲一个画面

所谓的“在睡觉时让 AI 替你打工”，听起来像是自媒体吹嘘的幻觉。
但现实是，这已经在很多顶尖技术团队的 CI（持续集成）和日常流水线里悄悄运转了。

我们将要剖析三个代表性案例：一个人的晨间分诊、一家公司每周合并 1300 个 PR 的“小兵（Minions）”大队，以及实现关机自转的后台调度表。

你会发现：**决定循环能否成功跑在深夜的，从来不是模型有多强，而是这套 Harness 外壳有多稳。**

---

## 1. 案例一：Addy 的早晨（一个人的 triage loop）

这是 Google Chrome 团队工程师 Addy Osmani 每天天亮自动运行的系统。
* **流程**：每天清晨自动唤醒，利用 triage skill 扫描昨天的构建错误、新开的 issue ➔ 将结论写入 `TODO.md` 状态文件 ➔ 为每个任务派发独立的 worktree 分支，一个子 Agent 编写代码，第二个子 Agent 跑测试审核 ➔ 通过了自动开 PR ➔ 搞不定的落入“人工分诊箱”，等待他上班后处理。
* **设计细节**：他没有把一大段 Prompt 贴在定时任务日程里，而是封装成了一个 `$triage-skill` 脚本。因为“把一大段提示词直接贴日程表里，以后绝对不会有人去更新它”。

---

## 2. 案例二：Stripe 的 Minions（每周 1300 个 PR）

这是 Stripe 内部最大规模的自动化写代码系统。最惊人的数字是：**每周合并 1300 多个 PR，没有一行是人手写的。**

Stripe 团队并没有采用什么神秘的黑科技模型（它是基于 Goose 框架的定制分支），它的成功完全取决于极高水准的 **Harness Engineering**：

1. **确定性准备（LLM 醒来前的工作）**：
   当用户在 Slack 里 @ 机器人，或者对一条工单点了一个 emoji 反应时，循环被触发。但在大模型睁眼思考之前，一个**确定性的 Orchestrator 代码程序**先去把所有背景资料备齐——扫链接、拉 Jira 状态、在代码库里用 Sourcegraph 搜出关联代码。
   **“能用确定性代码解决的，绝对不要交给概率模型。”**
2. **流水线硬卡关**：
   子 Agent 改完代码后，必须强制经过一段硬编码的 Pipeline 跑 linter 语法检查。AI 如果跑不过，直接强制它自己修，修不过就不许 git commit。
3. **“牛群而不是宠物”（Cattle not Pets）**：
   每个 Agent 干活的沙箱（Sandbox）都是跑在 EC2 上的一次性虚拟机，坏了不修直接销毁重建。这保证了 1000 多个 Agent 同时改代码绝不会互相踩到文件。
4. **人的角色转变**：
   人并没有被踢出工作流。1300 个 PR 最终依然要由人类工程师做 Code Review。**时间从“写代码”挪到了“审代码”**。

## 3. “睡觉跑”到底靠什么？

很多人误以为本地敲个 `/loop` 定时命令就能让它睡觉跑了。但笔记本一旦合盖或断网，程序就中断了。
真实的调度分为以下几种，我们需要根据是否依赖“本地状态”来选型：

| 调度方式 | 跑在哪里 | 需要开机吗 | 最小间隔 | 适合场景 |
|---|---|---|---|---|
| **本地 /loop** | 你的本机 | 是 | 1分钟 | 本地实时盯防（如监控服务器） |
| **Desktop 定时任务** | 你的本机 (后台) | 是 | 1分钟 | 挂在本地后台跑的维护任务 |
| **云端调度 (如 Actions)** | 远端云服务器 | 否 | 1小时 | 凌晨自动扫描仓库、自动提交 PR |

## 一句话带走

> **在其睡觉时跑的自循环并不是魔术，它的靠谱来自外壳约束的质量：Stripe 表明，把找资料和语法检查等确定性环节交给硬编码，LLM 只负责写代码，结合一次性临时沙箱（Cattle not Pets）与人工最终 Review 关卡，才能让每周上千次无监督提交安全落地。**
