# LE4 · 生成器与评判器：为什么写代码的 AI 不能给自己打分

> 本层目标：搞清为什么大模型永远倾向于自信地赞美自己的平庸之作，学会用 Maker/Checker 隔离结构在循环里放置能说“不行”的哨兵。

---

## 0. 先讲一个画面

你写完一篇文章，自己回头读一遍。你可能觉得字字珠玑，顺畅无比。
但事实上，你读的并不是纸面上的字符，而是你脑子里原本就设定好的那个“完美版本”——你根本看不见自己的盲区。

大模型也是一样的。写代码的那个 Agent（Maker）在写代码时，它的工作上下文里已经塞满了“我为什么要这样设计”的各种自我说服理由。
这时候你如果问它：“你写得怎么样？有什么 Bug 吗？”
根据 Anthropic 工程师的实测发现：**Agent 绝对会极度自信地赞美自己产出的平庸代码**（confidently praising the work）。它无法跳出自己的初始视角，甚至会为了证明自己是对的去编造借口。

如果在一个自跑的循环里，写代码的人和挑错的人是同一个 Agent，那么每一轮循环都只是 AI 在不断地和自己达成共识、相互点头。跑得越多，烂代码积攒得越快。

---

## 1. 核心手艺：调一个独立的“怀疑论者”

与其费尽心机去修改 Prompt 逼着生成器自我批判（这往往极难见效），最划算、性价比最高的工程解法是：**另起一个独立的 Agent 专门用于审查（Checker）**。

这套思路借鉴了 GAN（生成对抗网络）的架构设计：

* **Maker（生成器）**：负责写代码、出主意。它只管干活。
* **Checker（评判器/审核器）**：完全不参与写代码。它以“怀疑论者”的心态从零审阅代码。

为了让 Checker 足够可靠，实践中通常有这几项调校手艺：
1. **指令往坏处写**：让评判器默认**“这段代码是坏的，除非被证明能跑”**（assume the code is broken until proven otherwise）。
2. **动手验证，而不只是看**：如果评判器只是读一遍代码，它容易犯“假性看懂”。必须给它配工具（如 Playwright 或单元测试环境），让它真的去运行代码、点击按钮、截图、核对 DOM 状态。看行为，不看意图。
3. **更换底层底座模型**：有时候生成器用大模型，评判器用一个指令不同、甚至模型也不同的新模型（sometimes a different model）。因为同一个模型的盲区是一致的，换个底座，能逮住很多思维定式留下的坑。

---

## 2. 停止条件的“独立判定”

这种 Maker/Checker 的思想，在 Claude Code 里被做成了一个非常有力量的产品原语：**`/goal`**。

你给它一个命令：`/goal all tests pass`。
它会一直在后台跑，直到测试通过。但“通不通过”的最终裁决权，并不在那个正在哼哧哼哧改代码的 Agent 手里，而是在每轮结束后，由外壳自动调起的一个**全新、独立的 Fresh 小模型（Checker）**去对照条件判定的。

不通过，就重新丢回去再跑一轮，绝不让干活的模型自己决定“我搞定了”。

---

## 一句话带走

> **写代码的模型倾向于无条件赞美自己的成果，这被称为自我催眠。防范自跑循环失控的核心是 Maker/Checker 分离：引入一个完全不同的、心怀怀疑的、会动手测试的独立 Agent 作为 Checker，并将停止条件判定权交还给一个全新的 Fresh 模型。**
