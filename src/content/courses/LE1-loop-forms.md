# LE1 · 循环的形态选型

> 本章目标：拧第一个、也是最大的一个旋钮——**循环的骨架长什么样**。同一个任务，循环可以"边想边做"，也可以"先规划后执行"，选错形态会从根上拖累整台发动机。
> 拧的旋钮：① 循环形态（loop form）。

---

## 0. 先讲一个画面

还是那面要刷白的墙，你请了两个工人：

- **工人甲**：上来就刷一道，退后看一眼"哪儿没盖住"，再补一道，再看，再补……他**边想边做**，从不预先规划，走一步看一步。
- **工人乙**：先掏出本子，把"先补缝 → 刷底漆 → 刷两道面漆 → 收边"整个施工顺序列出来，然后**照单逐条执行**，中途基本不停下来重想。

两个人都能把墙刷白，但他们循环的**骨架**根本不同。甲是 **ReAct（边想边做）**，乙是 **Plan-then-Execute（先规划后执行）**。这一章就是教你：什么任务该派甲，什么任务该派乙。

> 关系说明：本章是全新内容，把市面上"ReAct、Plan、Reflexion 各讲各的"拼成一张可选型的图谱。它建立在 Harness L3 那个裸 `while` 之上——同一个 `while`，里面"模型每一步在干嘛"可以摆成不同形态。

---

## 1. 核心概念：三种主形态

| 形态 | 大白话 | 一圈在干嘛 | 最适合 |
|---|---|---|---|
| **ReAct**（Reason+Act，边想边做） | 每步先想一句、再动一下，看了结果再想下一步 | 想→做→观察→想→做→观察…… | 探索性、环境会变、无法预先拆解的任务 |
| **Plan-then-Execute**（先规划后执行） | 先一次性列出完整计划，再逐条执行 | 先产出一整份计划 → 顺序执行每条 | 步骤清晰、可预先拆解、要省 token 的任务 |
| **Plan-and-Reflect**（计划+回看，混合，进阶） | 先列计划，执行中允许回头改计划 | 计划 → 执行几步 → 发现不对就改计划 → 继续 | 中等复杂、计划可能中途失效的任务 |

术语注释：
- **ReAct**：Reasoning + Acting 的缩写，指"推理和行动交织"——模型每一步都先输出一小段思考（reason），再开一张工具申请单（act），是目前最常见的 agent 形态。
- **Plan-then-Execute**（也叫 Plan-and-Execute）：把"规划"和"执行"拆成两个阶段，先让模型当一次"项目经理"列出全部步骤，再让它（或子代理）当"施工队"逐条做。

---

## 2. 原理"为什么"：没有最优形态，只有任务匹配

两种主形态各有天生的代价，这正是"选型"存在的理由：

- **ReAct 灵活，但容易步步漂、费 token。** 它不预设全局，每步临场决定——遇到意外能随机应变，但也容易"走着走着忘了大方向"（埋下 LE5 漂移的种子），而且每一步都要把整叠 messages 重发一次，步数一多就慢且贵。
- **Plan 省 token、有全局观，但计划一旦错就整条偏。** 先规划意味着只在开头"重想"一次，后面照单执行很便宜、方向也稳；但如果开头的计划基于错误假设，执行得越顺、错得越彻底——它不会中途质疑自己。
- **混合形态（Plan-and-Reflect）是想两头都要：** 有全局计划兜底，又允许执行中回头改。代价是更复杂、更难调。

> 选型的判断轴只有一句话：**任务越"可预测、可预先拆解"，越偏 Plan；越"探索、环境会变、开头说不清步骤"，越偏 ReAct。** 拿不准就从 ReAct 起步（更鲁棒），发现重复试错太费再上 Plan。

## 3. 结构图：两种骨架的形状

```
ReAct（锯齿形：想-做-想-做）           Plan-then-Execute（先一坨，再顺序跑）

  想→做→👀                              ┌──── 规划阶段 ────┐
       │                                │ 1. 补缝          │
       ▼                                │ 2. 刷底漆        │
  想→做→👀                              │ 3. 刷面漆 x2     │
       │                                │ 4. 收边          │
       ▼                                └────────┬─────────┘
  想→做→👀  …直到完成                            ▼
                                         执行：1→2→3→4（基本不重想）
  灵活·能应变·费token·易漂              省token·方向稳·计划错则全错
```

## 4. Claude Code 锚点：它什么时候像甲，什么时候像乙

| 你看到 Claude Code | 对应哪种形态 |
|---|---|
| 接到模糊/探索性的活，直接开始读文件、试一下、看结果再决定下一步 | **ReAct**——边想边做 |
| 接到稍大的活，先用 TodoWrite 列出一串待办，再逐条勾掉 | **Plan-then-Execute** 的影子——先规划再执行 |
| 列了计划，但干到一半发现某步行不通，回头改了待办再继续 | **Plan-and-Reflect** 混合 |

观察练习：下次给它派活，留意它是"上来就动手"还是"先列计划"。任务越清晰，它越倾向先列计划；任务越含糊，它越倾向边试边走。你也可以主动要求它"先给我一个计划再动手"——那就是手动把旋钮拧向 Plan。

## 5. 小练习 / 思考题

1. 下面两个任务各该配哪种形态，为什么？
   (a)"把这个 100 行函数重构成 3 个小函数，保持测试通过"
   (b)"这个线上 bug 不知道哪来的，帮我查出根因"
2. ReAct 最大的两个代价是什么？
3. Plan-then-Execute 为什么"执行得越顺，可能错得越彻底"？
4. 如果一个任务你也拿不准该用哪种，本章建议从哪种起步、为什么？

<details>
<summary>参考答案</summary>

1. (a) 偏 **Plan**：步骤清晰、可预先拆解（先拆函数→再跑测试），先列计划省 token 且方向稳。(b) 偏 **ReAct**：根因未知、要边查边缩小范围，环境信息随每步揭开，必须走一步看一步。
2. ① 费 token / 慢（每步都重发整叠 messages，步数一多成本飙升）；② 易漂移（无全局计划兜底，走久了容易偏离原目标）。
3. 因为它在开头只"重想"一次，后面照单执行、不再质疑计划。若开头的计划基于错误假设，它会忠实地、顺畅地把错误执行到底，不中途纠偏。
4. 从 **ReAct** 起步。它更鲁棒、能应变，不依赖"开头就能说清全部步骤"这个前提；等发现重复试错太费，再把方向稳定的部分上 Plan。

</details>

## 一句话带走

> **第一个旋钮是"循环的骨架"：ReAct（边想边做）灵活能应变但费 token 易漂，Plan-then-Execute（先规划后执行）省钱方向稳但计划错则全错。没有最优形态，只有任务匹配——越可预测越偏 Plan，越探索越偏 ReAct，拿不准从 ReAct 起步。**
