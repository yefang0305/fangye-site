# LE4 · 嵌套循环：循环套循环

> 本章目标：拧第四个旋钮——当一个循环太长太乱，把它**拆成"循环里再开循环"**：一个工头（orchestrator）调度一队各自跑完整小循环的工人（worker）。重点是嵌套带来的**控制问题**，不是子代理本身。
> 拧的旋钮：④ 嵌套结构（nested loops）。

---

## 0. 先讲一个画面

一套三居室要装修。你可以让**一个**工人从主卧刷到客厅再到厨房——但他刷到第三间时，早累糊涂了，还得在脑子里同时装着三个房间的所有细节。

更好的办法：请一个**总包工头**。他不亲自刷墙，只做四件事——**拆活**（分成"刷主卧""刷客厅""刷厨房"）、**派活**（每间派给一个工人）、**收活**（工人干完回来汇报）、**定下一步**。每个工人自己跑一个**完整的小循环**（他自己的"想-做-看"），只把"主卧刷好了"这个结论交回来。

工头的循环里，套着工人的循环。这就是**嵌套循环**。

> 关系说明：Harness L6 讲过子代理，但角度是"为什么拆"（隔离、并行、专精）。本章角度不同——讲**嵌套循环怎么控制**：总预算怎么切给子循环、结果怎么汇聚、谁负责收尾。同一个东西，L6 看"组织"，本章看"循环的嵌套与控制"。

---

## 1. 核心概念：工头循环 + 工人循环

| 概念 | 大白话 | 关键职责 |
|---|---|---|
| **orchestrator loop**（工头/主循环） | 不亲自干活，负责拆活、派活、汇总、定下一步 | 调度与决策 |
| **worker loop**（工人/子循环） | 每个子代理自己跑一个完整 agent loop | 闷头把分到的子任务做完 |
| **预算分配**（budget split） | 把主循环的总预算切给各子循环 | 子循环也要有自己的 max_steps（见 LE2） |
| **结果汇聚**（aggregation） | 子循环只把"结论"交回主循环，不把全过程塞回来 | 控制上下文，防撑爆 |
| **串行 vs 并行嵌套** | 子循环一个接一个跑 / 同时跑 | 看子任务之间有没有依赖 |

术语注释：
- **orchestrator（编排者/工头）**：一个专门负责"分解任务、分派给子代理、汇总结果"的循环，自己一般不直接调用底层工具。
- **worker / subagent（工人/子代理）**：被工头派去做一个子任务的独立 agent，有自己完整的内循环（自己的形态、缰绳、纠错）。
- **结果汇聚（aggregation）**：子循环跑完后，只把**浓缩后的结论**返回主循环，而不是把它一路上几十步的过程原样倒回来——否则主循环的上下文会被瞬间塞爆。

---

## 2. 原理"为什么"：用嵌套换"短而干净"

为什么不一个循环干到底？因为单循环有两个随步数增长的硬伤（都在后面或前面章节出现）：

- **撑爆窗口**：循环每转一圈，messages 就变长一点（L3 的结论）。一个循环干完整套大活，几十上百步后，上下文窗口必然装不下。
- **越长越漂**：步数越多越容易跑题（LE5 的主题）。

嵌套循环正面解决这两点：把一个"长循环"拆成几个"短而干净的子循环"，**每个子循环上下文独立、预算独立、跑完即弃**。工头那层只需要保留每个子任务的"结论"，自己的上下文始终很短。

但天下没有免费的拆分，嵌套引入两笔新成本：

- **协调成本**：工头要花步数去拆、派、汇总，本身也烧 token。
- **汇报失真**：子循环把几十步压成一句"做好了"，必然丢信息。如果工头据此决策，可能因为"看不到细节"而误判——好比工人说"刷好了"，其实边角没盖住。缓解办法是让子循环的汇报**带上关键证据**（不是"做好了"，而是"做好了，测试 12 个全过，附日志摘要"——呼应 LE3 的"好信息"）。

> 原理一句话：**嵌套循环用"协调成本 + 汇报失真"换"每个子循环都短而干净"。它把单循环"越长越爆越漂"的问题，转化成"如何拆得好、如何让汇报不失真"的问题。**

## 3. 结构图：大循环里套小循环

```
┌──────────── orchestrator loop（工头·上下文始终很短）──────────┐
│  拆活 →  派活 ┬─────────────┬─────────────┐                   │
│              ▼             ▼             ▼                    │
│        ┌─worker A─┐  ┌─worker B─┐  ┌─worker C─┐  (并行或串行) │
│        │ 想-做-看 │  │ 想-做-看 │  │ 想-做-看 │  每个有自己的 │
│        │ …小循环… │  │ …小循环… │  │ …小循环… │  形态+缰绳+纠错│
│        └────┬─────┘  └────┬─────┘  └────┬─────┘               │
│             │只回结论     │只回结论     │只回结论              │
│             └─────────────┴──────┬──────┘                     │
│                          汇聚 ▼                                │
│                  工头读结论 → 定下一步 / 收尾                   │
└───────────────────────────────────────────────────────────────┘
       ↑ 派活↓ 汇报↑：工头与工人之间只传"任务"和"结论"
```

## 4. Claude Code 锚点：它派出去的"小分队"

| 你在 Claude Code 看到 | 对应嵌套循环的哪部分 |
|---|---|
| 它把一个大任务拆开，派出多个 Task/subagent 去并行处理不同部分 | **工头派活** + 多个 **worker 子循环** |
| 子代理跑完只回来一段结论摘要，而不是它读过的所有文件 | **结果汇聚**——只回结论，保护主循环上下文 |
| Superpowers 的 subagent-driven-development / dispatching-parallel-agents | 把"嵌套循环怎么拆、怎么派、怎么汇"规范成流程 |

观察练习：当你看到它"派了几个子代理"，想一想——每个子代理都是一个**独立的完整内循环**（有自己的 LE1 形态、LE2 缰绳、LE3 纠错），而你看到的主线，是工头那层在拆派汇。意识到这点，你就能理解为什么子代理的失败不一定拖垮主任务：工头收到"某个子循环失败"的结论后，可以重派或换路子。

## 5. 小练习 / 思考题

1. 嵌套循环解决了单循环的哪两个核心问题？（提示：一个关于上下文，一个关于方向）
2. 子循环为什么也要有自己的 max_steps / 预算？不设会怎样？
3. "汇报失真"是什么意思？用一个例子说明它怎么导致工头误判，以及怎么缓解。
4. 嵌套不是免费的，它引入了哪两笔新成本？

<details>
<summary>参考答案</summary>

1. ①撑爆上下文窗口（单循环干完整套大活，几十步后 messages 装不下）；②越长越漂移（步数越多越跑题）。嵌套把长循环拆成几个短而干净、上下文独立的子循环。
2. 因为子循环也是完整的 agent loop，同样会死循环/烧钱/跑太久。不设的话，一个失控的子循环就能拖垮整个任务，甚至烧光分给它的资源还停不下来。缰绳要逐层都有。
3. 子循环把几十步压成一句"做好了"，必然丢细节。例：子代理报"功能实现完了"，其实漏了边界情况；工头据此收尾，bug 流到最后。缓解：让汇报**带关键证据**（"做好了，12 个测试全过，附摘要"），而不是空口"做好了"。
4. ①协调成本（工头拆、派、汇本身也烧步数和 token）；②汇报失真（浓缩结论必然丢信息，可能让工头误判）。

</details>

## 一句话带走

> **第四个旋钮是把长循环拆成嵌套的短循环：工头循环负责拆派汇、自己上下文始终很短，工人子循环各自跑完整内循环、只回结论。它用"协调成本 + 汇报失真"换"每个子循环都短而干净"，从根上缓解单循环越长越爆越漂的毛病。**

下一章 **LE5 漂移与长程控制**：嵌套缓解了"长"，但只要循环还得连续转很多步，就躲不开一个幽灵般的敌人——它会让 agent 在不知不觉中越跑越偏题。这是本课最独特的一章。
