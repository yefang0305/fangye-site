# L6 · 一个 agent → 一支团队：子代理与编排

> 本层目标：理解当任务大到一个 agent 的"桌子"摊不下时，怎么把它拆成一支会分工的团队。
> 这一层不修补新的模型缺陷，而是**绕过 L4 的窗口上限、并放大产能**的架构升级。
> 关键词：子代理（sub-agent）、编排（orchestration）、上下文隔离。

---

## 0. 先讲一个画面

你（主管，**主代理 / orchestrator**）接了个大项目：调研三家竞品、各写一份分析、最后汇总成报告。

**单人硬扛**：你把三家竞品的所有资料全堆到自己一张桌子上（L4 上下文窗口）——桌子爆了，而且资料互相干扰，你看 A 的数据时被 B 的噪声带偏。

**带团队**：你派三个下属（**子代理 / sub-agent**），每人专责一家：给他**干净的一张新桌子**和**只属于这家的资料**，让他独立调研、产出一份分析交回来。你（主管）只收三份**精炼结论**，桌上始终清爽，最后专心做汇总。

第二种就是**子代理 + 编排**。它的精髓不在"人多力量大"，而在四个字：**上下文隔离**——每个子代理有自己独立的、干净的上下文窗口，互不污染。

---

## 1. 要解决什么：一个上下文窗口的三重天花板

到 L5 为止我们的 agent 很能干，但"单个 agent + 单个上下文窗口"撞到三堵墙：

1. **容量墙**：大任务需要的资料，一张桌子根本摊不下（L4 的硬上限）。
2. **干扰墙**：就算勉强摊下，多个子任务的信息**互相污染**，模型在 A 任务里被 B 的上下文带偏，越想越乱（L4 的中间遗忘加剧版）。
3. **产能墙**：单个 agent 的循环（L3）是**串行**的，一步接一步，慢。三家竞品明明能同时调研，却只能排队。

这三堵墙，靠"把窗口做大"治标不治本（L4 讲过为什么）。真正的解法是**架构升级**：把一个大脑的活，拆给多个各有独立上下文的大脑去并行干。

---

## 2. 这层怎么补：主代理 + 子代理 + 编排

核心结构是一个**两层（或多层）的指挥体系**：

```
                    ┌────────────────────────┐
                    │   主代理 / Orchestrator  │  ← 它的桌子上只放:
                    │   (拆任务、派活、汇总)    │     总目标 + 各子代理交回的"精炼结论"
                    └───────┬─────────┬──────┘
                  派子任务A  │ 派子任务B│  派子任务C
              ┌─────────────┘    │     └─────────────┐
              ▼                  ▼                   ▼
     ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
     │ 子代理 A      │   │ 子代理 B      │   │ 子代理 C      │
     │ 独立干净上下文 │   │ 独立干净上下文 │   │ 独立干净上下文 │  ← 每人一张新桌子,
     │ 只看子任务A资料│   │ 只看子任务B资料│   │ 只看子任务C资料│     互不干扰
     │ 自己跑完整loop │   │ 自己跑完整loop │   │ 自己跑完整loop │  ← 各自是个完整 agent(L2+L3)
     └──────┬───────┘   └──────┬───────┘   └──────┬───────┘
            └── 交回精炼结论 ────┴─── 精炼结论 ──────┘
                          ▼
                  主代理汇总 → 最终产出
```

拆开看三个要件：

**① 子代理（sub-agent）是一个"完整的小 agent"。** 它自己有 L1–L5 那一整套：独立的 messages 列表、独立的上下文窗口、能调工具(L2)、能跑自己的循环(L3)。**关键在它的桌子是全新、干净的**——只装它那一份子任务，不被主线和其他子代理的内容污染。

**② 编排（orchestration）= 主代理怎么协调这群子代理。** 主要两种模式：
| 模式 | 怎么跑 | 适合 |
|---|---|---|
| **并行（parallel）** | 多个独立子任务**同时**派出去，一起干，再收齐 | 子任务之间没有依赖（三家竞品互不相关）→ 快 |
| **串行（sequential）** | 一个子代理的输出喂给下一个，接力 | 后一步依赖前一步结果（先调研、再据调研写方案）|
真实系统常是两者混合：能并行的并行、有依赖的串行。

**③ "上下文隔离"是收益的真正来源。** 子代理把一大堆中间过程（读了 50 个文件、试错 20 次）消化掉，**只把一小段结论交回主代理**。主代理的桌子因此始终干净——它从不接触子任务的"过程噪声"，只接收"提炼结果"。**这等于用多个窗口，突破了单个窗口的容量与清晰度上限。**

> **一句话：子代理不是"更多算力"，而是"更多张干净的桌子"。** 价值首先是隔离（每张桌子专注一件事、互不污染），其次才是并行（多桌同时开工提速）。

---

## 3. 底层原理：收益、代价与"何时该拆"

**收益**（对回那三堵墙）：
- 破容量墙：n 个子代理 ≈ n 张桌子，总可用上下文成倍放大。
- 破干扰墙：隔离让每个子任务在"无噪声"环境里做，质量更高。
- 破产能墙：并行让独立子任务同时跑，墙钟时间大幅缩短。

**代价**（拆不是免费的，这是高手和新手的分界）：
- **协调开销**：拆任务、派活、收结果、合并本身要花 token 和模型调用，小任务拆了反而更慢更贵。
- **信息损耗**：子代理只交回"精炼结论"，主代理看不到过程细节——如果子任务的关键信息没被总结进去，就丢了（接力时尤其要小心交接面）。
- **接口设计**：子代理要交回什么、格式如何、主代理怎么用——这个"交接契约"没定义清楚，团队就乱套。这跟人类团队一模一样。

> **何时该拆？** 判据是任务能否**清晰切成相对独立的块**。能（三家竞品、并行搜多个目录）→ 拆，收益大。不能（一个环环相扣、必须连贯推理的小任务）→ 别拆，硬拆只会增加协调开销和信息损耗。**默认单代理，遇到"大而可分"才上多代理**——这是务实的工程纪律，别为了炫技而拆。

## 4. Claude Code 锚点：你已经见过它派子代理

Claude Code 内置了子代理机制，Superpowers 更把它做成了一套方法论：

| Claude Code / Superpowers | 对应本层概念 |
|---|---|
| 它派出 **Task / 子代理**（Explore、general-purpose 等）去搜代码、做调研 | 主代理派**子代理**，各自独立上下文跑完再交回结论 |
| 子代理"读了一堆文件，只把结论返回给主线" | **上下文隔离**：过程噪声留在子代理桌上，主线只收精炼结果 |
| 多个独立子代理**同时**派出去 | **并行编排**（Superpowers 的 dispatching-parallel-agents 技能就在教这个）|
| Superpowers 的 **subagent-driven development**：把实现计划拆成任务，逐个/并行派子代理做、再复查 | 串行+并行混合编排 + 交接契约（每个任务有明确产出）|
| 系统反复提示"别为单个简单任务派子代理" | **何时该拆**的工程纪律——协调开销不值当就别拆 |

下次 Claude Code 说"正在派一个子代理去探索代码库"，你能看穿：它在**开一张新的干净桌子**，让子代理在隔离环境里把"读 30 个文件"这种重活干完，只把"我找到了，在这几个文件里"交回主线——保护主线桌面不被 30 个文件的内容淹没。这正是它能处理大型代码库还不"变笨"的关键招数之一。

## 5. 小练习 / 思考题

1. 子代理带来的两类收益里，哪个是更根本的——"并行提速"还是"上下文隔离"？用本层的"桌子"比喻说明为什么。
2. 给两个任务判断该不该拆成多个子代理，并说明理由：(a) "把这个 2000 字段落改通顺"；(b) "调研 5 个开源库各自的优缺点并对比"。
3. "并行"和"串行"编排各适合什么情况？举一个必须串行（不能并行）的例子。
4. 拆子代理不是免费的。列出至少两项代价，并说明"信息损耗"具体是怎么发生的。
5. 自检：一句话说清子代理为什么能"绕过单个上下文窗口的上限"（提示：和 L4 的窗口上限挂钩）。

<details>
<summary>参考答案</summary>

1. **上下文隔离**更根本。并行只是"多桌同时开工"提速；但即便串行地用子代理，"每张桌子只装一件事、互不污染"本身就能显著提升每个子任务的质量，并绕过容量墙。隔离是因，提速是其中一个果。
2. (a) **不该拆**：小而连贯，拆了协调开销 > 收益。(b) **该拆**：5 个库相对独立，可并行调研，每个给一张干净桌子专注一个库，最后主代理汇总对比——典型的"大而可分"。
3. 并行适合**子任务互相独立**（同时干、最后收齐）；串行适合**后一步依赖前一步输出**。必须串行的例子：先让子代理 A 调研需求产出规格，再让子代理 B 依据这份规格写实现——B 没有 A 的产出就没法开始。
4. 代价如：①协调开销（拆/派/合并本身耗 token 和调用）；②信息损耗（子代理只回传精炼结论，过程细节丢失）；③接口/交接契约要设计。信息损耗发生在"子代理总结结论"这一步——没被写进总结的关键细节，主代理就永远看不到了。
5. 因为每个子代理有**自己独立的上下文窗口**，n 个子代理等于 n 张桌子，把"单张桌子装不下"的大任务分摊到多张干净桌子上，从而突破了 L4 单窗口的容量与清晰度上限。

</details>

## 一句话带走

> **把一个 agent 变成一支团队，靠的不是"更多算力"，而是"更多张干净的桌子"——每个子代理在隔离的上下文里专注一件事，把过程噪声消化掉、只交回精炼结论。隔离保质量、并行提速度；但拆有协调成本，所以默认单代理，遇到"大而可分"才组队。**

下一层 **L7 可靠性、验证与自主性**：我们的 agent 现在能力拉满、还能组队了——但能力越强、跑得越自主，**跑偏和犯错的破坏力也越大**（L3 埋下的那颗雷）。怎么给这头猛兽套上缰绳，让它"自主"且"靠谱"？这是从"能跑"到"敢托付"的最后一道关。
