# L3 · 让模型能"持续做事"：Agent Loop

> 本层目标：理解"agent 之所以是 agent"的那个核心机关——一个循环。
> 它把 L2 的"单次工具调用"接成"一步接一步直到完成"。对应修补缺陷：**③ 不能持续**。
> 这一层很短，但它是整个领域的**分水岭**：循环之前叫"聊天机器人"，循环之后才叫"智能体"。

---

## 0. 先讲一个画面

你请了个装修工（模型）。两种合作方式：

- **没有循环**：你说一句"把墙刷白"，他刷一下油漆，停下，等你下一句指令。墙没刷完？不管，他只动一下就僵在原地。你得手动喊"继续……继续……再继续……"几百遍。
- **有循环**：你说"把这面墙刷白"，他自己开始：刷一道 → 看哪里没盖住 → 补一道 → 再看 → 再补 → 直到整面白了，才停下报告"刷完了"。

第二种里，那个"看一眼→决定下一步→动手→再看一眼"**自动重复**的机制，就是 **Agent Loop（智能体循环）**。它不在模型里——模型还是那个"动一下就停"的工人——它是 harness 用一个 `while` 循环，**一遍遍把工人喊回来继续干**。

---

## 1. 模型缺了什么：一次调用，只走一步

L0 缺陷③：模型说完一句就停。L1 印证了这点——一次调用 = 喂进 messages、吐出一条 assistant 消息，结束。哪怕任务只完成了 5%，模型也**不会主动"再来一轮"**。

可是真实任务几乎都是多步的："修好这个 bug"要：读代码 → 定位 → 改一处 → 跑测试 → 看报错 → 再改……一次调用根本走不完。**谁来驱动"做完一步、看结果、决定并执行下一步"的反复？** 不是模型——是 harness 的循环。

---

## 2. 这层怎么补：一个 while 循环

Agent loop 朴素到你会惊讶。去掉所有花哨，它就是这段伪代码：

```
messages = [system, 用户任务]            # L1 那叠纸的开头

while True:                              # ← 整个 agent 的心脏，就是这个循环
    回复 = 调用模型(messages)            # 模型走一步：思考 + 可能开一张工具申请单(L2)

    if 回复 包含工具申请:
        结果 = 执行工具(回复.工具申请)    # harness 真去做(L2 第③步)
        messages.append(回复)            # 把模型这步的话记进列表
        messages.append(结果)            # 把工具结果也记进列表(L2 第④步)
        continue                         # ← 关键：带着新结果，回到循环开头再走一步

    else:                               # 模型不再申请工具，说明它认为任务做完了
        return 回复                      # 跳出循环，把最终答复交给用户
```

就这么点东西。但请盯住三个地方：

1. **`while` 是发动机。** 模型每轮只走一步，是这个循环让它**一步接一步**。没有它，agent 就退化成 L2 的单次调用。
2. **messages 在循环里不断变长。** 每轮把"模型的话 + 工具结果"追加进去。所以**下一轮模型能看到前面每一步做了什么**——这就是它"知道自己进行到哪"的全部来源（又一次印证 L1：记忆在列表里）。
3. **退出条件 = 模型不再开申请单。** 当模型觉得活干完了，它就只输出文字、不再申请工具，`else` 分支触发，循环结束。**是模型在"判断任务是否完成"，但 harness 在"执行这个判断"。**

> **一句话定义：Agent = L2 的工具调用 + 一个让它反复执行直到完成的循环。** "Agentic（具备智能体性）"这个词，指的就是这个"自主走多步"的能力——而它的实现，平凡到只是一个 `while`。

---

## 3. 底层原理：自由的代价与必要的缰绳

循环给了模型"自主连续行动"的自由。但自由有代价，好的 harness 必须在循环里装几道保险（这些也是 L7 的预告）：

- **必须有"硬刹车"。** 万一模型陷入"申请→失败→再申请同样的东西→再失败"的死循环怎么办？所以真实的循环里永远有 `max_steps`（最大步数）上限：走了比如 50 步还没完，强制停下交还控制权。**永远不要让 agent 拥有无限循环的权力。**
- **错误不该终止循环，而该喂回去。** 接 L2：工具失败时，把错误当结果 append 进 messages，让循环继续转——模型读到报错往往能自己换路子。这正是 agent "看起来会自我纠错"的来源。
- **步数越多，越容易跑偏（埋下 L7 的种子）。** 每一步模型都可能犯个小错，循环把这些小错**累积**起来。走 3 步通常没事，让它自主走 80 步就可能越跑越歪。所以"能自主多步"是把双刃剑——L7 整层就在教怎么给这把剑配上缰绳（验证、计划、复查）。

> 原理一句话：**循环把"判断"（模型，每步决定做什么）和"驱动+刹车"（harness，反复调用并设上限）拼在一起。给模型自由走多步，同时握紧"最多走几步、错了怎么办"的控制权——这就是 agent loop 的工程精髓。**

## 4. Claude Code 锚点：你看到的"转圈圈"就是这个循环

你给 Claude Code 派一个稍复杂的活（"帮我把这个功能加上并跑通测试"），然后看着它自己读文件、改代码、跑测试、看报错、再改……**那个持续转圈、一步步推进的过程，就是 agent loop 在转。**

| 你看到 Claude Code | 对应 loop 里的哪一步 |
|---|---|
| 它读文件、跑命令、改代码，一步接一步自动推进 | `while` 每转一圈 = 模型走一步 + harness 执行工具 + 结果回填 |
| 测试报错后它"看了一眼"又自己改 | 错误结果被 append 回 messages，下一圈模型读到后纠正 |
| 干到一半它停下来问你 / 报告完成 | 模型不再开工具申请单，`else` 触发，循环退出，控制权交还你 |
| 极少数时候它"卡住/绕圈"，或你按 Esc 打断 | 撞上 `max_steps` 硬刹车，或你手动中止——握在 harness/你手里的控制权 |

下次看它干活，试着数"它走了几步"，并意识到：**每一步之间，都有一次完整的 L1 调用（整叠 messages 重发）+ L2 工具执行。** 这也解释了为什么复杂任务又慢又费 token——循环转得越多，调用越多。

## 5. 小练习 / 思考题

1. 一句话说清：聊天机器人和 agent 的根本区别是什么？（提示：就差这一层的一个东西）
2. 为什么 agent loop 里**必须**有 `max_steps` 这类上限？不设会出什么事？
3. 在循环的伪代码里，模型"觉得任务完成了"是怎么表现出来的？harness 又是怎么据此退出的？
4. 有人说"Claude Code 会自己纠错，好智能"。请用 L2+L3 拆穿这个"智能"背后的平凡机制。
5. 自检：默写 agent loop 的伪代码骨架（不用精确语法，讲清"循环、调模型、判断是否有工具申请、执行并回填、退出条件"即可）。

<details>
<summary>参考答案</summary>

1. 就差一个**循环**。聊天机器人是 L1 的单次调用（答一句就停）；agent 是把工具调用(L2)套进一个 while 循环，能自主走多步直到任务完成。
2. 防死循环 / 防失控。模型可能陷入"申请→失败→再申请→再失败"的无限重复，或一直觉得"还没完"。没有上限，agent 会无限烧 token、无限运行。`max_steps` 是必备的硬刹车。
3. 表现为：模型这一轮**不再输出工具申请单**，只输出普通文字回答。伪代码的 `else` 分支据此判断"没有工具申请 = 它认为做完了"，于是 return、跳出 while。
4. "纠错"= L2 的错误结果回填 + L3 的循环继续：工具报错被当结果 append 回 messages，循环转到下一圈，模型读到报错、重新开一张修正过的工具申请单。没有"智能纠错"，只有"错误信息被喂回 + 循环再转一圈"。
5. （对照正文伪代码：初始化 messages → while 调模型 → 若有工具申请则执行+把模型输出和结果都 append 回去+continue → 否则 return；外加 max_steps 上限。）

</details>

## 一句话带走

> **Agent 不是某种更聪明的模型，而是"工具调用 + 一个 while 循环"。循环负责让只会走一步的模型一步步走到底，harness 同时握着"最多走几步、错了怎么办"的缰绳——这就是"智能体"四个字的全部硬核。**

接下来三层是一组"记忆与容量"的攻坚战。下一层 **L4 上下文工程**：循环转得越多，那叠 messages 越长，迟早撑爆上下文窗口。怎么在有限的窗口里只装最该装的东西？这是 harness 工程里最考手艺的部分。
