上一篇文章，我分享了我 [ 短视频自动化工作流从 0-1 的开发流程
](https://mp.weixin.qq.com/s?__biz=MzcwODI5MjA5NQ==&mid=2247483928&idx=1&sn=49a30df53136b2e94b6142843fe9ede0&scene=21#wechat_redirect)
。

最近我又一直在研究 agent，前阵子去玩了openclaw、又用了一阵子Hermes。

我灵机一动，我那个工作台，本质上是一个类似 Coze
工作流的东西，如果我多搞几个节点，把我所有工作相关的节点都放进去，那应该是一个很有趣的事情，如果我再能给他装一个 LLM 当总控，那它岂不是就成了
agent 了吗？可以学习Hermes自主造工具的这个优点啊。

说干就干！

此前我做的「掌镜使」，核心解决的是短视频生产链路的问题：

![Image](/images/claudecode-codex-production-system/img-02.png)

    对标采集 -> 视频下载 -> ASR 提取文案 -> 文案二创-> TTS 配音 -> 批量混剪 -> MediaPush 发布  
    
这套东西跑通之后，我的第一反应是：爽!

因为它确实把我每天重复做的短视频流程压缩进了一个本地工作台里。

但用着用着，我又发现了一个新问题：  ** 我的工作并不只有短视频。  **

我还要写公众号，要做封面，要生成配图，要整理文章，要发小红书，要做知识卡片，后面可能还要做数据复盘、选题管理、账号诊断、私信处理。

如果每来一个新需求，我都重新做一个独立工具，那最后我电脑里会堆满一堆小软件。

每个软件都能干一点事，但它们之间互相不认识，产物也不能自然流转。

于是我开始想：

能不能不要再做“一个又一个工具”，而是做一个“能不断接工具的工作台”？

也就是说，我真正想要的，其实是一个本地内容生产系统，短视频只是它的第一块。

** 它应该像 Coze 一样，可以把能力拆成节点；也应该像 ClaudeCode / Codex
一样，可以理解我的目标，自己知道该调用谁、先做什么、后做什么。  **

这就是这个项目的起点。

我给它起了一个很直白的名字：  ** 无限节点画布工作台。  **

后来做到 v2，它其实已经不太只是“短视频”了。

更准确地说，它变成了一个：

    Coze 的身体 + Codex / Claude 的脑子  
    
身体是可视化节点画布，脑子是外部 agent，节点是一个个员工，MCP 是 agent 进入工作台、调度员工的控制台。

这就像是我开了一家公司，Codex、ClaudeCode当我的总经理，而这一个一个的节点，就是我公司的实习生们。

![](/images/claudecode-codex-production-system/img-03.png)

#  我想做的到底是什么

这个项目一开始的想法很简单：把上一版短视频自动化工作台，改成一个节点画布。

比如原来是几个独立工作台：

  1. 抖音主页采集； 

  2. 抖音视频下载； 

  3. ASR 文案提取； 

  4. 文案改写； 

  5. 批量混剪； 

  6. MediaPush 发布。 

它们可以分别跑，但中间衔接还是偏“工具拼工具”。

我希望把它们变成画布上的节点。

每个节点有输入，有输出，有参数，有状态。

采集节点输出作品链接，下载节点接收作品链接；下载节点输出视频文件，ASR 节点接收视频文件；ASR
输出口播文案，改写节点接收文案；改写节点输出批量任务，混剪节点接收任务；混剪节点输出成片，发布节点接收成片。

画出来大概是这样：

    抖音主页采集  
        ↓  
    抖音视频下载  
        ↓  
    ASR 文案提取  
        ↓  
    文案改写 / 标题生成  
        ↓  
    批量混剪生成  
        ↓  
    MediaPush 发布  
    
这件事第一眼看起来像是“做个 UI”。

但真正开干之后，我发现它比 UI 复杂得多。

因为画布只是表面。

真正难的是：  **
节点之间怎么知道彼此能不能连接？一个节点的输出到底是什么格式？下游怎么确定自己能消费？如果某个节点失败了，状态怎么保存？如果程序关了再打开，之前的画布还在不在？
**

这些问题如果不解决，最后做出来的就只是一个好看的流程图，而不是一个能真正跑工作的系统。

所以我把项目拆成了三层：

层级  |  要解决的问题   
---|---  
画布层  |  节点怎么拖拽、连线、保存、加载、运行   
节点层  |  每个能力怎么声明输入、输出、参数、风险、产物   
总控层  |  大模型怎么理解节点，并根据目标编排和执行流程   
  
这也是我这个项目最重要的产品判断：

** 不要先做“聪明的 AI”，先做“能被 AI 理解的工具”。  **

如果节点自己都说不清楚自己能干什么，大模型再聪明也只能靠猜。

#  阶段一：先把短视频链路节点化

第一阶段，我没有一上来就做“万能工作台”。

还是先从我最熟的短视频链路开始。

因为这条链路我已经跑通过，知道每一步的输入输出，也知道哪里容易出问题。

这条链路最后拆成了 6 个真实节点：

节点  |  输入  |  输出   
---|---|---  
抖音主页采集  |  抖音主页链接  |  作品链接列表   
抖音视频下载  |  作品链接列表  |  本地视频文件   
ASR 文案提取  |  视频文件  |  纯口播文案   
文案改写 / 标题  |  口播文案  |  改写文案、标题、混剪任务   
批量混剪生成  |  混剪任务  |  成片视频   
MediaPush 发布  |  成片视频  |  发布记录   
![](/images/claudecode-codex-production-system/img-04.png)

这里面有一个很关键的变化。

以前我做工具的时候，更多关注的是“这个功能能不能跑”。

但做节点画布之后，我开始必须关注另一个问题：

** 这个功能能不能被别的功能稳定地接住。  **

比如 ASR 节点，如果它输出的是一堆 Markdown、JSON、时间戳、文件名混在一起，下游改写节点就会很难处理。

所以后来我把 ASR 的正式输出收紧成“纯 TXT 文案”。

` .md  ` 、  ` .json  ` 这些调试产物可以保留，但不能作为正式输出传给下游。

![](/images/claudecode-codex-production-system/img-05.png)

这个小改动对我启发很大。

以前我会觉得多输出一点没坏处，反正都在文件夹里。

但到了工作流系统里，多余信息很可能就是噪音。

节点之间最重要的，是一份承诺：我交给你的，一定是稳定、干净、你可以用的东西。至于我手上那些乱七八糟的中间产物，是我自己的事，不该一股脑倒给你。

这就是工作流和普通脚本最大的区别。

#  阶段二：无限画布和执行引擎

画布部分我做成了 PyQt5 桌面端。

左边是节点库，中间是无限画布，右边是参数、状态、环境和设置区域。

节点可以拖拽、双击添加、移动、选中、删除，也可以从输出端口拖线连到下游输入端口。

一开始我以为这些只是交互细节。

但做下来才发现，这些细节决定了它是不是“工作台”，而不是一个临时脚本壳子。

比如：

  1. 节点要能保存和加载，否则每次都要重新搭流程； 

  2. 参数要控件化，路径要能选择，否则非开发者根本不好用； 

  3. 节点要有最近输出，否则跑完以后不知道产物在哪； 

  4. 运行日志要落盘，否则失败以后只能凭感觉猜； 

  5. 环境检测要放在界面上，否则 FFmpeg、bun、Python、外部工具缺哪个都看不出来。 

这些功能看起来都不酷。

但我现在越来越觉得，一个产品能不能长期用，拼的就是这些不酷的东西。

特别是“运行方式”。

我给节点做了几种执行方式：

  1. 运行当前节点； 

  2. 从这里继续运行； 

  3. 运行全部流程； 

  4. 没有依赖的节点可以并行启动。 

![](/images/claudecode-codex-production-system/img-06.png)

这就意味着它不再只是一个静态流程图。

它真的开始像一个小型生产系统了。

你可以只重跑失败的节点，也可以从中间继续跑下游，不需要每次从头开始。

对于内容生产来说，这一点非常重要。

因为一条链路里，下载、ASR、TTS、混剪、发布都可能很耗时。

如果一个环节失败就全链路重跑，那用户很快就会崩溃。

#  阶段三：节点要有“岗位说明书”

做到这里以后，我遇到了一个非常本质的问题：

如果我要让大模型当总控，它怎么知道每个节点是干什么的？

一开始我的节点信息很薄，大概只有：

    {  
    "name":"抖音视频下载",  
    "description":"下载抖音视频",  
    "inputs":["profile_links"],  
    "outputs":["video_files"]  
    }  
    
这就像给总控看了一张员工名片。

它知道这个员工叫啥，但不知道这个员工什么时候该上场、需要什么材料、交付什么结果、参数怎么填、填错会怎样。

如果只是人自己拖节点，这也许够用。

但如果是 agent 来编排，就不够了。

所以 v2 的核心，我做了一件事情：

** 把节点自描述做厚。  **

我把每个节点从“名片”升级成“岗位说明书”。

它里面包含：

  1. 这个节点的能力标签； 

  2. 什么时候应该使用它； 

  3. 典型上游是谁； 

  4. 典型下游是谁； 

  5. 输入输出端口的数据契约； 

  6. 每个参数是什么意思、怎么填、填错的后果； 

  7. 真实产物样例； 

  8. 风险等级，是否需要人工确认。 

![](/images/claudecode-codex-production-system/img-07.png)

比如“抖音视频下载”这个节点，不再只是“下载视频”四个字。

它要告诉总控：

当你已经拿到了作品链接列表，需要把视频下载到本地时，用我。

我的上游通常是“抖音主页采集”，我的下游通常是“ASR 文案提取”。

我吃进去的是一组作品链接，不是随手一段文本。

我吐出来的是一批本地视频文件路径，不是一个字符串。

我是真实重任务，运行前需要确认。

这个设计完成之后，我突然明白了一件事：

** Agent 的记忆，不一定非要放在 prompt 里，也可以放在工具的说明书里。  **

![](/images/claudecode-codex-production-system/img-08.png)

一个节点把自己说清楚了，总控就不需要每次靠猜。

这也是我整个项目里最喜欢的一个设计。

（后来这份说明书还遇到一个新问题：节点越来越多，agent 每次上来把所有节点的完整说明书读一遍，太费
token。所以我又加了一层——先给一句话的节点清单，agent 真要用到、或要排查某个节点时，再去调它的完整说明书。先略读，按需深挖。）

#  阶段四：强 Schema 端口，不再靠名字瞎连

节点有了岗位说明书之后，下一步是让节点连线更可靠。

早期的连线逻辑很简单：输出端口名和输入端口名一样，就允许连接。

比如  ` video_files  ` 接  ` video_files  ` ，这当然没问题。

但真实工作流里，不可能所有端口名字都完全一样。

有时候两个端口名字不同，但数据结构兼容；有时候名字看起来差不多，实际根本不能接。

所以我给端口也做了数据契约。

每个端口不仅有名字，还有：

  1. 人类可读标签； 

  2. 数据形态，比如 text、file_list、json、image_list； 

  3. 单个元素是什么； 

  4. 字段结构； 

  5. 示例。 

这样连线校验就不再只是看名字，而是看契约是否兼容。

比如“作品链接列表”和“本地视频文件列表”都可能是列表，但它们显然不是一种东西。

前者是 URL，后者是本地文件路径。

如果错误连接，画布会拒绝，并告诉你原因。

这个能力对人有用，对 agent 更有用。

因为 agent 编排流程时，最怕的就是“看起来差不多，实际接不上”。

强 Schema 端口就像给每个节点的交接材料贴了标签。

谁能接谁，谁不能接谁，不靠感觉，靠协议。

#  阶段五：Skill 节点，让能力可以无限叠加

做到这一步，我的野心又变大了。

如果只能接短视频相关节点，那它还是一个垂直工具。

我真正想做的是：

** 任何一个能力，只要给它一份说明书，就能成为节点。  **

比如：

  1. 公众号文章配图； 

  2. 封面设计； 

  3. 信息图设计； 

  4. 小红书图片卡片； 

  5. 文生图； 

  6. 公众号草稿上传； 

  7. 后续的翻译、排版、Markdown 转 HTML、文章评分。 

这里我没有选择“让 agent 在运行时现场写段代码就地跑”。

因为这件事听起来很智能，但实际很危险。

如果每新增一个能力，agent 都临时写一段代码并执行，那这个工作台就会变成另一个 ClaudeCode。

而且还是一个更难审计、更容易失控的 ClaudeCode。

这也是我对开头那个念头的修正：我一开始是羡慕 Hermes 那种「自主造工具」的劲儿，但真做下来才想明白——我想要的是它的自主，不想要它的失控。

所以我给自己定了一条铁律：

** 能力以“节点”为单位沉淀——可以写代码，但不在运行时即兴写段就地跑、跑完即弃。  **

外部大脑（Claude / Codex 这类擅长编码的
agent）写代码本身没问题，那正是它们的强项；关键是写出来的能力，必须落成一个可复用、可审、画布上看得见的节点，而不是每次活儿都临时雇个黑工、干完就消失。

新能力只走三条路径：

  1. 提示词 skill：适合分析、写作、评分、出方案； 

  2. 脚本 skill：适合排版、出图、上传、转换这类行动； 

  3. 外部 agent 写脚本 / 连接器节点：没有现成 skill 或工具时，让擅长编码的 agent 写一个，人工审核后落盘，写一次永久复用。 

这个设计的关键是“声明与执行解耦”。

造节点时，只生成节点声明，也就是 Manifest。

![](/images/claudecode-codex-production-system/img-09.png)

真正执行时，所有同类 skill 节点共用一个通用执行器。

比如 text 模式，就是把 skill 正文当 system prompt，把上游输入作为 user 内容，调 LLM 后把结果落盘。

script 模式，就是调用 skill 自带的 bun / python 脚本，把输入文件、输出目录、环境变量传进去。

也就是说，新增一个 skill 节点不需要也不允许改工作台代码。

只要它有说明书，符合输入输出协议，就能被画布认识、被总控调度。

这一步做完之后，项目的性质就变了。

它不再是“短视频工具”，而是一个能不断接入新能力的内容生产底座。

#  阶段六：公众号链路跑起来

接入 skill 节点之后，我很快做了另一条链路：公众号文章配图并上传草稿箱。

这条链路是这样的：

    文章 MD 导入  
        ↓  
    文章配图方案  
        ↓  
    文生图  
        ↓  
    公众号文章装配  
        ↓  
    公众号草稿上传  
    
![](/images/claudecode-codex-production-system/img-10.png)

这跟短视频链路已经完全不是一个领域了。

短视频链路处理的是视频、文案、TTS、素材、成片。

公众号链路处理的是文章、配图方案、图片、Markdown 装配、草稿上传。

但它们可以共用同一个画布、同一套端口协议、同一套运行引擎。

这就是 v2 最有价值的地方。

以前我做一个新工具，就要重新做一套界面、一套参数、一套日志、一套输出。

现在我只需要思考：

这个能力是什么节点？

它吃什么？（输入是什么？）

它吐什么？（输出是什么？）

它有什么风险？

它适合接在哪些节点后面？

这个思维变化很重要。

从“做功能”，变成“设计岗位”。

节点像员工一样，有岗位职责、有上游交接、有下游交付、有风险边界。

总控的活，是认识员工、分派任务、检查结果；具体每件事，未必要它亲自上手。

#  阶段七：把内置总控拿掉，让外部 Codex / Claude 当大脑

最开始，我其实在应用里做过一个内置总控。

它可以填 OpenAI-compatible API，可以根据自然语言目标生成计划，可以自动创建节点和连线。

听起来很合理，但项目做到后面，我反而把它拿掉了。

原因也很简单：

外部 Codex / ClaudeCode 已经是更强的大脑了。

我没必要在应用里再造一个弱版总控。

如果我硬要把所有智能都塞进软件内部，最后大概率会得到一个能力有限、上下文有限、调试困难的内置 AI。（主要是我实操下来发现，接入的 LLM
只能帮我「招人」和「排班」，排好班后节点干活出了问题它不知道，也没法介入修正。）

不如反过来：

** 工作台只负责把节点、画布、执行、状态、产物做好；大脑交给外部 agent。  **

于是我做了 MCP 控制面。

MCP 这东西你可以简单理解为：外部 AI 进入工作台的控制台，更通俗的理解它像是一把键盘鼠标，Agent 可以通过键盘鼠标操控这个工作台。

它可以看到有哪些节点，可以添加节点，可以连线，可以设置参数，可以运行节点，可以读取输出，可以看日志，也可以创建新的 skill 节点。

同时，画布和 MCP 共用同一个  ` active.json  ` 。

外部 agent 通过 MCP 改了工作流，PyQt 画布会实时监听并重绘。

也就是说：

Codex/ClaudeCode 在外面调度，用户在画布上看见。

这件事做完以后，整个产品的形态突然清晰了。

    用户：提出目标  
    Codex / Claude：理解目标，拆解任务，调度节点  
    MCP：控制台  
    画布：作战地图  
    节点：具体员工  
    运行器：执行系统  
    日志 / 输出：复盘证据  
    
我在「入职文档」里把它写成了一句很土但很好懂的话：

    用户 = 老板  
    Codex / Claude = 总经理 / 大脑  
    工作台画布 = 公司作战地图  
    节点 = 各岗位员工  
    MCP = 进入公司和调度员工的控制台  
    
这个比喻很形象。

因为我越来越觉得，一个 agent 产品能不能用，关键看它有没有一套清晰的组织结构去干活，而不只是看 AI 自己有多会临场发挥。

这里也说句实在话。这套东西的架构和统筹，其实主要是我带着 Claude
一点点啃下来的——拆阶段、定协议、设计节点和端口、守边界，都是反复磨出来的。Codex
更多是接我派下去的实现杂活，比如某些节点的批量改造。运行时谁当大脑可以随时换，但把这套“组织结构”本身想清楚、搭起来，才是最花心思、也最值钱的部分。

#  阶段八：Codex 亲自接手自己擅长的事

MCP 控制面做好以后，我又遇到一个有意思的问题：  生图节点到底应该谁来跑？

一开始文生图节点是走第三方 provider，比如即梦、OpenRouter、OpenAI、Google、Replicate 等等。

但我后来发现，Codex 本身就有内置 imagegen 能力。

既然外部 Codex 已经是总控，那为什么一定要让工作台自己调用第三方生图接口呢？

于是我把文生图节点改成了外部动作协议。

流程变成这样：

    文章配图方案  
        ↓  
    文生图节点生成 external_action_request  
        ↓  
    节点状态变成 waiting_external  
        ↓  
    Codex 读取待处理动作  
        ↓  
    Codex 用内置 imagegen 生成图片  
        ↓  
    Codex 回填 image_list  
        ↓  
    公众号文章装配继续运行  
    
![](/images/claudecode-codex-production-system/img-11.png)

这个设计我非常喜欢。

因为它既不让工作台什么都自己扛，也不让 Codex 绕过工作台乱来。

两边各干各的擅长：

工作台负责流程、状态、产物协议。

Codex 负责它更擅长的生图、网页抓取、复杂判断。

干完以后，再把结果按标准端口交回工作台。

这就像一个公司里，有些员工是内部岗位，有些任务需要外部专家协助。

但不管谁干，最后交付物都要回到公司的流程系统里。

这才是可审计、可恢复、可继续往下跑的 agent 工作流。

#  阶段九：通用网页抓取节点

做完生图外部动作后，我又顺手把这个协议扩展了一下。

既然 Codex 可以接手生图，那它也可以接手网页抓取。

于是我做了一个“网页正文抓取”节点。

输入一个 URL，输出一篇本地 Markdown 文章，也就是  ` article_text  ` 。

它的逻辑分两路：

  1. 如果是 X / Twitter 链接，就走专门的 x-markdown 脚本，解析长文并下载图片； 

  2. 如果是普通网页，就发起 external_action，让外部大脑用 WebFetch 抓正文后回填。 

这个节点看起来很小，但意义很大。

因为它是一个“输入源层”的通用节点。

以前一篇文章进入工作流，可能要我手动复制、保存、整理。

现在可以是：

    网页正文抓取  
        ↓  
    文章配图方案  
        ↓  
    文生图  
        ↓  
    公众号文章装配  
        ↓  
    公众号草稿上传  
    
这就从“我准备好文章后再交给工作台”，变成了“工作台自己帮我把网页内容接进来”。

更重要的是，external_action 协议不再只为生图服务。

它开始变成一个通用机制：

工作台可以发起请求，外部大脑用自己的原生能力完成，再把结果按端口类型回填。

今天是生图和网页抓取。

明天可以是搜索、OCR、复杂网页解析、竞品研究、数据分析。

这就是一个底座开始变厚的感觉。

#  真正难的不是节点，而是状态可信

这个项目做下来，我最大的感受是：

做几个节点不难。

真正难的是让节点执行结果可信。

因为一旦进入 agent 编排，系统最怕的不是失败。

失败不可怕，失败还能重试。

最可怕的是“假成功”。

比如某个节点表面显示 success，但实际没有产物。

或者某个命令返回失败，但磁盘上真实产物已经生成了。

这些情况在真实链路里都遇到过。

这对 agent 来说很危险。

因为 agent 会根据状态决定下一步。

如果状态是假的，后面的所有推理都会被带偏。

所以我后来越来越重视这些看起来很底层的东西：

![](/images/claudecode-codex-production-system/img-12.png)

  1. 节点状态要清晰：pending、running、success、failed、waiting_external； 

  2. last_output 要记录真实产物； 

  3. error 要能说明失败原因； 

  4. 日志要能追溯过程； 

  5. 高风险节点要 confirm； 

  6. 外部动作要能等待和回填； 

  7. 工作流要有单一真相源； 

  8. 画布和 MCP 要通过同一份状态同步。 

以前我会觉得 agent 产品最重要的是“智能”。

现在我反而觉得，agent 产品要进入生产状态，最重要的是“状态可信”。

智能可以帮你想办法，但状态决定它想的是不是同一个现实。

#  当前它已经能做什么

截至目前，这个工作台已经不是 UI 原型了。

![](/images/claudecode-codex-production-system/img-13.png)

它能真实跑短视频链路（也就是我掌镜使在干的事情）：

    抖音主页采集  
      -> 抖音视频下载  
      -> ASR 文案提取  
      -> 文案改写 / 标题  
      -> 批量混剪生成  
      -> MediaPush 发布  
    
它也能跑公众号内容链路：

    文章 MD 导入 / 网页正文抓取  
      -> 文章配图方案  
      -> 文生图（Codex imagegen）  
      -> 公众号文章装配  
      -> 公众号草稿上传  
    
它还有一套 MCP 控制面，外部 Codex / Claude 可以通过 17 个工具操控画布：

    list_node_index / describe_node / get_workflow  
    add_node / connect / set_params / run_node / run_chain  
    get_output / get_logs / create_skill_node  
    get_external_actions / complete_external_action ...  
    
这里面我最满意的是它形成了一套扩展方法：

  1. 新能力先变成节点； 

  2. 节点必须写清楚岗位说明书； 

  3. 输入输出必须有端口契约； 

  4. 能用提示词 skill 就不写代码； 

  5. 能用脚本 skill 就不重造轮子； 

  6. 需要外部大脑亲自做的事，就走 external_action； 

  7. 最后所有结果都回到画布状态里。 

这套方法一旦成立，后面能接的东西就很多了。

短视频只是第一条链路。

公众号、小红书、知识卡片、选题库、数据复盘、私信管理，都可以继续往上挂。

#  成本和结果

这个项目做到现在，最直接的结果是：

我从“做一个个工具”，开始转向“搭一套工具组织系统”。

以前每新增一个需求，我的第一反应是再写一个脚本、再做一个界面。

现在我的第一反应是：

这个能力应该是什么节点？

它的输入是什么？

它的输出是什么？

它能不能复用已有 skill？

它应该由工作台执行，还是由 Codex 通过外部动作接手？

这是一种很不一样的产品思维。

成本方面，主要还是模型 API、TTS、生图和时间成本。

但相比以前每个工具都从零写一遍，现在很多能力可以通过 skill 节点快速接入。

真正贵的不是调用成本，而是把系统边界想清楚。

比如我明确不让管家在运行时跑没沉淀成节点的代码。

比如高风险节点必须确认。

比如凭证统一放在 gitignored 的  ` credentials.json  ` ，不让 MCP 回传密钥。

比如文生图默认让 Codex 接手，但回填必须走标准  ` image_list  ` 。

这些选择看起来没有功能演示那么刺激，但它们决定了这个东西后面能不能继续长大。

#  最后复盘

如果总结这个项目，我觉得最大的收获有三个。

第一，工具自动化的下一步，不在于堆更多工具，而在于把它们组织起来。

上一版短视频工作台解决的是“重复劳动自动化”。

这一版节点画布解决的是“能力如何编排、复用和扩展”。

一个工具再强，也只能解决一类问题。

但如果每个工具都能变成节点，并且节点之间有稳定协议，那它就开始变成系统了。

第二，Agent 与其说是一个会魔法的大模型，不如说是一个能调度工具的组织者。

以前我会把 agent 想成“AI 自己干活”。

现在我更愿意把它理解成“AI 作为总控，理解目标、拆解任务、派发节点、检查结果、接手自己擅长的部分”。

真正厉害的地方，是给它一套可视、可控、可复盘的工作系统；放它无边界地乱跑，反而是下策。

第三，产品边界比智能更重要。

能不能让外部大脑写代码？

能，而且鼓励——那是它的强项。

要不要让它在运行时即兴写段代码、就地跑、用完即弃？

我的答案是：不要。

代码可以写，但必须落成节点——可复用、可审、画布上看得见。

因为我的目标不是做一个替代 ClaudeCode 的东西。

我的目标是做一个内容运营者也能看懂、能复用、能沉淀、能把风险握在手里的本地工作台。

所以我宁愿它慢一点、笨一点、边界清楚一点。

只要它能稳定地把节点串起来，把结果交付出来，把失败留下证据，它就有长期价值。

现在再回头看，这个项目已经从“短视频节点画布”变成了一个更大的东西。

它像是我给自己搭的一家公司。

每个节点是一个员工。

每个端口是交接标准。

每份 Manifest 是岗位说明书。

MCP 是管理后台。

Codex / Claude 是外部总经理。

而我，只需要告诉它：

今天的目标是什么。

以前是我在工具之间搬砖。

后来是工具在我的流程里干活。

现在，是 agent 开始调度这些工具替我干活。
