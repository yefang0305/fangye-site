#  项目背景

作为一个玩短视频矩阵的人来讲，日常最繁琐的工作，莫过于每天重复做视频剪辑、发布、账号管理这些事情。

我在运营的账号加起来一共有 50 个，覆盖了抖音、快手、视频号、小红书，如果加上 TK 的话那就更多了。在 vibe coding
出来之前，我每天有一半的时间是在给人做交付，另一半的时间则是给这些账号做视频。

此前我的工作流程大概是这样的：

    找对标 → 下载视频 → 提取文案 → 文案清洗 → 文案二创 → 配音  
    → 剪气口 → 剪模板 → 配画面 → 配字幕 → 配 BGM → 导出 → 发布  
    
用到的工具覆盖了 CR-Tubeget、CR-Videomate、AutoCut、迅捷视频转文字、剪映、易媒助手。

每天每个账号发一个视频，我需要工作五个小时以上在这里。

Vibe coding 出来之后，我做了一件事情：我把上面整个流程做到了一个工作台里，这个工作台我称之为「掌镜使」。

后来复盘下来，我发现这件事最有价值的地方，已经不只是“我用 AI 写了一个软件”这件事本身了。

更重要的是，我把自己每天重复五小时的工作，拆成了可执行、可排队、可恢复、可追踪的流程。

说白了，我做出来的东西，已经从一个单点工具，慢慢变成了一条短视频自动化生产流水线。

#  项目立项拆解

对于一个没有代码背景、没有项目开发背景的小白来说，一次性把整个项目完成是不可能的。

所以我一开始没有直接冲着“全能软件”去。

我先做的是一件很笨但很有效的事：把我的真实工作流拆成几个可以独立交付的模块：

  1. 对标采集：采集爆款视频的链接； 
  2. 对标处理：把对标视频的文案提取并清洗筛选； 
  3. 文案二创：把爆款转换成自己的风格，一是去重，二是有自己的身份标识； 
  4. 视频剪辑：把口播、画面、字幕、BGM 合成为成片； 
  5. 视频发布：把生成好的视频按账号、平台、时间发布出去； 
  6. 账号管理：同步私信、管理作品、清理低效内容。 

如果用一张流程图来讲，它大概是这样：

    对标账号 / 视频链接  
            ↓  
    视频采集与下载  
            ↓  
    ASR 提取文案  
            ↓  
    LLM 清洗 / 过滤 / 适配审查  
            ↓  
    文案二创与标题生成  
            ↓  
    TTS 配音 + 自动分段  
            ↓  
    素材库随机匹配 + FFmpeg 合成  
            ↓  
    封面 / 字幕 / BGM  
            ↓  
    MediaPush 发布队列  
            ↓  
    账号发布 / 私信同步 / 低效作品清理  
    
这也是我第一次比较深刻地理解“产品经理思维”到底是什么。

![](/images/claudecode-codex-video-automation/img-02.png)

以前我以为产品经理思维可能是脑子里有一个很大的产品愿景。

这个项目做下来，我反而觉得，它更像是把一个复杂流程拆成模块，定义每个模块的输入、处理逻辑和输出，再让它们之间可以稳定衔接。

我后来给这个系统做了一张模块表：
![](/images/claudecode-codex-video-automation/img-03.png)

这张表对我很重要，因为它让我从“想到哪做哪”，变成了“每个模块都要有边界、有状态、有结果”。

#  技术环境和依赖

虽然我是一个非科班出身的人，但这个项目做到后面，我也慢慢意识到：一个工具要变成真正的生产力，技术选型不能只看“能不能实现”，还要看“能不能本地跑、能不能打包、能不能给非开发环境使用”。

所以这个项目最后大概形成了四类依赖：

  1. 桌面端：Windows + PyQt5，用来做本地工作台界面； 
  2. 音视频处理：FFmpeg + pydub，负责裁剪、拼接、混音、字幕烧录、封面插入； 
  3. AI 能力：火山引擎 TTS / ASR、faster-whisper、本地或云端 LLM； 
  4. 自动化能力：yt-dlp、浏览器 Cookie / Profile、发布队列，用来处理采集、下载和发布。 

开发语言主要是 Python，打包用 PyInstaller，项目里内置了 FFmpeg，这样打包后的 Windows
客户端不需要用户再单独安装音视频环境。

这点看起来很小，但对一个自用工具能不能长期用非常关键。

如果每次换一台电脑都要重新配一堆依赖，那这个工作台本身就会变成新的麻烦。

#  项目开发

##  阶段一：视频混剪功能

使用工具：ClaudeCode、Codex、火山引擎 TTS、FFmpeg

我最先做的是视频剪辑工作台。

这个工作台其实早在 2020 年我做电商的时候就想做。

鲁班电商时代，甚至是现在的短视频电商时代，电商短视频的结构是很有逻辑性的：痛点、卖点、场景、促销等模块的排列组合。

也就是说，一个电商视频大致可以分为几个固定的模块。剪辑师要做的工作，是把口播录制好，把每个模块对应的视频素材放进去，然后配 BGM
和字幕，一个片子就出来了。

剪过电商短视频的人都知道，通常一个产品的每个分类下是会有很多素材的，而电商短视频付费跑千川，需要大量的素材去测。

注意这里的词：大量。

所以通常来讲，电商短视频的要求跟影视作品不一样，不会要求 100 分，而是满足七八十分就足矣。当然，我指的是混剪，真人出镜、一镜到底的不在这个范畴里。

所以我干的第一件事情，是先把我的想法雏形告诉 ClaudeCode。在一系列沟通之后，第一份 PRD 出来了。

![Image](/images/claudecode-codex-video-automation/img-05.png)

按照这个 PRD 文档，ClaudeCode 帮我做出了第一版。

![Image](/images/claudecode-codex-video-automation/img-06.png)

它第一版的使用逻辑是这样的：

  1. 我输入一段改好的文案，调用火山引擎 TTS，生成一段音频； 
  2. 我可以在音频上打点标记分段，比如一个 26 秒的音频，我边听边标记，可能会根据痛点、卖点、场景、促销被分成 5 + 8 + 8 + 7； 
  3. 分好段后，我会给每一段匹配素材文件夹，每个文件夹里的素材都是分类好的； 
  4. 设置 BGM、字幕参数、生成数量、输出参数。 

![](/images/claudecode-codex-video-automation/img-07.png)
整个操作就结束了。

在生成视频的时候，它会随机从素材文件夹里拉一个素材到时间线上。这就意味着，只要素材库里的视频足够多，一条爆款文案就能生成 N 多条不重复的视频。

这里面一开始看起来只是“随机选素材”，但真正做起来后，我发现技术核心在音视频链路的稳定性：

  1. 每段素材要按音频分段时长裁剪； 
  2. 多段视频要拼接成完整视频； 
  3. TTS 和 BGM 要混音，不能出现只有人声没有 BGM 的情况； 
  4. 字幕要根据时间戳生成并烧录； 
  5. 最后还要插入封面，保证导出的视频首帧可控。 

我一开始只觉得“能合出来就行”，后面才发现 FFmpeg 的坑非常多。

比如 BGM
混合失败，后来定位到是音频编码、采样率、中文路径等问题；又比如音频末尾被截掉，是因为响度归一化滤镜有缓冲延迟；再比如封面插入失败，是因为视频段和封面段的音频参数不一致。

这些问题修完之后，我才真正明白：视频工具表面上看的是界面按钮，底层拼的其实是音视频管线。

素材、音频、字幕、封面这些东西能不能稳定地合在一起，才决定它到底能不能长期用。

这是 V1.0 上线，中间遇到了许多 BUG 调试，这里不展开讲。

![](/images/claudecode-codex-video-automation/img-08.png)

V2.0 我做了一件事情，就是在文案分段的地方，加了自动分段功能和按时间分段功能。

自动分段是什么意思呢？就是按原始文案的句号分段。

因为绝大多数时候，我们都是以句号为单位分模块的。其实我当时想过调用大模型来辅助分段，但是对我当前阶段来讲，用不上，所以这个功能我没加进去。

这也是我后来比较重要的一个产品判断：能用 AI 做，不代表第一时间就要用 AI 做。

如果规则能解决 80% 的场景，就先用规则。AI 应该去解决规则解决不了的问题，别为了显得高级到处硬塞。

至此，视频混剪工作台我已经做出来了。

##  阶段二：视频发布功能

使用工具：ClaudeCode、浏览器自动化、账号 Profile

每天要管理 50 个账号的发布，是一件很费劲的事情。

目前网上有很多矩阵管理软件，比如易媒助手、蚁小二，还有新榜出的小豆芽，这些我都用过，最满意的还是易媒助手。

所以我在做视频发布工作台的时候，一开始先研究了一下这类矩阵管理工具的实现方式。

后来发现，本质上，矩阵管理软件是一个浏览器管理软件。

也就是说，在一个界面背后，其实是单独开了很多浏览器，每个浏览器都登录着一个账号，有 Cookie，有独立 Profile，所以会保持长期在线状态。

同样的流程，我跟 ClaudeCode 说了需求，出了 PRD 文档，然后开干。

![Image](/images/claudecode-codex-video-automation/img-09.jpg)

这个功能逻辑我也大概讲一下：

  1. 可以支持增删账号，支持账号分组。比如一个手机号注册了抖音、快手、小红书、视频号、B 站甚至 TK，就可以把它们分在一个组里，一个视频可以按组发布到这个组内的所有账号里； 
  2. 每个账号背后都是一个浏览器 Profile，前端不展示发布过程； 
  3. 发布的时候，它没有走平台开放 API 这条路，核心逻辑是模拟我们手动发布视频的过程。 

这里做着做着我才发现，点击上传按钮其实很简单，各种异常状态才折磨人。

我后来把它拆成了几个产品问题：

** 问题 1：Cookie 失效导致登录失败怎么办？  **

解决方案：设计重试机制。如果因为登录态失效导致发布失败，就在重试时弹出有头浏览器，方便使用者扫码登录。登录成功后继续后面的发布流程。

如果有头浏览器在一分钟内没有被用户响应，则可能意味着用户不在电脑面前，自动关闭，跳过该任务，继续下一个视频发布。

** 问题 2：发布过程中出现“自主声明”弹窗怎么办？  **

有的视频上传后会提示自主声明，有的不会。如果没有处理，这个弹窗会挡住后续发布流程。

解决方案：在发布流程里主动检测并处理自主声明，默认选择“无需添加自主声明”，避免弹窗阻碍流程进行。

** 问题 3：发布时间怎么自动排？  **

我目前每个账号每天三更，定时在早上 7 点、中午 12 点、晚上 18 点。

所以我给每个账号加了发布日志。程序发布视频时，会先读一下日志，看看它最后一条发布的时间是什么时候。如果早上 7 点已经发布过了，那么新发布的一条就排到中午
12 点，以此类推。

![](/images/claudecode-codex-video-automation/img-10.png)

这里如果只写“定时发布”四个字，就把事情说轻了。

它背后其实需要有一个发布日历模型。

它要知道今天哪些槽位已经被占了，哪些槽位还可用，平台要求提前多久定时，过期槽位不能再排。

** 问题 4：发布显示成功，但后台没有作品怎么办？  **

这个问题很坑。

有时候页面上会出现类似“已发布”的状态，但实际是风控页、二次验证页，或者视频还在上传中。以前如果只靠页面文案判断，很容易出现“系统显示成功，后台没有作品”的假成功。

解决方案：重新定义“成功”的判定标准。

所以后面我把成功判定收紧了：不能看到某个成功文案就算成功，还要检测二次验证、安全验证、验证码、操作频繁、发布失败、上传任务是否真正结束。

一旦阻塞，就截图、记录日志，并标记失败，后续允许人工核对和重试。

![](/images/claudecode-codex-video-automation/img-11.png)

这是我在这个阶段最大的收获。

产品里的“成功”，最后还是要落到用户有没有真正得到结果。

##  阶段三：对标采集功能

使用工具：Codex、yt-dlp、CR-Tubeget 思路借鉴、faster-whisper、LLM

短视频矩阵的内容生产，本质上离不开对标研究。

照搬这件事其实没什么意义，真正有用的是筛选结构、提炼表达，再结合自己的人设做二次创作。

在做这个工作台的时候，我的 ClaudeCode 账号被封禁了。此前我一直是 ClaudeCode 的忠实用户，而四月份 Codex
开始在外网疯传，于是我果断开通了 Codex。

真香。

依旧是此前的流程，我文章开头讲了，对标采集我大体分了四个步骤：

  1. 找对标； 
  2. 视频链接展开； 
  3. 视频下载； 
  4. 文案提取和清洗。 

找对标这个事情，我一直没有交给工具。

因为我觉得这个是要人为判断的，而且这个活对我来讲很省时间。毕竟我对标的不是某个视频，而是某个账号。也就是说，他整个账号的视频，都可以是我的爆款素材库。

所以我给 Codex 大概讲的是：

  1. 我把一个抖音账号的主页链接给到工具后，它把整个账号的视频链接都抓下来； 
  2. 这些链接抓下来之后，要把视频下载到本地； 
  3. 下载到本地之后，要把文案提取出来； 
  4. 文案提出来之后，会有一些断句错误、错别字，需要调用 LLM，对文案进行清洗。 

也就是说，表面上是“输入主页链接，输出文案库”，实际上中间有四个子功能要实现。

在实现链接展开和视频下载的时候，因为需要 Cookie，容易触发平台风控，所以我研究了一下 CR-Tubeget 这类下载工具的实现思路。

最后的方案是：常规下载走 yt-dlp，抖音场景下增加一个 fallback 方案，用已有浏览器 Cookie / 下载组件来提升成功率。

这个地方给我的启发是：做产品的时候，没必要所有能力都从零发明一遍。

如果已有工具已经证明某条路径可行，我更应该做的是理解它到底解决了什么问题，然后把这个能力抽象成自己系统里的一环。

到了文案提取阶段，我此前是用一个专门的视频转文字软件，叫迅捷语音助手，也是付费软件。

我跟 Codex 聊这个需求的时候，它给我的方案是：现在有现成的 ASR 小模型 faster-whisper，模型不大，可以本地跑，也可以从
Hugging Face 下载。

(吾去，汝不早言。)

于是功能三也顺利做出来了。

功能四就很简单了。我因为开了火山方舟的 coding plan，用来给我干苦活脏活的，所以直接调用它家的大模型来干就行。

告诉它：这是本地 ASR 识别出来的文案，可能有错别字、断句错误、标点错误，请结合上下文修改，但不要改变原意。

至此，对标采集工作台也搞出来了：输入一个主页链接，采集所有作品并提取文案。

但很快我发现，能采集不等于能用。

某个视频可能跟时效性有关，比如讲过年、讲中秋；也可能跟作者本人经历有关；也可能跟我的人设不符，比如对方说自己是女性，或者讲的是某段不可迁移的个人经历。

所以我在文案清洗前加了一个过滤器，让 LLM 先做适配审查：

  1. 这个视频是否有强时效性； 
  2. 放在今天讲是否还适合； 
  3. 是否包含作者本人不可迁移的经历； 
  4. 是否跟我的人设冲突； 
  5. 是否需要轻微改写，还是直接拒绝入库。 

如果不符合，就直接标记 rejected，不进入后面的清洗和二创流程。

![](/images/claudecode-codex-video-automation/img-12.png)

这个过滤器后来非常关键。

它主要帮我挡掉的，其实不是时间成本。

更要命的是那些不该进入生产线的错误内容，它能提前拦住一部分。

一条自动化流水线，跑得慢一点其实还能接受。

最可怕的是，把不该生产的东西高速生产出来。

##  阶段四：文案二创功能

使用工具：Codex、LLM、人设提示词、结构化 JSON 输出

在没有 AI 的时候，文案二创是一个很费脑力和时间的事情。

后来 ChatGPT 出来后，我也用它二创过，但很多时候不能直接达到能用的水平，还是得自己手动改。

即便放在今天，让 AI 创作还是会有很浓的 AI 味。

我做的事情是“蒸馏自己”。

那时候网上很流行蒸馏这个词，我也第一时间把自己过往所有的爆款文案打了个包，然后丢给
Codex，让它帮我提炼我的爆款文案写作方法，再植入我的人设、我的语气、我的口头禅等等信息。

![Image](/images/claudecode-codex-video-automation/img-13.png)

第一版是实现了单篇文案的二创。

但如果要进入生产状态，单篇是不够的。

所以后面我加了批量队列：导入一批文案，系统依次进行 LLM 改写、TTS、分段、合成、封面插入、重命名和派发。

这里有一个很重要的细节：LLM 节点不能只返回一段文案。

它必须返回结构化 JSON：

    {  
    "rewritten":"二创后的完整文案",  
    "title":"视频标题",  
    "cover_text":"封面重点词"  
    }  
    
其中：

  1. ` rewritten  ` 用于 TTS 生成音频； 
  2. ` title  ` 用于视频文件命名，后续发布时也作为发布标题； 
  3. ` cover_text  ` 用于生成封面上的关键词。 

![](/images/claudecode-codex-video-automation/img-14.png)

这个设计看起来只是一个字段变化，但它本质上是把“文案生成”变成了“视频生产元数据生成”。

也就是说，AI 在这里已经不只是写一段话了，它开始给后续视频合成和发布流程提供结构化数据。

中间也踩过坑。

比如有一次 LLM 明明返回了爆款标题，但封面标题永远是文案第一句硬切 12 字。

后来排查发现，是解析 JSON 之前先把文本清洗了一遍，清洗函数只保留了 rewritten 字段，直接把 title 字段丢掉了。

这个 bug 对我很有启发：当工作流开始依赖结构化数据之后，提示词当然重要，解析链路也一样重要。

AI 返回了不代表系统拿到了，系统拿到了不代表后续模块用对了。

##  阶段五：功能串联

在完成了上述四个功能后，要做的就是把它们串联起来。

![](/images/claudecode-codex-video-automation/img-15.png)

这种感觉就像是我招了四个实习生，我培养了他们独立的技能，但他们每个人现在都是给我单独汇报。

我需要把采集的文案丢给二创，把二创的文案丢给混剪，把混剪的视频丢给发布。

还是很麻烦。

是时候把他们串起来了。

我继续让 Codex 帮我把这些功能串在了一起。

但为了方便管理，我没有把所有东西都塞进同一个 UI 界面。

最后我把它做成了几个工作台，中间通过文件、队列和状态衔接。

![Image](/images/claudecode-codex-video-automation/img-16.png)
![Image](/images/claudecode-codex-video-automation/img-17.png)

这个工作台实现了以下几个功能：

  1. 输入一个主页链接，采集所有作品链接，进行文案提取、清洗、过滤； 
  2. 处理好的原始文案自动进入批量自动化工作台，进行文案二创、TTS、视频混剪、封面匹配、标题生成； 
  3. 最终生成的视频推送到发布工作台，由发布系统自动发布到各个平台账号上。 

这里我专门做了一个 MediaPush inbox 的设计。

简单说，视频生成模块不直接控制发布模块。

它只负责把一批生成好的视频移动到一个 inbox 目录，并写入一个  ` manifest.json  ` 。

这个 manifest 里记录批次 ID、计划发布时间、视频文件列表等信息。

发布工作台只需要监听 inbox，一旦发现新批次，就把它加入发布队列。

这个设计的好处是：视频生成和视频发布解耦了。

生成模块只管生产成片，发布模块只管按规则发布。哪怕发布模块挂了，已经生成的视频和批次信息也不会丢；哪怕生成模块继续跑，也不会直接影响发布系统。

这也是我后来越来越喜欢的一个产品设计思路：复杂系统不要硬耦合，用中间状态和明确协议衔接。

封面风格我做了背景图加文案的设计。

让二创 LLM 节点输出 JSON 后，系统拿到  ` title  ` 和  ` cover_text  ` ，再通过 FFmpeg
或图片生成逻辑把它们变成视频首帧封面。

![Image](/images/claudecode-codex-video-automation/img-18.png)

到这个阶段，这个工具已经不只是“帮我剪视频”了。

它开始像一个真正的工作台：上游负责原料入库，中游负责内容生产，下游负责分发和反馈。

##  阶段六：附属功能优化

以上的功能，已经把我此前每天要干五个小时的活替代掉了。

我要做的事情，只是找好对标，然后把链接丢给它，后面的流程自动跑。

但是对我来讲，我还有一个很重要的需求，就是私信管理。

做账号嘛，当然是要奔着变现去啦。每天有谁后台私信我了，我得知道。

于是我继续让 Codex 帮我加了私信管理功能。

这个功能的底层逻辑，是定时打开对应账号的浏览器
Profile，进入私信界面查看有没有新增私信。如果有，就同步到前端界面。我双击后就能进去互动，加到私域平台转化变现。

后面，我又新增了低效作品清理功能。

也是通过浏览器自动化去扫描过去 3 天发布的视频。如果低于 1000 播放、低于 30 点赞，或者违规了，就进入待清理列表，必要时执行作品删除。

![Image](/images/claudecode-codex-video-automation/img-19.png)

这个阶段我开始意识到：视频发布出去以后，内容生产这件事还没结束。

发布之后，还有互动、私信、转化、低效作品清理。

如果只解决生产效率，那它只是一个生产工具；如果连发布后的运营动作也能接住，它才更像一个账号工作台。

#  最难的是稳定地跑完

这个项目做下来，我最大的感受是：

让 AI 生成一段文案，让 FFmpeg 合成一个视频，这些单点能力都能慢慢解决。

真正麻烦的是，让整条链路在无人值守时稳定跑完。

所以后面我花了很多精力做这些看起来“不性感”的东西：

  1. 队列状态保存：程序关了再打开，知道哪些任务完成了，哪些任务失败了； 
  2. 失败重试：LLM、TTS、合成、发布任何一步失败，都不能把整批任务拖死； 
  3. 日志记录：出错后必须知道错在哪里，不能只给我看“失败”两个字； 
  4. 发布槽位管理：每个账号每天早中晚发布，不重复、不漏发； 
  5. 异常截图：遇到风控、验证码、二次验证时，能留下现场； 
  6. 人工复核入口：自动化处理不了的事情，要能交还给人。 

这也是我后来对“产品化”的理解。

一个功能能跑，只是 1.0。

能稳定跑、失败可恢复、结果可追踪、异常可人工接管，到了这一步，我才觉得它真的进入了生产状态。

![](/images/claudecode-codex-video-automation/img-20.png)

#  成本和结果

到这里，我这个项目就完成得七七八八了。

此前考虑过把这个软件卖给一些同样做矩阵或者做电商的人用，所以我还对接了激活码系统。

但后来发现自己不擅长商业化，也没这块的资源，便没有去推广它。

主要是精力有限，每天 coding 不能自拔。

因为是自用，所以 UI 也长得比较朴素，不过这都是小问题。

毕竟我此前每天干五小时，也就只能满足每个账号每天更一个视频；现如今，每天每个账号供应 3 条视频，只花我点击一下的时间。

我都不知道效率翻了多少倍。

成本也就是 LLM 和 TTS 的成本。

LLM 因为我有 coding plan，每个月 200；TTS 则按需付费，28 元 / 十万字。照我这类视频长度，平均一个视频 500
字左右，一条视频成本大概一毛钱，非常能接受。

![](/images/claudecode-codex-video-automation/img-21.png)

#  最后复盘

如果重新总结这个项目，我觉得它给我最大的收获有三个：

第一，需求这东西，靠想象很难想准，还是要从每天重复到想吐的工作里长出来。

我之所以能把这个东西做出来，技术当然帮了很多忙，但核心原因其实还是我太熟悉这个流程。

哪里耗时、哪里容易错、哪里必须人工判断、哪里可以自动化，我每天都在亲身经历。

第二，AI 编程最适合解决“明确流程里的明确问题”。

如果我一开始只说“帮我做一个短视频自动化软件”，大概率会做崩。但我把它拆成采集、清洗、二创、TTS、混剪、发布、私信管理，每个模块单独定义输入和输出，AI
就能一步步帮我实现。

第三，产品经理思维这件事，我以前可能会理解成画大饼。

现在我更愿意把它理解成：设计系统边界。

哪些事情交给规则，哪些事情交给 AI；哪些模块直接调用，哪些模块用文件和队列衔接；哪些失败自动重试，哪些失败必须交给人。

这些选择加起来，才让一个自用脚本慢慢变成了一个真正能跑的工作台。

现在再回头看，「掌镜使」对我来说已经不止是一个软件。

它更像是我把自己的短视频运营经验、内容生产方法、账号管理流程，全部压缩进了一套可以自动执行的系统里。

以前是我在工具之间搬砖，现在是工具在我的流程里干活。
