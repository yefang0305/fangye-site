![](/images/claudecode-codex-subagent-workflow/img-01.png)

最近发现了一套很有意思的工作流。

![](/images/claudecode-codex-subagent-workflow/img-02.png)

表面上看，它是一个  ** Codex + Claude Code + DeepSeek（或者其他便宜的大模型）  ** 的省 token 方案。

但真跑顺之后，我发现它真正解决的问题，不只是省钱，而是把我以前在多个 AI 之间来回调度的那层项目经理劳动，封装进了 Codex 的执行协议里。

以前我已经会用多模型分工：

Codex 负责想清楚问题，便宜模型负责干苦活。但中间所有调度，都是我手动做的。

![飞书文档 -
图片](/images/claudecode-codex-subagent-workflow/img-03.jpg)

现在这套工作流把 Claude Code CLI 接进 Codex 子代理执行链路，让 Codex 继续当
leader，负责理解需求、拆任务、审核、打回和最终交付；Claude Code/DeepSeek 负责执行层的重活，比如读代码、改文件、跑测试、看日志。

一句话概括：

我不再手动调度多个模型，而是让 Codex 自己去调度执行层。

* * *

##  一、 这是什么

这个项目叫  codex_with_cc  ，它做的事情很明确：

把一套  Codex 主线程 -> Codex 子代理 -> Claude Code CLI  的委派工作流，集成到你的目标项目里。

它不是让 Codex 自己变成 Claude Code，也不是简单给 Codex 换个 DeepSeek 后端。

更准确地说，它是让 Codex 当调度层，在合适的时候通过子代理去调用你本机的 Claude Code CLI。

至于 Claude Code CLI 背后用什么模型，取决于你本机配置。

如果你通过 CC Switch 把 Claude Code 后端切到 DeepSeek，那么真正读代码、改文件、跑测试的执行层，就可以交给 DeepSeek
来干。

> 其实简单来讲就是，Codex聪明，所以让它当你的总监；
>
> 国内大模型便宜，所以让它干“脏活累活”；
>
> 以前你是分别去管他们，现在你只需要管Codex，让他去管下面的工人了

所以这套东西的分工是：

  * 我：提目标、定标准、拍板。 
  * Codex 主线程：理解需求、拆任务、派工、审核、打回、汇总。 
  * Codex 子代理：接收具体任务，调用委派脚本。 
  * Claude Code CLI：执行分析、修改、验证。 
  * DeepSeek：作为便宜执行后端，承接高 token 的重活。 

这套工作流最核心的价值是“让 Codex 继续当大脑，同时把执行层调度自动化”。

![](/images/claudecode-codex-subagent-workflow/img-04.png)

##  二、 它解决了我什么问题

我原来的模式其实已经很成熟了。

遇到复杂问题时，我会先和 Codex 把问题想清楚，让它帮我拆方向、定策略、找风险。

然后，为了不把 Codex 额度烧在大量体力活上，我会把一些具体任务拆给便宜模型，比如查调用链、读模块、分析日志、补测试、对比方案。

便宜模型给出结果之后，我再拿回来让 Codex 判断：哪个靠谱，哪个有问题，哪里需要返工，最后怎么合并成一个可执行结论。

中间有大量工作不是模型在做，而是我在做：

  * 手动拆任务给不同模型 
  * 手动维护每个任务的上下文 
  * 手动复制粘贴代码片段、日志、分析结果 
  * 手动把便宜模型的结果拿回来给 Codex 判断 
  * 手动组织返工 
  * 手动把多份结果合成一个可执行结论 

说白了，我是在多个 AI 之间当传话筒、项目经理和返工催办员。

而  codex_with_cc
解决的，就是这层“人工调度劳动”。它没有替代我的核心判断，也没有替代我做项目的能力。我的价值仍然是知道目标是什么、质量标准是什么、优先级是什么、最终该选哪个方案。它替代的是我在多个模型之间搬砖。

更准确地说：

> 是替代我在多个模型之间复制上下文、转述结果、催返工、做汇总。

“Codex 适合当脑子，便宜模型适合当劳动力”。

这套工作流只是把这份经验，封装成了一条更自动化的流水线。

##  ![飞书文档 -

以前的链路大概是这样：

  *   *   *   *   *   *   *   *   *   * 

    我 -> 和 Codex 想清楚问题我 -> 把任务拆给便宜模型我 -> 复制上下文、代码片段、报错日志便宜模型 -> 给出分析或修改建议我 -> 把结果拿回给 Codex 判断Codex -> 发现问题，要求返工我 -> 再把返工要求转述给便宜模型便宜模型 -> 重新分析我 -> 再拿回来给 Codex我 -> 最后手动汇总

` 这一套跑下来人很累的，得一直盯着电脑。尤其是任务一复杂，复制上下文、同步状态、转述返工意见、合并多份结果，都会变成非常烦的机械劳动。  `

这才是它真正香的地方：不是单纯省 token，而是我终于不用在多个 AI 之间当搬运工了。

##  四、 它的工作逻辑是啥

这套工作流的完整链路是：

` 你提出复杂任务  
-> Codex 主线程理解、拆分、审核    
-> Codex 子代理接到具体任务    
-> 子代理调用 delegate_to_claude.ps1    
-> 脚本启动或续用你的 Claude Code CLI session    
-> Claude Code 执行具体分析、修改或验证    
-> 如果通过 CC Switch 切到 DeepSeek，执行层就由 DeepSeek 承接    
-> 结果回到 Codex 主线程做判断、整合、返工或交付  `

` ![飞书文档 -
图片](/images/claudecode-codex-subagent-workflow/img-07.png)  
`

这里有几个关键点。

第一，主 Codex 线程不能直接跑 C  laude  ，也不能直接跑委派脚本。真正的 Claude Code 委派必须由 Codex
子代理执行，并且子代理调用前要设置：  

  * 

    CODEX_CLAUDE_CHILD_THREAD=1

这个限制很重要。它保证主线程和执  行层之间有边界：

  * 主线程负责规划、审核、裁决；子代理负责承接任务； 

  * Claude Code CLI 负责执行； 

  * 最后结果回到主线程。这样链路不会乱，责任也不会糊。 

第二，它有 Claude session 复用池。

每个任务都从零读一遍项目，是  大项目里最浪费 token 的事情之一  。这个工作流提供了几种 session 模式，比如  PrimaryReuse
、  PrimaryAnchor  、  ParallelPool  ，目的就是尽量让相似任务复用上下文，减少重复阅读和重复建模。

>
> （举个例子来解释：假设你是包工头，以前是每来一个工人，你都要重新给他讲一遍：这个工地在哪里，图纸怎么看，水电在哪，哪个墙不能动，之前出了什么问题。讲三个人，就讲三遍。有
> session 复用之后，就像留下几个已经熟悉工地的工人。下次再派相似任务时，优先找已经听过背景、知道现场情况的人继续干，不用每次从零培训。
>
>
> 所以PrimaryReuse像固定找一个熟悉项目的主力工人连续干活；PrimaryAnchor像先安排一个人把工地情况摸清楚，后面一批任务都以他的上下文为参照。ParallelPool像养一批已经熟悉项目的工人，适合分头干互不冲突的活。）

第三，它会落审计产物。

每次委派默认会在  .codex/claude-delegate  下面生成一批文件，比如：

  *   *   *   *   *   *   * 

    config_<RunId>.jsonstatus_<RunId>.jsonprompt_<RunId>.mdstream_<RunId>.jsonltrace_<RunId>.logclaude_<RunId>.mdsession-pools/<SessionKey>.json

` 这些产物能让你回头查：任务怎么发出去的、用了哪个 session、有没有 resume、输出是什么、链路有没有断。不是 AI
说“我干了”，而是过程能回看。  `

第四，Claude worker 的输出也被规范了。它需要按固定结构交付：

> Process Log
>
> #  它怎么干的。比如先看了哪些文件，发现了什么问题，怎么定位的，中间有没有遇到阻塞。相当于“工作过程记录”。
>
>  
>
>
> Summary
>
> #  它干了什么。用几句话总结本次任务的核心结果。相当于“本次工作摘要”。
>
>  
>
>
> Changed Files
>
> #  它改了哪些文件。如果只是分析，没有改代码，就写没有改文件。相当于“改动清单”。
>
>  
>
>
> Verification
>
> #  它怎么验证的。相当于“验收凭证”。
>
>  
>
>
> Final Result
>
> #  这次任务最终算不算完成。相当于“最终结论”。
>
>  
>
>
> Risks Or Follow-ups
>
> 还有什么风险或后续要注意的事。相当于“遗留问题和提醒”。

` 这套格式就是让执行层别只说“我干完了”，而是必须交代：怎么干的、干了什么、改了哪里、怎么证明没问题、最后结论是什么、还有什么坑。  
`

这对 Codex 主线程审核非常重要。因为执行层如果只说“完成了”，你根本不知道它改了什么、测了什么、有没有风险。

固定报告格式之后，Codex 更容易判断这个结果能不能收，不能收就打回。

另外，它内部还做了任务指纹、租约锁、会话回收这些工程化细节，避免多个子代理并行时乱抢 session、状态不清、任务卡死没人管。

##  五、 怎么安装和使用

前置条件很简单：

  1. [ 安装 Claude Code CLI（之前的文章里有些） ](https://mp.weixin.qq.com/s?__biz=MzcwODI5MjA5NQ==&mid=2247483745&idx=2&sn=eb1293121d5cbee31ec9d3902b97da56&scene=21#wechat_redirect) 。 
  2. [ 安装 CC Switch。 ](https://mp.weixin.qq.com/s?__biz=MzcwODI5MjA5NQ==&mid=2247483745&idx=1&sn=15b37f663e885849a3e8390131b37aaa&scene=21#wechat_redirect)
  3. 在 CC Switch 里把 Claude Code 的后端 API 切到 DeepSeek（或者其他便宜的大模型）。 
  4. 准备一个你想接入这套工作流的目标项目。 
  5. 打开 Codex。 

然后在目标项目里，把这句话发给 Codex：

> 请把 https://github.com/yefang0305/codex-claude-delegation-workflow
> 调度子代理工作流集成或更新到当前项目。

接入之后，最重要的不是命令，而是你怎么使唤 Codex。不要再对它说“帮我把这个大需求做完”，这种说法容易让主线程一个人从头硬扛到底。更好的说法是：

> 你负责拆解、派工、审核和最终交付。子代理负责执行。
>
> 结果不合格就返工，直到符合我的要求。

如果是大任务拆分，可以这样说：

> 你先阅读项目，拆成 3 个互不冲突的实现任务，分别交给子代理处理。每个子代理必须给出变更文件、验证命令和风险说明。你最后统一
> review、整合，并跑最终验证。

如果  是多方案比较，可以这样说：

> 请委派三个子代理分别分析这个问题。
>
> 每个子代理给出方案、风险、成本和验证依据。
>
> 对于矛盾点，你要打回让他们重新验证。
>
> 最后汇总一份可执行方案。

`  
`

` 如果是实现加审查，可以这样说：  `

> 安排一个子代理实现 xxx，再安排另一个子代理专门做代码审查和边界情况攻击。
>
> 你负责判断 review 是否成立。
>
> 成立就打回修改，不成立就说明理由。
>
> 最后统一交付并跑验证。  
>

如果是长上下文探索，可以这样说：

> 请把项目里的 xxx 模块交给子代理做深度调查。
>
> 要求输出调用链、关键文件、潜在风险和建议修改点。
>
> 你只保留结论，别把所有噪音塞回主上下文。

这类提示词的共同点很清楚：Codex 主线程不是苦力，Codex 主线程是负责人。它要拆任务、派工、验收、打回和交付。

##  六、 注意事项

1\. 这套工作流适合那些“单点不难，但整体很吃上下文”的任务，比如大范围代码阅读、模块梳理、多文件实现、测试修复、多方案比较、代码
review、迁移重构、补测试、查调用链、长上下文探索。

任务越大，主线程越容易被代码、日志和中间判断淹没，这套分工就越有价值。

2\. 但它不适合所有场景。如果只是改一两行代码，直接让 Codex
主线程改就行，没必要开子代理、写任务文件、跑委派链路。如果需求还没想清楚，比如产品边界还在变、业务规则还没定、交互细节需要你实时拍板，也不适合急着委派。应该先在主线程里把问题想清楚，再把明确的执行任务派出去。

3\.
另外，如果多个子代理会同时改同一批文件，也要谨慎并行。并行的前提不是人多，而是边界清楚。任务范围能拆开，才适合并行；范围拆不开，就应该串行执行，不然很容易互相踩。

4\. 最后再强调一次：它适合替你调度执行，不适合替你决定方向。方向、标准、优先级和最终取舍，还是你来定。

所以这套工作流最爽的地方，不只是省 token。

省 token 很爽，但更重要的是，它把我原来在 Codex、Claude Code、DeepSeek 之间手动调度的项目经理劳动，制度化了。

以前我是人工调度员。现在我只需要给 Codex 这个包工头下任务，要结果。

这才是它最  香的地方。
