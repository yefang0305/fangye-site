##  问题一：Agent 和 Chatbot、Workflow 的本质区别是什么？

先说前提：这里讲的是典型形态，不是说现实产品只能长成这样。现在很多 Chatbot 也能接工具，Workflow
里也可以塞条件分支和循环，但看它们的“控制权”在哪里，区别还是很明显。

类型  |  本质  |  控制流程   
---|---|---  
Chatbot  |  单轮或者多轮应答，输出就是终点，不在循环里自驱改变外部世界，本质上是应答  |  人问，模型答   
Workflow  |  工作流，路径是人为编排好的，大模型只是其中的一环，本质上是编排  |  人预先设计流程   
Agent  |  模型在循环里自主决定下一步动作，直到完成任务为止，本质是模型在 Harness、权限和策略边界内决定控制流程  |  模型决定下一步   
  
** 这三个东西不是一个物种，越往 Agent 端靠，能力上限越高，可控性越差。  **

##  问题二：ReAct、Planning、Reflection、Memory 这几个 Agent 范式，分别解决什么问题？

###  ReAct：动手能力

` Reasoning + Acting  ` ，推理和行动交替，解决的问题是让模型不只是想，而是能边想边动手。

早期的大模型只能在脑子里推理，碰不到外部世界，  ` ReAct  ` 模式是把“推理一步 → 采取行动 → 观察结果 → 推理下一步”串成了一个循环。

简而言之，  ** ReAct 是让 Agent 能够思考、调工具、看结果、再思考，是 Agent 能用工具干活的基础模式，解决的是光会想不会做的问题。
**

###  Planning：计划能力

它解决的是任务太复杂、步骤太多时，不能走一步看一步，而是先有全局计划。

` ReAct  ` 是短视的，每次只想下一步，走一步算一步，一旦任务复杂了，容易走偏或者绕路；  ` Planning  `
是把大任务拆成子任务，排好顺序再去执行，中途可能还会根据情况调整计划。

简而言之，  ** Planning 解决的是复杂长任务怎么不迷路的问题。  **

###  Reflection：反思能力

它解决的问题是，Agent 会犯错，得让它能发现自己的错并且纠正，而不是一条路走到黑。

` Reflection  ` 是 Agent 回头审视自己产出或者执行过程，判断做得对不对、够不够好，不行就修正重来。

一句话解释，  ** Reflection 解决的是 Agent 怎么自我纠错、自我改进的问题。  **

###  Memory：记忆能力

更准确地说，模型本体没有跨任务、跨会话的记忆；你看到的“记得你”，通常是产品或者 Agent
系统在外面做了一层持久记忆。得给它挂一个，不然每次都失忆，记不住以前做了什么，也不记得用户是谁。

` Memory  ` 通常分两类：短期记忆和长期记忆。

  * 短期记忆：当下这个任务或者当下这个会话的上下文，记得是刚才做了什么、上一步输出了什么，让多步任务能够连贯。 
  * 长期记忆：跨任务保留的用户偏好、过去经验、之前学会的做法，让 Agent 越来越懂你，不用每次解释。 

###  四块拼图

这四个东西，其实是 Agent 能力逐步进阶的四块拼图：

  1. ` ReAct  ` 让 Agent 能边思考边用工具，这是地基，但是光会动手不够，复杂任务会迷路。 
  2. 所以有了  ` Planning  ` ，先规划，再执行，但是规划和执行都会出错。 
  3. 于是有了  ` Reflection  ` ，让它能自我发现错误并纠正。 
  4. 这前三个是针对单次任务内的，要让它跨任务积累、记住用户，就需要  ` Memory  ` 。 

简单说，  ** ReAct 解决会动的问题，Planning 解决不迷路的问题，Reflection 解决能纠错的问题，Memory 解决不失忆的问题。
**

##  问题三：Function Calling / Tool Use 的机制是什么？MCP 和它什么关系？

###  Function Calling / Tool Use 的机制是什么？

` Function Calling  ` 和  ` Tool Use  ` 基本是一回事，前者是 OpenAI
早期的叫法，后者是更为通用的说法，可以说就是一个东西的不同叫法。

它核心解决的是，大模型本身只会生成文字，不能真的去查知识库、调  ` API  ` 、发请求。而  ` Tool Use  `
就是给大模型一种能伸手勾到外部世界的机制。

大概机制是这样子的：

  1. 先把可以用的工具描述给模型：这个工具叫什么，是干啥的，需要哪些参数。 
  2. 模型在推理的时候，如果判断需要某个工具，它不会自己执行，而是输出一个结构化的  ` JSON  ` 请求：我要调用某个工具，参数是这些。 
  3. 真正执行工具的是外部程序，不是模型本身。外部程序拿到了模型的请求，去实际跑这个工具，拿到结果。 
  4. 把结果再递交给模型，模型基于结果继续推理或者生成下一步。 

** 模型自己不执行任何工具，它只负责调哪个、传什么参数，执行和拿结果是外部系统干的。  **

很多人认为模型自己去调用  ` API  ` ，其实不是。

一句话总结  ` Tool Use  ` 就是：  **
模型负责决定哪个工具、怎么传参数，外部系统负责真正执行并把结果喂回来，两边配合让模型能影响真实世界。  **

###  MCP 是什么，跟 Tool Use 什么关系？

` MCP  ` 不是  ` Tool Use  ` 的替代或者竞争，它是  ` Tool Use  `
的标准化连接层，两者是不同层面的东西，不矛盾，是配合的。

` Tool Use  ` 是模型能调用工具这个能力本身，但是它带来一个工程难题：每个工具怎么接进来？

如果没有标准，那就是  ` N  ` 个模型/Agent ×  ` M  ` 个工具 =  ` N×M  ` 种各写各的对接，乱七八糟。

` MCP  ` （全称是  ` Model Context Protocol  `
）解决的就是这个对接标准化的问题。它定义一套统一协议规定，工具/数据源按照这个协议把自己暴露出来（做成一个  ` MCP Server  ` ），任何支持
` MCP  ` 的 Agent 都能用同一种方式发现和调用它。它把  ` N×M  ` 变成了  ` N+M  ` 。

严谨一点说，  ` MCP  ` 不只是接工具，它还可以暴露资源、提示词这类上下文能力；也不是说所有  ` Tool Use  ` 都必须走  ` MCP
` 。你完全可以手写工具对接，只是工具多了、客户端多了之后，标准化这件事就会变得很香。

怎么理解呢，  ` Tool Use  ` 是电器能用电这个能力，  ` MCP  `
是统一的插座标准。有了标准插座，所有电器插任何插座都能好用，而不用为每个电器单独配接口。

所以它们之间的关系是：模型通过  ` Tool Use  ` 决定了“我要调用这个工具”，而这个工具是通过  ` MCP  `
这套标准协议来被接进来、被发现、被调用的。

** 一个是调用能力，一个是连接标准，合在一起工作。  **

##  问题四：Multi-Agent 在什么情况下值得用？什么情况下是过度设计？

我的默认立场是，  ** 能用单一 Agent 解决的，不要用 Multi-Agent。  **

多智能体并不是更高级，而是用更高的复杂度和成本去换某些特定的权益，所以它得先证明这个交换是划算的，而不是默认就该用。

###  什么情况下值得用？

  1. 任务能被清晰地拆解成“职责不同、互不重叠”的角色，并且每个角色需要不同的专长、不同的工具、不同的上下文。比如一个负责写代码、一个负责审查、一个跑测试，它们关注的点不一样，用的工具不同，分开就能更专注，更不容易相互干扰。 

这里的关键词是：  ** 职责清晰可分割。  **

  2. 需要通过对抗或者制衡来提高质量的场景。典型的例子就是一个 Agent 负责生成，一个 Agent 负责挑错。让做事情的和挑刺的分开，比让一个 Agent 既当裁判又当选手要靠谱。（  ` LLM-as-judge  ` 常见的坑） 

  3. 需要真正并行、且子任务之间耦合很低的场景。比如同时调研十个独立的主题，或者同时整理知识库里的十个不同文件，十个 Agent 各跑各的最后汇总。并行是实打实能够省时间的，且彼此不依赖，不会相互等。（我经常用这个玩法来整理知识库，很香；我把 Claude Code 接进了 Codex 子代理工作流） 

  4. 单个 Agent 的上下文装不下，需要分而治之的情况。任务信息量太大，塞进一个 Agent 会超上下文或者注意力涣散，拆给多个各管一摊更清醒。 

###  什么情况是过度设计？

  1. 如果一个任务的本质是线性的，一条链走到底的，那是工作流。 

这是最常见的伪需求，很多人把一个 Agent 按顺序做几步包装成多个 Agent 协作，其实根本没有真正的多方协作，只是流水线。

如果步骤之间是顺序依赖、不需要不同角色独立决策，那一个 Agent 带  ` Planning  ` 就够了，拆成多个 Agent 纯属增加复杂度。

我自己的那个短视频链路，看起来有六个节点（采集、下载、  ` ASR  `
、改写、混剪、发布），看起来很多环节，但本质上是一条线性流水线，后一步等前一步，没有谁需要做独立判断和博弈，所以它就该是一个 Agent
编排一条链，而不是六个 Agent。如果我硬要拆成六个 Agent，只会浪费 token 和增加出错点，没有任何收益。

  2. 多 Agent 带来的协调成本 > 它省下来的东西。 

` Multi-Agent  ` 有实打实的代价：Agent
之间要通信，要传递上下文，每多一次交接，就多一个出错和信息丢失的点；调试也会指数级变难，一个结果错了，你得排查哪个
Agent、哪次交接出了问题。如果任务没有复杂到需要分工，这些成本纯属浪费。

  3. 用 Multi-Agent 来掩盖单个 Agent 没调好。 

有时候单 Agent 效果不行，真正原因是提示词、工具、流程没设计好，结果有人不去解决根本问题，而是堆砌更多
Agent，用复杂度掩盖能力缺陷，只会让系统更脆弱，更难定位问题。

###  判断要不要上 Multi-Agent 的三个问题

总结一下，让我判断要不要上 Multi-Agent，先问三个问题：

  1. 任务能不能拆成责任清晰、互不重叠的角色？ 
  2. 这些角色之间是需要真正的并行或制衡，还是只是按顺序流水线？ 
  3. 多拆出来的成本高不高，划不划算？ 

![](/images/agent-qa-guide/img-05.png)

其实用一个简单的例子来解释就是：拍一个简单的短视频，你不需要编剧、导演、拍摄、编剧、场务、灯光、道具、妆造这些人，但是如果你拍的是一个院线大电影，那就需要了。

###  Multi-Agent 最大的工程挑战是什么？

其实就是上下文传递和结果可信度的问题。

如果一个 Agent 给另外一个 Agent 传递的信息是错的，那这个错误会沿着链路放大，而且很难定位是谁的锅。

##  问题五：Agent 任务失败了，怎么定位是“模型能力问题”还是“Harness / 工程问题”？

` Harness  ` 指的是包在模型外面的那一套工程脚手架：工具怎么调用、结果怎么解析、上下文怎么管理、失败了怎么重试、环境依赖、调度这些。

简单说，  ** 模型是大脑，Harness 是身体和环境。  **

所以本质上这个问题是在问，一个任务失败了，到底是脑子不行，还是手脚或者环境出了问题。

所以得先看模型的判断和意图本身对不对：

  * 如果模型想做的事是对的，调用的工具和参数也都合理，只是执行环节出了问题，那么大概率是  ` Harness  ` / 工程问题。 
  * 如果模型从一开始就理解错了任务，选错了工具，或者推理逻辑是错的，那么这才是模型能力问题。 

###  Harness / 工程问题的信号

  1. 模型决策正确，但是工具执行失败。 
  2. 结果是对的，但是  ` Harness  ` 把状态读错了。 
  3. 失败是环境相关、在特定条件下可以复现。 
  4. 同样的输入，换个更强模型也一样失败（  ` A/B  ` 测试）。这不是铁证，但它是一个很强的工程问题信号。 

###  模型能力问题的信号

  1. 模型理解错了任务意图，比如你让它去做  ` A  ` ，它去做  ` B  ` ，这就是指令理解问题。 
  2. 模型选错工具，或者参数构造得离谱，这是模型对工具理解问题。 
  3. 多步任务里逻辑断裂、规划混乱、绕路或者鬼打墙，比如重复干一件无效的事情、规划自相矛盾、或者可以往下走了还卡在原地，这是规划和推理的问题。 
  4. 换个更强的模型，问题就消失了（上面说的  ` A/B  ` 测试）。这也不是铁证，但很像模型能力或者模型理解的问题。 

###  实操怎么排查？

上面说的只是分类，实操上来看：

  1. 先要看完整的轨迹，定位到具体是哪一步。那一步的模型的决策是什么，工具返回了什么，把决策和执行分开来看。 
  2. 其次看错误信息的性质，是缺了某个库、连接超时这种明确的工程错误，还是说它根本没有理解我要什么这种语义的错误。 
  3. 接着做控制变量，同样的任务换一个更强的模型审视。问题还在，大概率是工程问题；问题没了，大概率是模型问题。但这里要小心，换模型往往也会顺手换掉系统提示、工具描述、参数习惯，所以它只能当强信号，不能当法院判决书。或者把错误那一步单独拎出来，在一个干净环境里手动跑一遍，看看是不是环境问题。 

##  问题六：上下文窗口、上下文工程是什么？长任务里上下文爆了怎么办（压缩 / 记忆 / 检索）？

###  上下文窗口（context window）

模型一次能看到的信息总量上限，按 token 算。

模型做任何推理，都只能基于这个窗口里装着的东西，窗口之外的看不到、不知道、不记得。它就像一个模型的工作台面，台面就这么大，放不下的东西就得拿走，拿走了它当下就看不见了。

###  上下文工程（context engineering）

指的是主动地、有策略地管理每一步往这个窗口里放什么。

早期大家关注的是  ` prompt engineering  ` （提示词工程，也就是怎么把每一句话问好），但是 Agent
时代，任务是多步、长链路的，真正要挑战的就变成了：在任务的每一步，怎么把最相关的信息恰好放到有限的窗口里，既不遗漏关键信息，也不被无关信息塞爆。

也就是说，  ** 提示词工程是怎么把问题问好，上下文工程是怎么管理好每一步模型该看到什么，后者是 Agent 长任务的核心工程。  **

> 上下文不是越多越好。塞多了无关信息，模型就容易分心，抓不到终点。上下文工程的目标也不是塞满，而是精准，给对的，不给多的。

###  为什么长任务上下文会爆？

Agent
跑长任务，每一步的推理、每次工具调用的返回、每个中间产物都会不断累计进上下文。一条几十步的链路跑下来，历史越堆越多，迟早是会超过窗口上限，这就是爆了。

爆了之后要么报错，要么模型开始忘记关键的信息，任务越跑越崩。

###  爆了怎么办？

三个手段：

方法  |  解决什么  |  代价   
---|---|---  
压缩 / 摘要（compression / summarization）  |  直接减小占用，让窗口腾出空间  |  摘要必然有损，可能压缩掉后面才发现有用的细节   
记忆 / 外部状态（memory / externalization）  |  让窗口只装下这一步需要的，其他存在外面，不占地方  |  需要设计好什么该写进去、什么时候读回来   
检索（RAG / Retrieval）  |  应对信息总量远超窗口的情况，不是一开始就把所有信息塞进来，而是每一步只取相关的  |  检索可能不准，找错了或者找漏了，模型就拿不到关键信息   
![](/images/agent-qa-guide/img-06.png)

###  三种手段怎么配合？

这三个不是三选一，是配合着用的：

  * ` RAG  ` 管的是从海量里只取相关的进来。 
  * 压缩管的是已经进来的历史怎么瘦身。 
  * 记忆 / 外置管的是什么该放窗口外，需要时再读回。 

一个完整的长任务通常是三个一起上。

这就好比你去图书馆里坐着写一篇长论文，  ` RAG  `
就是辅助你的图书馆管理员，记忆就好像辅助你管理桌子上的资料的人，而压缩摘要则是辅助你记录进度的人（随时帮你把进度记好摘要）。

从产品的角度来说，上下文管理的核心取舍是信息完整性和成本性能之间的考量。窗口塞越满，成本越高，响应越慢，模型越容易分心；塞得太省，可能丢关键信息导致任务失败。

这不是纯技术问题，而是产品权衡问题，要根据任务类型来定策略。短平快的任务可以激进压缩，高风险强依赖前文的任务就要保守地保留上下文了。

关于压缩时保留什么、丢什么，这个也很有讲究，跟任务目标强相关的，以及高风险不可逆的决策点要保留，比如关键指令、已经确定的约束、出过错的地方。纯过程性的、已经有结论的中间步骤可以压缩一句话就可以了，原则是保留决策依据，压缩执行过程。
